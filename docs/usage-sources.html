Usage Sources

Where vBilling's usage comes from, what each source guarantees, and how to bill AI gateways and Prometheus counters without losing a request or counting one twice.

Billing data is not telemetry

Runtime telemetry is built to watch systems. It may drop a sample under load, extrapolate between samples, and keep a few days of history. For a dashboard or an alert, that is fine.

A bill is different. Every unit must be counted exactly once: a lost minute is lost revenue, a doubled one is an overcharge. And the evidence must outlive the invoice, because customers dispute bills months later. So billing data needs its own pipeline.

In vBilling, every source lands in the same hash-chained ledger, one closed window at a time, with deterministic event IDs, before any billing platform sees it. What a source can guarantee depends on how vBilling reads it.

What each source guarantees

SourceGuaranteeKeep in mind

CPU and memory usage from metrics-server (CPU_MEMORY_BASIS=usage) is a sample of the live window and is never backfilled.

In a live run

On a kind control plane cluster with one cluster, Prometheus v2.55.1 scraping a test engine pod that exposes vLLM's output token counter, and vBilling installed from the chart, 17 one-minute windows included a rolling upgrade of vBilling, a 7-minute vBilling outage and a restart of the engine pod:

  • The counter: metric billed 20,500 tokens. Prometheus's raw samples for the same period sum to 20,500.0.
  • An increase() query on the same counter came to 20,700.13. Its windows held fractional quantities such as 1199.976 tokens, and a partial window read 921.8 tokens where the counter grew by 800.
  • A simulated LiteLLM gateway sent 60 requests (5,400 output tokens) and retried 10 of its batches. The ledger shows exactly 5,400. A record sent 4 minutes late became a separate 77-token adjustment to its own window.

scripts/e2e-usage-sources.sh in the repository runs these checks on a laptop.

Against a real LiteLLM v1.108.11 proxy with Postgres and mock responses, with both the push and the spend log pull on, six teams, users and end users made 312 successful requests (9,546 input and 3,744 output tokens) and 108 failed ones:

  • Per tenant, the ledger matched LiteLLM's own spend logs and the clients' responses exactly. Failed requests were skipped.
  • vBilling was stopped for 90 seconds. LiteLLM retried each batch three times, then dropped it, with the records of all 113 requests made meanwhile. The first pull after the restart stored exactly those 113 (3,529 input and 1,312 output tokens), billed as late adjustments to their own windows, and found the other 110 requests in its range already stored.
  • 199 requests delivered by both the push and the pull counted once.

Per-request records

AI usage happens per request. A gateway knows the tokens of each request, but summing them into windows, retrying failed sends and placing late arrivals is exactly where usage gets lost or doubled. POST /api/v1/records takes the records as they are and does that work inside vBilling.

curl -X POST localhost:8080/api/v1/records \ -H "Authorization: Bearer $INGEST_TOKEN" -H "X-VBilling-Client: edge-gateway" \ -d '{"id": "req-7f3a", "tenant": "acme-ai", "time": "2026-11-18T10:00:01.123Z", "usage": {"inference_input_tokens": 512, "inference_output_tokens": 128}, "sku": "llama-3.1-70b", "dimensions": {"endpoint": "chat"}}' { "format": "vbilling", "received": 1, "accepted": 1, "usage_rows": 2 }
FieldMeaning
idRequest ID, unique per request and the same on every retry. Required, unless RECORDS_ALLOW_UNKEYED=true derives one from the record's content (identical records then count once).
tenantThe tenant to bill: a tenant ID or an alias (see Which tenant pays). Ignored with a tenant-bound token.
time (or timestamp)When the request happened: RFC 3339 (UTC when no zone is given) or a Unix timestamp in seconds, milliseconds, microseconds or nanoseconds. It picks the window. Without it, vBilling uses the arrival time and warns.
usageQuantities by metric code. Every metric must be declared (see Custom metrics).
metric, quantityShorthand for one metric.
sku, region, projectEvent fields. region defaults to REGION.
tenant_clusterSets the tenant_cluster dimension.
dimensionsMore dimensions, as strings.
  • The body is one record, a JSON array, {"records": [...]} or NDJSON, up to 16 MiB.
  • ?format= (or the X-VBilling-Format header) picks the payload format: vbilling (the default), litellm, or a mapping of your own.
  • X-VBilling-Client names the emitter and defaults to the format name. It is part of each record's identity, so two emitters never deduplicate each other's request IDs. Keep it stable for one emitter, or its retries are not recognized as retries.
  • Ingest needs a token: INGEST_TOKEN (or API_TOKEN), or a tenant-bound token from INGEST_TOKENS.

Responses and retries

vBilling answers only after the records are fsynced to their own ledger, under DATA_DIR/records. On any answer other than 2xx, nothing was stored: retry.

StatusMeaning
200Stored. rejected lists the records refused one by one, with their index and reason: sending them again does not help. skipped counts records the format filters out, duplicates_in_batch repeated request IDs, and unknown_tenants and warnings report the rest.
400Nothing stored: an unknown format, a body that is not JSON, or every record rejected.
401, 403A wrong token, or ingest disabled because no ingest token is set.
413The body is over 16 MiB. Send smaller batches.
503Nothing stored. Retry. Either the records ledger could not be written, or vBilling has just started and has not discovered tenants yet, so it cannot map gateway identities with vbilling.vcluster.com/aliases (the response carries Retry-After: 5; this lasts until the first discovery, normally under a second and never more than two minutes, and does not apply to tokens bound to a tenant).

A record is refused when it has no request ID, no tenant, a metric that is not declared, a negative or non-numeric quantity, a time more than 5 minutes ahead of vBilling's clock, or a time older than RECORDS_RETENTION minus one hour (34 days at most). The vbilling_records_rejected_total{client} counter on /metrics counts them.

Windows, retries and late records

  • A record belongs to the window its time falls in, not to the window it arrives in.
  • RECORDS_SETTLE (default 30s) after a window ends, vBilling commits one usage event per tenant, metric, SKU and dimensions for that window. properties.records counts the requests in it. A request ID already counted for the window, from a retry or a resent batch, is dropped.
  • A record that arrives later becomes a separate late adjustment for the same window: same window_start and window_end, with properties.late: true and properties.arrived_by. Its ID is deterministic. Nothing is ever merged into a window that was already committed.
  • The split between on time and late depends only on when each record was stored, never on when vBilling ran. After a crash or an upgrade, vBilling rebuilds the same events with the same IDs: nothing is lost and nothing is counted twice.
curl -s 'localhost:8080/api/v1/events?tenant=acme-ai&metric=inference_output_tokens' \ | jq -c 'select(.properties.late) | {window_start, quantity, properties}' {"window_start":"2026-11-18T10:03:00Z","quantity":77,"properties":{"arrived_by":"2026-11-18T10:08:00Z","late":true,"records":1}}

Retention and evidence

Raw records stay under DATA_DIR/records for RECORDS_RETENTION (default 168h, at least 2h). They are the evidence behind each window's event and the input to aggregation; billing adapters receive only the window events. With RECORDS_ARCHIVE=true (Helm records.archive, which needs persistence.archive.enabled), vBilling also archives them to ARCHIVE_DIR/records before retention deletes them: request-level evidence for disputes, at a high volume. See Retention and disputes.

vBilling stores only the fields a format maps: request ID, time, tenant, quantities, SKU and dimensions. Prompts and responses in a payload are never stored.

Which tenant pays

Tenant-bound tokens

A token in INGEST_TOKENS is bound to one tenant. Everything sent with it is billed to that tenant, whatever the payload says, so a gateway inside a tenant's cluster can never bill another tenant. Give each such gateway its own token. In the Secret the format is token=tenant,...:

kubectl -n vbilling-system create secret generic vbilling-api \ --from-literal=api-token="$(openssl rand -hex 32)" \ --from-literal=ingest-token="$(openssl rand -hex 32)" \ --from-literal=ingest-tokens="$ACME_GATEWAY_TOKEN=acme-ai,$GLOBEX_GATEWAY_TOKEN=globex" helm upgrade vbilling deploy/helm/vbilling -n vbilling-system --reuse-values --set api.existingSecret=vbilling-api

The Helm value api.tenantIngestTokens takes the same tokens the other way round, as {tenant: token}, and renders them into the chart's Secret.

The tenant in the payload

Without a bound token, vBilling resolves the record's tenant value against:

  • the tenant IDs it knows, such as vcluster-<namespace>-<name> or a cluster's vbilling.vcluster.com/tenant value;
  • the aliases in vbilling.vcluster.com/aliases, a comma-separated list on a cluster's StatefulSet or Deployment, its namespace, or its vCluster Platform VirtualClusterInstance;
  • for a custom format, its tenantMap, applied first.
# Records from LiteLLM team e2f1c0de-... are billed to the tenant of this cluster kubectl annotate namespace globex vbilling.vcluster.com/aliases=e2f1c0de-7b1a-4c55-9a7e-2d4f8b3c6a10,globex-prod

A record for a tenant that matches nothing is accepted and reported: the response lists it under unknown_tenants with a warning, and the source records/<client>/unknown-tenants turns empty in source health. Its usage is billed to a tenant with that raw ID, so your billing platform gets a customer with that ID. RECORDS_UNKNOWN_TENANTS=reject refuses such records instead. See Records billed to an unknown tenant.

AI gateways

An AI Cloud that sells inference bills per token, and only the gateway in front of the inference engines knows which customer sent each request. Any gateway works: it posts one record per request, in vBilling's own format, in LiteLLM's built-in format, or in any JSON shape through a mapping. If the gateway also keeps its own log of requests (a database or a logs API), vBilling can read that log back to fill what the push lost. LiteLLM has a built-in format and a built-in pull; every other gateway uses a mapping and a pull spec.

LiteLLM

LiteLLM's generic API logger posts a StandardLoggingPayload for every request. The built-in litellm format reads it as posted. Enable it with RECORDS_LITELLM=true (Helm records.litellm: true); it is off by default because it declares inference_input_tokens and inference_output_tokens, which every billing adapter then creates.

# LiteLLM proxy config.yaml litellm_settings: callbacks: ["vbilling"] callback_settings: vbilling: callback_type: generic_api endpoint: http://vbilling.vbilling-system.svc:8080/api/v1/records?format=litellm headers: Authorization: os.environ/VBILLING_AUTHORIZATION # "Bearer <ingest token>" max_retries: 5 # retries after a connection error, a timeout or a 5xx retry_delay: 1 # seconds, doubled on each retry: 1, 2, 4, 8, 16

The endpoint assumes LiteLLM runs in the control plane cluster and vBilling in vbilling-system. A gateway elsewhere needs a route to vBilling's Service. The shorter form, callbacks: ["generic_api"] with GENERIC_LOGGER_ENDPOINT and GENERIC_LOGGER_HEADERS in the environment, works too, but never retries. See LiteLLM's Generic API Callback docs.

Neither ID alone identifies a request. A client can set litellm_call_id with the x-litellm-call-id header, so keying on it would let a tenant make its requests look like retries of one. Response IDs repeat: every cache hit of one entry returns the cached response's ID, and some providers return the same ID for every call.

Records are billed to the team of the virtual key. LiteLLM generates team IDs unless you pass team_id when you create a team, so either create teams with the tenant ID as their team_id, or list each team ID in the vbilling.vcluster.com/aliases of the tenant's cluster. A LiteLLM that serves one tenant can use a tenant-bound token instead.

!
LiteLLM queues records in memory and posts them in batches: by default every 512 records or 5 seconds (DEFAULT_BATCH_SIZE, DEFAULT_FLUSH_INTERVAL_SECONDS). A batch dropped after its retries, or still in the queue when the proxy stops, is never sent again. To recover them, pull LiteLLM's spend logs. Each record also carries the messages and the response, so lower DEFAULT_BATCH_SIZE when prompts are long: vBilling accepts up to 16 MiB per request.

Pulling LiteLLM's spend logs

LiteLLM also writes every request to its own database, in the LiteLLM_SpendLogs table. vBilling can read those rows back through LiteLLM's GET /spend/logs/v2 API and ingest them as litellm records. The push stays the fast path; the pull fills whatever the push lost, such as batches LiteLLM dropped while vBilling was down.

records: pullLiteLLM: url: http://litellm.litellm.svc:4000 existingSecret: litellm-admin # key litellm-key: the master key or a proxy admin key interval: 5m lookback: 1h

Without Helm, set RECORDS_PULL_LITELLM_URL and RECORDS_PULL_LITELLM_KEY. Setting the URL also enables the litellm format. It needs LiteLLM v1.103.0 or later, with a database.

  • Counted once. A pulled row gets the same record ID as the pushed record of the same request: the same client, the same tenant value, the same <litellm_call_id>/<id> and a time rounded to the same millisecond. The pull does not store rows that are already in the records ledger, and the aggregator drops any duplicate that slips through.
  • Same identity as the push. The client is part of every record ID. The puller uses litellm, which is what the push uses unless it sends X-VBilling-Client; if it does, set records.pullLiteLLM.client to the same value. If the push uses a tenant-bound token, set records.pullLiteLLM.tenant to that token's tenant.
  • Late rows are adjustments. A pulled request whose window has already settled is billed as a late adjustment to its own window, never merged into the committed event.
  • Outages are covered. Each pull starts lookback before the end of the last successful pull, which vBilling keeps in DATA_DIR/litellm-pull.json. The first pull after an outage reads the whole outage, up to the records retention. Pulls start once vBilling has discovered its tenants, so aliases apply.
  • Only successful requests are read, as with the push.

The pull reports as the source records/litellm/pull in source health, with the rows read by the last pull as series. On /metrics: vbilling_records_pull_runs_total, vbilling_records_pulled_rows_total, vbilling_records_pulled_new_total (requests the push had missed), vbilling_records_pull_failures_total and vbilling_records_pull_last_success_timestamp_seconds, each with a client label.

!
The pull recovers only what LiteLLM stored. LiteLLM writes spend logs in batches too, so requests it had not written when it stopped are in neither copy. LiteLLM keeps one row per response ID: in a test where a mock model returned one ID for 20 requests, its spend logs kept one row, while the push billed all 20. Rows without litellm_call_id, from LiteLLM releases before v1.103.0, are not ingested and turn the source failing, because they cannot be matched to pushed requests.

Any other gateway

A gateway that can post JSON for each request, such as Kong, an Envoy AI Gateway access log or your own proxy, needs a mapping, not a shim: field paths for the request ID, the time, the tenant and the quantities. With Helm, add it under records.formats. Without Helm, put the same YAML, a map of format names, in a file and point RECORDS_MAPPINGS_FILE at it. Then post to /api/v1/records?format=kong.

records: formats: kong: id: request.id time: started_at tenant: consumer.username tenantMap: {acme-prod: acme-ai} # gateway value: tenant ID usage: inference_input_tokens: ai.proxy.usage.prompt_tokens inference_output_tokens: ai.proxy.usage.completion_tokens sku: ai.proxy.meta.response_model

Kong's AI fields differ between Kong versions and plugins. Check one real log entry from your Kong and adjust the paths before you bill from it.

KeyMeaning

A path is dotted, or a list of paths of which the first non-empty one wins. timePrecision (for example 1ms) rounds each record's time; set it when the gateway's own log, read back by a pull, stores times less precisely than the push sends them, so both copies of a request fall in the same window. When it is enabled, the built-in litellm format declares inference_input_tokens and inference_output_tokens (unit tokens, priced by sku), so any format can use them, and billing adapters create them at startup. Declare other metrics in a format's metrics or in metering.customMetrics, which wins. A format named litellm replaces the built-in one; vbilling cannot be redefined.

Pulling any gateway's request log

A push can lose records: a batch the gateway drops while vBilling restarts, a gateway crash before it sends. When the gateway keeps its own request log behind an HTTP API, list it under records.pull (or in a YAML file named by RECORDS_PULL_FILE). Every interval, vBilling reads the log from the end of the last successful pull minus lookback, maps each row with the same format as the push, and stores only the requests it does not have yet. Pushed and pulled copies of a request get the same record ID and count once; rows that arrive after their window settled become late adjustments.

records: pull: - name: kong-logs format: kong # the format the push uses client: kong # the push's X-VBilling-Client (default: the format name) url: "https://logs.example.com/requests?from={{from}}&to={{to}}&page={{page}}&limit={{limit}}" headers: {Authorization: "Bearer ${RECORDS_PULL_KONG_TOKEN}"} rows: data # path to the array of rows in the response paging: {mode: page, limit: 500} interval: 5m lookback: 1h pullEnv: - {name: RECORDS_PULL_KONG_TOKEN, secret: kong-logs, key: token}

name, formatRequired. The name appears in source health and metrics. The format maps each row, so the log's rows must carry the same request IDs the push sends.
client, tenantPart of every record ID, so they must match the push: client is the push's X-VBilling-Client, and tenant is set when the push uses a tenant-bound ingest token.
url, method, bodyThe request. Placeholders: {{from}} (required) and {{to}}, {{page}}, {{offset}}, {{limit}}, {{cursor}}. method is GET (default) or POST with a JSON body.
timeFormatHow {{from}} and {{to}} are written: rfc3339 (default), unix, unixms, or a Go layout such as 2006-01-02 15:04:05, in UTC.

Each pull reports as records/<client>/pull/<name> in source health: failing with the HTTP status when the log cannot be read, or when every row is rejected by the format. Error messages never include the URL's query string. The vbilling_records_pull_* metrics count runs, rows read, new requests and failures per pull.

Prometheus counters and queries

Metrics in prometheus.metrics (Helm) or PROMETHEUS_METRICS_FILE are read from Prometheus for every cluster and window. Give each one a counter: or a query:.

prometheus: url: http://prometheus.monitoring.svc:9090 metrics: - code: inference_output_tokens name: Inference output tokens unit: tokens dimensions: [model_name] skuLabel: model_name counter: vllm:generation_tokens_total{{selector}} # exact: raw samples
KeyMeaning
code, name, unit, descriptionThe metric, as billing platforms see it.
counterA plain series selector of a monotonic counter, such as vllm:generation_tokens_total{{selector}}: no functions, no range. Exact. vBilling sums the matching series per dimension itself.
queryAny PromQL returning one value per series at the window end. An estimate.
billableDefault true. false keeps the metric informational: it stays in the ledger, the exports and the webhook feed, and never reaches Stripe, Metronome or Lago. Use it for a second source to cross-check.
scaleMultiplies every quantity, for example 0.001 to turn milliseconds into seconds.
dimensionsSeries labels kept as event dimensions and pricing group keys. modelName becomes model_name.
skuLabelThe label whose value becomes the event's SKU. sku, its v0.2 name, still works and logs a warning.

Templates: {{selector}} and {{matchers}} scope series to the cluster (see below), {{namespace}}, {{vcluster}} (the cluster's name), {{instance}}, {{project}}, {{tenant}}, {{tenant_cluster}}, {{window}} (for example 60s) and {{window_seconds}} (for example 60).

Bill each kind of usage from one source. If a gateway already sends inference_output_tokens as records, give the engine's counter its own code and billable: false, and compare the two with a cross-check.

How counters are billed

  • vBilling asks Prometheus for the raw samples of every matching series (a range selector, which Prometheus returns as stored, without extrapolation) and bills each sample's increase in the window the sample falls in. A drop in value is a counter reset: the new value counts in full.
  • A window's quantity runs up to its last sample, so usage between that sample and the window's end lands in the next window. Nothing falls between windows.
  • The last sample of each series is the next window's starting point. These baselines are saved in DATA_DIR/prom-counters.json in two generations, and the ledger decides which one is in force after a restart, so a crash between saving them and committing a window cannot count that window twice.
  • On the first read of a counter, its history is not billed: billing starts with the first window vBilling reads. A series that appears later, such as a new pod or a new model, counts from zero. A series not seen for 7 days is forgotten.
  • PROMETHEUS_LOOKBACK (default 10m) is how far before a window vBilling looks for a counter's starting sample. Keep it longer than the scrape interval plus any remote-write delay.
  • Usage after a pod's last scrape never reaches Prometheus, so no counter can bill it. Scrape inference engines often, so little is left between the last scrape and a pod's end.

Outages

Prometheus usage is committed under its own ledger source, with its own watermark, after the Kubernetes windows. Kubernetes metering never waits for Prometheus.

  • vBilling was down: on restart it reads every window it missed, up to MAX_BACKFILL, and each counter sample lands in its own window. A counter's usage from before that is billed in the first window read.
  • Prometheus is down (every read fails): nothing is committed and the sources turn failing. The windows wait, and once Prometheus answers they are read one by one, counters and queries alike, so each window gets its own usage.
  • Only some reads fail (one cluster's own Prometheus, one metric): the window is committed without them. Those counters keep their last sample, so the first window that reads them again bills the whole increase since then. The total stays exact; that usage lands in the recovery window. A query that failed has no usage for that window.

Cross-checks

A gateway counts the tokens that pass through it; an inference engine counts the tokens it generated. Both see the same requests, so they should agree. When they do not, a gateway batch was lost, requests bypassed the gateway, or scrapes went missing. A cross-check finds out within the hour, before an invoice goes out, instead of in a dispute afterwards.

prometheus: metrics: - code: vllm_output_tokens # the second source, never billed name: vLLM output tokens unit: tokens billable: false counter: vllm:generation_tokens_total{{selector}} crossChecks: - primary: inference_output_tokens # billed, from LiteLLM records secondary: vllm_output_tokens tolerancePercent: 2

Without Helm: CROSS_CHECKS="inference_output_tokens=vllm_output_tokens:2%". Both metrics must be declared. The default tolerance is 1%.

  • Every 5 minutes, vBilling compares each tenant's totals for the last complete hour, 10 minutes after it ends, so late records and Prometheus catch-up are in.
  • The divergence is the difference between the two totals divided by the larger one. Above the tolerance, the source crosscheck/<primary>~<secondary>/<tenant> turns diverged with both totals, and vbilling_crosscheck_divergence_ratio{check,tenant} on /metrics shows the ratio.
  • Billing continues from the primary. A cross-check tells you which tenant, which hour and by how much; it never changes a bill.
  • The engine's counter is attributed to the cluster the engine runs in, so the check works per tenant when each tenant's traffic is served by engines in its own clusters. Gateway cache hits and traffic that skips the gateway also show up as divergence: set the tolerance for them.
curl -s 'localhost:8080/api/v1/crosscheck?tenant=acme-ai' | jq '.rows[] | select(.ok | not)' { "check": "inference_output_tokens~vllm_output_tokens", "tenant": "acme-ai", "from": "2026-11-18T09:00:00Z", "to": "2026-11-18T10:00:00Z", "primary": 1843200, "secondary": 1920000, "divergence": 0.04, "ok": false }

GET /api/v1/crosscheck takes from, to, tenant and bucket=hour (default) or day. Without a range it covers the last 24 complete hours.

Source health

A billing pipeline that fails quietly is worse than one that stops. A selector that matches nothing and a cluster API that refuses its credentials both look like zero usage. vBilling records the outcome of every attempt, for every source:

SourceName
A Prometheus metric, per clusterprometheus/<metric>/<cluster>
A cluster's own APItenant-api/<cluster>
A records clientrecords/<client>, and records/<client>/unknown-tenants
The LiteLLM spend log pullrecords/<client>/pull
The records aggregatorrecords/aggregator
A cross-check, per tenantcrosscheck/<primary>~<secondary>/<tenant>

<cluster> is the cluster's ID, vcluster-<namespace>-<name>. Each source has a status:

StatusMeaning
okThe last attempt returned data.
emptyThe source answered with nothing. For a billed metric this is usually a selector that matches no series; message says how the cluster was scoped and hint what to change.
failingThe last attempt failed; last_error_message has the error.
divergedA cross-check's two sources disagree beyond the tolerance.
  • GET /api/v1/sources lists every source, problems first, with status, message, hint, since, last_success, last_error, last_error_message, series and how many attempts in a row failed or were empty. ?kind= narrows it to prometheus, tenant-api, records or crosscheck.
  • GET /api/v1/status adds healthy (no source needs attention), sources (counts by status) and warnings (one line per problem, with its hint).
  • /metrics has vbilling_sources{kind,status}. Alert on vbilling_sources{status!="ok"} > 0.
  • The log, prefixed [health], records every change of state, and repeats a problem after 1, 10, 100 and more attempts in a row.
  • The dashboard has a Usage sources tile and panel.
  • A source that stops reporting, such as a gateway that stopped posting, keeps its last status, and vBilling forgets it after 6 hours. Watch last_success of records/<client>, or let a cross-check against the engine catch a silent gateway.

This cluster runs on its own nodes: its series must carry vcluster=<cluster name> ...)" ] }

What to do about an empty Prometheus source: A Prometheus metric returns nothing.

Window totals

POST /api/v1/events takes closed windows that your own pipeline already summed, such as Slurm accounting or a storage exporter (see the Ingest API). An event without an id gets one derived from its tenant, metric, window and dimensions, so two requests in the same window would look like one event sent twice. Since v0.3, vBilling rejects the second of two such events in one request, and warns when an event without an id matches usage already in the ledger. Per-request usage belongs in records, which sum it.
