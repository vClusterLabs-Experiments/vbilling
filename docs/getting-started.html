Getting Started

Install vBilling in your control plane cluster, connect the billing platform you run, and see the first usage arrive. vBilling meters; your billing platform prices, invoices and collects.

Prerequisites

  • A control plane cluster with at least one cluster. vBilling meters every tenancy model: clusters with their own nodes (vCluster Private Nodes, Auto Nodes, Standalone), dedicated nodes and shared nodes.
  • kubectl and Helm 3
  • metrics-server in the control plane cluster, for CPU and memory usage
  • An account on your billing platform (a Stripe sandbox, a Metronome account), or Docker to run Lago locally
i
vBilling finds clusters by their StatefulSets or Deployments (label app=vcluster), and through the vCluster Platform API when it is available. No cluster yet? Run everything on a laptop with vind and Lago, or follow the GKE example with real GPUs.

1Choose a billing platform

vBilling is the pipe, not the billing engine: prices, invoices and payments stay in the billing platform you choose. Each platform has a billing adapter in vBilling, and several adapters can run at once (for example adapters='{stripe,webhook}'), each with its own delivery cursor.

Billing adapterChoose it for
StripePay-as-you-go prices per metric and SKU, with Stripe invoices, payments and tax
MetronomePricing on many dimensions, commits, credits and rate cards, optionally with Stripe collecting payment
LagoOpen source, self-hosted billing that also runs on a laptop with Docker Compose
Custom Billing AdapterYour own rating engine or data platform, through signed CloudEvents webhooks or an adapter written in Go

2Install vBilling

The chart defaults to the published image ghcr.io/vclusterlabs-experiments/vbilling:v0.3.3 (linux/amd64 and linux/arm64). Keep billing keys in Secrets, never in --set flags or values files. Install from a release tag, because main can be ahead of the published image. From a clone of the repository, with Stripe as the example:

git clone --branch v0.3.3 https://github.com/vClusterLabs-Experiments/vbilling.git && cd vbilling kubectl create namespace vbilling-system kubectl -n vbilling-system create secret generic vbilling-stripe --from-file=api-key=./stripe-test-key helm upgrade --install vbilling deploy/helm/vbilling -n vbilling-system \ --set adapters='{stripe}' \ --set stripe.existingSecret=vbilling-stripe \ --set region=us-east-1

Each release also has the packaged chart attached, so you can install without a clone: replace deploy/helm/vbilling with https://github.com/vClusterLabs-Experiments/vbilling/releases/download/v0.3.3/vbilling-0.3.3.tgz.

The other adapters take the same shape:

AdapterSecret keysHelm values
stripeapi-key, webhook-secretstripe.existingSecret
metronomeapi-token, webhook-secretmetronome.existingSecret, metronome.provision
lagoapi-keylago.existingSecret, lago.apiURL
webhooksecretwebhook.existingSecret, webhook.url
noopNone: logs every event instead of sending it, for a dry run

Run one vBilling per control plane cluster and set region: it is stamped on every event, and every ledger record stays in that cluster.

Run from source (development)

make build ADAPTERS=noop DATA_DIR=./data ./bin/vbilling

Outside a cluster, vBilling uses your current kubeconfig context. With noop, each event is logged ([noop] event tenant=... metric=... qty=...) instead of sent.

3Configure pricing and packaging

vBilling creates the metrics in your billing platform; the prices are yours. Every tenant is on the default plan vcluster-standard unless its cluster carries vbilling.vcluster.com/plan.

  • Stripe: a metered price on each meter you charge for, tagged with the plan for automatic subscriptions. See Prices and subscriptions.
  • Metronome: rate card products on the billable metrics, priced on dimensions such as SKU, region and capacity type. See Pricing on dimensions.
  • Lago: the plan's charges, with charge filters on sku or capacity_type. See Configure pricing.

Every event carries the dimensions to price on, among them sku, region, capacity_type (on-demand, spot, preemptible or reserved), billing_mode and tenant_class. See the Metrics Reference.

4Verify it works

vBilling meters closed windows (60 seconds by default), commits them to its ledger, and delivers them to each adapter.

kubectl -n vbilling-system logs statefulset/vbilling Using in-cluster Kubernetes config [controller] starting (adapters=[stripe], window=1m0s, reconcile=30s, region=us-east-1) API listening on :8080 [controller] window 10:18:00: ... events for 3 tenant cluster(s) (...)
export VBILLING_TOKEN=$(kubectl -n vbilling-system get secret vbilling -o jsonpath='{.data.api-token}' | base64 -d) # the API token the chart generated kubectl -n vbilling-system port-forward svc/vbilling 8080 # dashboard: http://localhost:8080/ (it asks for the token) curl -H "Authorization: Bearer $VBILLING_TOKEN" -s localhost:8080/api/v1/status | jq '.destinations' # delivery health per adapter curl -H "Authorization: Bearer $VBILLING_TOKEN" -s 'localhost:8080/api/v1/usage?group_by=tenant,sku' | jq # line items from the ledger curl -H "Authorization: Bearer $VBILLING_TOKEN" -s localhost:8080/api/v1/reconcile | jq '.results[] | {destination, ok}' # Stripe and Metronome
✓
Once the destinations report deliveries, the usage is in your billing platform: meters and customers in Stripe, customers and usage in Metronome, or customers and subscriptions in Lago. A platform outage never loses usage: the ledger keeps it until the adapter catches up.

Upgrading to v0.3.3

v0.3.3 makes usage read from Prometheus exact at its edges, shows prices per series, lets an operator decide where a destination starts, checks pushed usage like measured usage, and keeps a live second copy of the ledger. It was shaped by a validation of v0.3.2 on vCluster Platform, with clusters on their own nodes and a Metronome sandbox, that exercised every metric, delivery path and billing state. Run helm upgrade with the v0.3.3 chart and keep the PVC.

Act on these:

  • The archive volume gets a second job. With persistence.archive.enabled, vBilling keeps a live copy of the whole data directory in <archive>/mirror and restores itself from it when it starts on an empty data volume. Size the archive volume for the archive plus the data volume's used space: the mirror leaves a tenth of the volume to the archive, and says so when it does not fit. On a bucket mounted through FUSE no mirror is kept (persistence.archive.mirror: auto); off keeps none anywhere. The mirror holds the generated API and ingest tokens, so protect the archive volume like the data volume. See The ledger mirror.
  • A configuration check runs before every install and upgrade. A pre-install and pre-upgrade Job runs vbilling check-config with the new values and fails the release, before the pod is replaced, when vBilling would refuse them at start-up. It pulls the image and creates a Job and ConfigMaps in the release namespace; Argo CD runs it as a PreSync hook. configCheck.enabled=false switches it off. See Check a configuration before it rolls out.
  • **production-values.yaml on an existing release.** The file now names a storage class for the data volume and keeps the pod off nodes labelled nvidia.com/gpu.present=true, and the chart refuses values that still hold a REPLACE_WITH_ placeholder. Kubernetes refuses to change the volume claim template of an existing StatefulSet, so the upgrade fails unless persistence.storageClass is the class the data volume already has: set that on an existing release. If that volume is node-local on a GPU node, the new affinity leaves the pod Pending: move the ledger first, or leave the affinity out until you have.
  • Pushed usage is checked like measured usage. An event pushed under a metric vBilling measures itself (GPU, CPU, memory, node, control plane, storage, load balancer, egress, anything read from Prometheus) is refused with reason reserved_metric, and a metric that a records format declares takes records only, unless you also declare it in metering.customMetrics. Operator corrections go to POST /api/v1/events?operator_adjustment=true with the API token. dimensions.tenant_cluster must name a cluster of that tenant, for a window in which it existed. RECORDS_UNKNOWN_TENANTS now covers POST /api/v1/events too: with reject an unknown tenant is refused, with the default accept it is stored and reported. Check what your emitters send against the ingest rules; every refusal has a reason and is counted.
  • **GET /api/v1/pricing has one row per series.** combinations and missing are gone: each row carries dims, the values of the metric's other pricing keys, and its own status, so a $0 rate is a zero row and a count in vbilling_price_series{destination,status}. A tenant without a customer or an active contract is unpriced (held with PRICE_CHECK=hold), no longer unknown. With METRONOME_PROVISION=true the check reads the rate card of each tenant's contract, so pointing the rate card alias elsewhere no longer holds a tenant that has a contract: to stop delivery on purpose, pause the destination.
  • A destination you remove and add back waits for you. vBilling neither replays nor skips what was recorded meanwhile: the destination is awaiting_start, its delivery/<name> source fails with the numbers, and POST /api/v1/destinations/<name>/start with {"from": "cursor"}, "head" or a time decides. POST …/pause and …/resume stop and continue delivery without touching the cursor. v0.3.2 kept no record of a removal, so a destination re-added in the same rollout as this upgrade is not fenced: upgrade first, then add it back. See Delivery operations.
  • Alert rules and metric labels. Apply the new vbilling-alerts.yaml: 19 rules, each with what to do. vbilling_records_rejected_total gained a reason label, and vbilling_held_events counts the price check only: events parked for a tenant that could not be set up are vbilling_parked_events.
  • Optional access inside clusters. With list and patch on ReplicaSets, StatefulSets, DaemonSets and Jobs in the in-cluster role, workloads come back at once when a suspension is lifted instead of when their controllers next retry. See enforcement inside the cluster.
  • Do not downgrade in place. v0.3.2 does not know the destination marks next to the cursors, and reads events parked for a tenant as price holds. Take a consistent backup of the data directory before the upgrade. To go back, resume or start every destination and let parked events drain first.

Behavior that changed:

  • Prometheus windows wait for their samples. A window is read once the cluster's newest sample is past its end, at most 60 seconds later (30 seconds for a cluster with only query: metrics); metering from Kubernetes does not wait. Every window holds the samples taken in it, live or after an outage. A sample that arrives later still is billed in the next window and counted in vbilling_prometheus_late_samples_total.
  • Counters that restart. A counter that starts seconds before a window closes counts from zero when its _created series or its process start time shows it is new, so a restarted engine loses nothing.
  • Idle GPUs. vcluster_gpu_utilization records 0% for an idle GPU instead of nothing.
  • Egress. The built-in metric counts the interfaces of pods only. The node's own interfaces, which every host-network pod repeats, are no longer summed: expect lower egress for clusters with their own nodes. EGRESS_QUERY=none and GPU_UTIL_QUERY=none take the metric out of the catalog.
  • Control plane hours. They follow the time a replica was ready, to about a second. For a paused cluster they stop when its last replica is gone, a few seconds before the verified stop that ends node and workload billing.
  • Deleted and changed objects. A deleted cluster, volume or load balancer is billed up to the second it was deleted, a resized volume at each size for its time, and volumes and load balancers from the second they were bound or got an address.
  • Excluded clusters. A cluster or tenant taken out of metering is billed up to the moment vBilling sees the exclusion and again from the moment it sees it end. Excluded time is never backfilled, counters skip what was counted meanwhile, and the tenant's record lists the cluster under excluded_clusters.
  • Node downtime. A node that fails and recovers within one window is not billed for the time between, and after a resume a kubelet that has not reported yet is not taken for a dead node.
  • **Node-hour events carry disk_gib.** Their IDs differ from v0.3.2's for windows metered after the upgrade. Committed windows are never sent again, so nothing is billed twice.
  • Late windows are marked. A window that closed before vBilling started carries backfilled: true, also when it is the newest one.
  • A changed billing ID is reported. When the billing ID of a Tenant or Project changes, vBilling logs it, counts it in vbilling_tenant_id_changes_total, reports a source, and writes the previous ID into the new customer's metadata.
  • One tenant cannot stall delivery. A tenant whose customer cannot be created waits alone: its events are parked and retried while every other tenant is delivered. Replaying dead letters answers 200 with what was replayed, what is still rejected and what was refused.
  • Pauses and suspensions. A hold lifted while its pause is still in progress ends the pause. A pause lowered to a suspension first restores the cluster's workloads, for at most 2 minutes after its API answers again, and then blocks new pods. A cluster whose API refuses vBilling is stopped at once and reported as enforcement-access/<cluster ID>, and a paused cluster whose stop could not be verified is the failing source pause/<cluster ID>, so the shipped alert on failing sources fires for both.
  • Webhooks and repairs are counted. vbilling_webhooks_total{source,result} and the source billing-unlock/<tenant> show a payment that did not unlock its tenant, vbilling_enforcement_repairs_total{kind} counts a policy vBilling had to put back, and vbilling_tenant_billing_state has a series for every known tenant.
  • Start-up. Everything is checked before vBilling takes the Lease, and the archive directory is created at start: an archive volume that is not mounted or not writable fails at once instead of at the first compaction.
  • Backfill reaches 24 hours. Windows missed while vBilling was down are metered up to 24 hours back (6 before), in batches of 6 hours, so a long backfill needs no more memory than before. An object deleted while vBilling was down is not in them.
  • Customer names follow tenants. With METRONOME_PROVISION=true, a customer vBilling created is renamed when its tenant's display name changes. Customers it found by alias or was given, and customers created before v0.3.3, keep their names.

New, off until you set them:

  • Grace periods. ENFORCEMENT_ESCALATIONS (enforcement.escalations) raises a billing hold after a set time, for example delinquent to suspended after 72 hours and suspended to paused 7 days later, and GET /api/v1/billing-states shows each tenant's next step and when. See Grace periods.

Upgrading to v0.3.2

v0.3.2 is the release run end to end against a live Metronome sandbox, with vCluster Platform on GKE, three teams' clusters and their inference tokens, and a dedicated A100 cluster. It fixes what that run found and ships the readiness fixes the v0.3.1 artifacts were rebuilt with on 2026-11-19. Run helm upgrade with the v0.3.2 chart and keep the PVC.

Act on these:

  • Leases. Host and tenant-reader roles need get,list on Leases (stale node Leases briefly hold a window). For spot or preemptible GPUs keep billing.collectionDelay: 75s.
  • Backups before you upgrade. The ingest index is rewritten in a compact format that older binaries cannot read: take a consistent backup of the data directory (with source.json and destination state) and do not downgrade in place.
  • A low-balance warning next to the pause. If your Metronome account has a warning notification of the same type as the one that pauses, give it a rule of its own: ENFORCEMENT_RULES="alerts.low_remaining_commit_balance_reached=paused,alert:<its name or ID>=warning". Before v0.3.2 a rule on the type paused at both thresholds.

Behavior that changed:

  • Pauses through vCluster Platform. With TENANT_SOURCE=platform, the Platform proxy holds calls to a stopped cluster until they time out instead of refusing them, so a pause of a cluster with its own nodes was never verified, and its nodes and GPUs kept billing while paused (found live on the A100). A call that gets no answer now counts as the API gone once the control plane cluster shows no pod of the cluster's control plane left.
  • Wallets refilled without a payment. A commit or credit Finance adds to the contract sends no payment webhook. Every minute vBilling reads Metronome for tenants a threshold notification paused, and lifts the hold once nothing that counts is in alarm. Holds a failed payment raised still wait for a payment; holds set by an operator or through the API (a portal's "awaiting first payment") are never lifted this way.
  • Rules per notification. ENFORCEMENT_RULES takes alert:<name or ID>=state for one Metronome threshold notification, which wins over a rule on its type.
  • Instance shape while a GPU driver loads. A node whose GPUs GPU Feature Discovery counts but whose device plugin advertises none yet (after a boot, while the driver loads) carried the SKU cpu-node and gpu_count 0 on its node-hour events. It now carries its GPU SKU and count from its first minute; its GPU hours are still GPU downtime until the GPUs are allocatable.
  • Rewinding a destination by time. POST /api/v1/destinations/<name>/cursor takes {"from": "<RFC 3339 time>"}: everything the ledger committed since then is sent again.
  • Reconciliation notes. Rows of a tenant no Metronome customer holds yet, or of tenants that share a customer, say so in note.
  • Independent collectors. Automatic aggregates include the persisted metering source, separating two hosts billing the same customer, model and window. Keep the whole data directory, including source.json and destination state, together in backups.
  • Stripe delivery recovery. Attempts and confirmations are persisted before network calls and cursor acknowledgement. An uncertain outcome older than 23 hours is parked for reconciliation instead of blindly retried. Provider acceptance is separate from inclusion on a finalized invoice. See Stripe recovery.
  • Stripe split meters. New meter names include a digest of the original split keys and values, so org/model, org-model and case differences remain separate. Existing names are retained when the available ledger history identifies one split identity. Ambiguous names, or names without retained evidence, get separate meters and need price coverage checked before use. Existing prices are not rewritten.
  • Ingest memory. The 48-hour index uses 128-bit hashes and integer timestamps. Existing indexes load automatically; compaction rewrites them to the new format. Old binaries cannot read the rewritten index: take a consistent backup before upgrading and do not downgrade in place.
  • Namespace ownership and node failures. Cross-namespace objects retain their owner's attribution; mixed Prometheus namespaces require pod and namespace labels. Stale node Leases briefly hold affected windows. Update tenant-reader roles to allow get,list on Leases. For spot capacity keep billing.collectionDelay: 75s, since a failure just before collection can still look fresh.
  • Production sizing. production-values.yaml provides an initial configuration with archival, price holds, tenant validation and larger resource allocations. Size it from measured request volume and retention; raw request rows often dominate the ledger. The file is not part of the packaged chart or the release assets: when you install without a clone, download it from the tag (https://raw.githubusercontent.com/vClusterLabs-Experiments/vbilling/v0.3.2/deploy/helm/production-values.yaml) and pass it with -f. It turns the archive on with existingClaim: vbilling-archive, so create that PersistentVolumeClaim in the release namespace first; without it the vBilling pod stays Pending.

Upgrading to v0.3.1

v0.3.1 closes the issues a second independent review found in v0.3.0: tenants can no longer lower their own bill, the API is never open, and the Metronome adapter no longer assumes it owns your Metronome account. Run helm upgrade with the v0.3.1 chart and keep the PVC.

Act on these:

  • API token. Every endpoint except /healthz and /readyz needs it, including the dashboard and /metrics. Without api.token or api.existingSecret the chart generates one and keeps it across upgrades. Tools that render with helm template (Argo CD) must set one of them, or the token changes on every render.
  • Ingest token. Gateways send INGEST_TOKEN (the chart generates it, key ingest-token) or a tenant-bound token. The API token is refused at ingest, so a gateway that sent it under v0.3.0 must switch.
  • Metronome. vBilling no longer creates billable metrics, customers or contracts unless metronome.provision=true (metronome.stripeLink=true still implies it). Add vBilling's billable metrics to your catalog before installing (vbilling metronome billable-metrics prints them): Metronome counts only usage sent after a metric exists, so vBilling holds usage no billable metric counts, for up to 23 hours. A customer pinned with metronome-customer-id needs the tenant ID as an ingest alias.
  • vCluster Platform mode. vbilling.vcluster.com/ settings on a cluster's StatefulSet, namespace or VirtualClusterInstance (prometheus-url and the others) are ignored: put them on the Tenant or Project. Clusters are reached only through the Platform proxy.
  • Pausing clusters with their own nodes. A pause first installs a vbilling-paused admission policy inside the cluster: add it to the in-cluster role next to vbilling-suspended (get, update, delete). Without it the pause stays unverified and keeps billing the cluster's own nodes.
  • One replica. The chart refuses replicaCount above 1. A second instance waits on a Lease instead of metering.
  • Removed settings. 35 settings are gone; a value still set only logs a warning. LiteLLM's settings are now LITELLM_URL, LITELLM_API_KEY, LITELLM_TENANT and LITELLM_CLIENT (the old names still work). With LITELLM_TENANT, bind at most one ingest token to that tenant, the LiteLLM's, or vBilling refuses to start. See Removed in v0.3.1.

Behavior that changed:

  • Pause. Capacity stops billing once vBilling has verified the cluster's workloads are gone, with successful reads and no pod able to start; a pause it cannot verify still stops the control plane and keeps billing the cluster's own nodes. Pods get at most 30 seconds of grace. Pauses made by v0.3.0 are verified again before they stop billing.
  • Billing holds. Billing webhooks only raise a hold. A payment lowers it only after vBilling reads Stripe and Metronome again and finds nothing still owed: no subscription past due or unpaid, no open invoice past due or failed, no Metronome notification in alarm that a rule maps above warning. A Metronome customer that funds several tenants releases them all. PUT /api/v1/billing-states without hold now sets an operator hold, which no webhook lifts; pass "hold": "billing" for a hold a payment may lift. Events apply in the order they happened, and a retried older event is ignored. An operator still sets or clears any hold with PUT /api/v1/billing-states.
  • Suspension inside clusters. Only kube-system is exempt; the enforcement-exempt namespace label no longer works.
  • Ingest. SKU, dimension, region, project and resource values with markup or control characters are refused, and so are dimensions named like an event's own properties (value, sku, region and the others). X-VBilling-Client must be a short plain name, with at most 16 names per tenant-bound token and 64 for the shared token. Per-token rate limits apply, and a records push that would write more than 64 MiB gets 413. A source's 101st new, unpriced SKU for a tenant in a UTC day is billed as sku-limit-exceeded and fails its health source. LiteLLM requests bill to the key's team only; keys without a team are refused. Events and records sent with a tenant-bound token get IDs of that token's own, so two tokens bound to one tenant never take each other's. Retries of records stored by v0.3.0 are recognized for 48 hours from their original arrival, including across an upgrade. The compact ingest index migrates automatically; older binaries cannot read a rewritten index, so preserve a consistent backup and do not downgrade in place.
  • Clusters with their own nodes. Labels and taints written inside a cluster never lower its bill: vbilling.vcluster.com/billable=false and vCluster's placeholder label are ignored on its own nodes, downtime comes only from the Ready condition, a node's GPU count never drops, and its SKU and capacity type stay as first seen (for existing nodes, the first read after the upgrade), except attributes the node showed empty during its first 10 minutes. This history is kept by cluster and node name, so give a machine that replaces another a new node name. Usage mode reads namespaces inside clusters to honor vbilling.vcluster.com/exclude=true: add namespaces (get, list) to the reader role.
  • Namespace syncing. With sync.toHost.namespaces, what a cluster syncs to other namespaces (pods, volumes, load balancers and their Prometheus series) is metered, paused and suspended. It belongs to the cluster that vCluster's namespace labels (vcluster.loft.sh/vcluster-name, vcluster.loft.sh/vcluster-namespace) name; in a namespace without them, only to a cluster whose name is unique, and otherwise synced-namespaces/<cluster> fails. Counters there bill from the upgrade on.
  • Offboarding. The hour without usage counts from when a tenant's last usage arrived, not from the window it covered, so usage that arrives as hourly totals never offboards a tenant between posts.
  • Held usage. PRICE_CHECK=hold releases unpriced usage after 23 hours, before its invoice period can be final. With Metronome, the default warn also holds usage no billable metric counts yet, for up to 23 hours.
  • Counters. A Prometheus series that appears with history (for example, a ServiceMonitor added for a running engine) is billed from its first sample, unless its start time shows it is new.
  • Volume health. The ledger volume, and the archive volume when set, report in source health and fail at 85% full: a full ledger volume stops every commit.
  • Node-hour events. They carry vcpus, memory_gib, gpu_count and public_ip, so their IDs differ from v0.3.0's. Committed windows are never sent again, so nothing is billed twice.

Upgrading from v0.2

Run helm upgrade with the v0.3.3 chart and keep the PVC. A ledger written by v0.2 opens, verifies and keeps its destination cursors and ingest dedupe, so nothing is billed twice or skipped. The chart adds read access to node Leases, and in enforce mode, delete access to pods.

  • CPU and memory now bill requests. CPU_MEMORY_BASIS (metering.cpuMemoryBasis) defaults to requests, which is exact. v0.2 defaulted to usage, a metrics-server reading per window. Set metering.cpuMemoryBasis=usage to keep v0.2 quantities. Pods that request nothing bill no CPU or memory under requests; vbilling_pods_without_requests counts them.
  • Egress is a counter. Without prometheus.egressQuery, egress is read from container_network_transmit_bytes_total as an exact counter, not with increase() at the window end. Expect small differences from v0.2's estimate. A custom egressQuery stays an estimate.
  • Prometheus metrics. query: metrics are marked as estimates. Use counter: for an exact counter (see Usage Sources). The sku key is now skuLabel; sku still works and logs a warning.
  • Custom metrics. metering.customMetrics takes a YAML list. The v0.2 string form still works.
  • Ingest without IDs. POST /api/v1/events now rejects two ID-less events in one request that derive the same ID (v0.2 kept only the first). Send per-request usage to POST /api/v1/records instead.
  • Billing platforms. Existing Stripe subscriptions and Metronome contracts are found and kept, not created again.
