Getting Started

Install vBilling in your control plane cluster, connect the billing platform you run, and see the first usage arrive. vBilling meters; your billing platform prices, invoices and collects.

Prerequisites

  • A control plane cluster with at least one tenant cluster. vBilling meters every tenancy model: tenant clusters with their own nodes (vCluster Private Nodes, Auto Nodes, Standalone), dedicated nodes and shared nodes.
  • kubectl and Helm 3
  • metrics-server in the control plane cluster, for CPU and memory usage
  • An account on your billing platform (a Stripe sandbox, a Metronome account), or Docker to run Lago locally
i
vBilling finds tenant clusters by their StatefulSets or Deployments (label app=vcluster), and through the vCluster Platform API when it is available. No cluster yet? Run everything on a laptop with vind and Lago, or follow the GKE example with real GPUs.

1Choose a billing platform

vBilling is the pipe, not the billing engine: prices, invoices and payments stay in the billing platform you choose. Each platform has a billing adapter in vBilling, and several adapters can run at once (for example adapters='{stripe,webhook}'), each with its own delivery cursor.

Billing adapterChoose it for
StripePay-as-you-go prices per metric and SKU, with Stripe invoices, payments and tax
MetronomePricing on many dimensions, commits, credits and rate cards, optionally with Stripe collecting payment
LagoOpen source, self-hosted billing that also runs on a laptop with Docker Compose
Custom Billing AdapterYour own rating engine or data platform, through signed CloudEvents webhooks or an adapter written in Go

2Install vBilling

The chart defaults to the published image ghcr.io/vclusterlabs-experiments/vbilling:v0.2.0 (linux/amd64 and linux/arm64). Keep billing keys in Secrets, never in --set flags or values files. From a clone of the repository, with Stripe as the example:

git clone https://github.com/vClusterLabs-Experiments/vbilling.git && cd vbilling kubectl create namespace vbilling-system kubectl -n vbilling-system create secret generic vbilling-stripe --from-file=api-key=./stripe-test-key helm upgrade --install vbilling deploy/helm/vbilling -n vbilling-system \ --set adapters='{stripe}' \ --set stripe.existingSecret=vbilling-stripe \ --set region=us-east-1

The other adapters take the same shape:

AdapterSecret keysHelm values
stripeapi-key, webhook-secretstripe.existingSecret
metronomeapi-token, webhook-secretmetronome.existingSecret, metronome.rateCard
lagoapi-keylago.existingSecret, lago.apiURL
webhooksecretwebhook.existingSecret, webhook.url
noopNone: logs every event instead of sending it, for a dry run

Run one vBilling per control plane cluster and set region: it is stamped on every event, and every ledger record stays in that cluster.

Run from source (development)

make build ADAPTERS=noop DATA_DIR=./data ./bin/vbilling

Outside a cluster, vBilling uses your current kubeconfig context. With noop, each event is logged ([noop] event tenant=... metric=... qty=...) instead of sent.

3Configure pricing and packaging

vBilling creates the metrics in your billing platform; the prices are yours. Every tenant is on the default plan vcluster-standard unless its tenant cluster carries vbilling.vcluster.com/plan.

  • Stripe: a metered price on each meter you charge for, tagged with the plan for automatic subscriptions. See Prices and subscriptions.
  • Metronome: rate card products on the billable metrics, priced on dimensions such as SKU, region and capacity type. See Pricing on dimensions.
  • Lago: the plan's charges, with charge filters on sku or capacity_type. See Configure pricing.

Every event carries the dimensions to price on, among them sku, region, capacity_type (on-demand, spot, preemptible or reserved), billing_mode and tenant_class. See the Metrics Reference.

4Verify it works

vBilling meters closed windows (60 seconds by default), commits them to its ledger, and delivers them to each adapter.

kubectl -n vbilling-system logs statefulset/vbilling Using in-cluster Kubernetes config [controller] starting (adapters=[stripe], window=1m0s, reconcile=30s, region=us-east-1) API listening on :8080 [controller] window 10:18:00: ... events for 3 tenant cluster(s) (...)
kubectl -n vbilling-system port-forward svc/vbilling 8080 # dashboard: http://localhost:8080/ curl -s localhost:8080/api/v1/status | jq '.destinations' # delivery health per adapter curl -s 'localhost:8080/api/v1/usage?group_by=tenant,sku' | jq # line items from the ledger curl -s localhost:8080/api/v1/reconcile | jq '.results[] | {destination, ok}' # Stripe and Metronome
✓
Once the destinations report deliveries, the usage is in your billing platform: meters and customers in Stripe, customers and usage in Metronome, or customers and subscriptions in Lago. A platform outage never loses usage: the ledger keeps it until the adapter catches up.
