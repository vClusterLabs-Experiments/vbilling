Stripe

Bill clusters with Stripe Billing Meters. vBilling creates the meters and customers, sends every usage window exactly once, keeps subscriptions in step with the prices you tag, and turns Stripe's payment events into billing states for your clusters.

How it works

tenant clusters ──► vBilling ──► ledger (fsynced, hash-chained)
                                   │ stripe cursor
                                   ▼
                          Stripe adapter
                          ├─ Billing Meters   one per metric, one per SKU
                          ├─ Customers        one per tenant, metadata vbilling_tenant_id
                          ├─ Meter events     identifier = event ID, timestamp = window start
                          └─ Subscriptions    optional: prices tagged vbilling_plan

Stripe ──► /webhooks/stripe ──► billing state ──► tenant cluster
invoices, subscriptions,          active, warning,
usage alerts                      delinquent, suspended

vBilling does

Meters, customers and meter events; retries and dead letters; optional subscriptions; reconciliation against Stripe; billing states from Stripe webhooks.

You do in Stripe

Products and prices, invoice and tax settings, payment methods, Smart Retries and dunning emails, and the customer portal.

i
A Stripe meter prices one quantity. To price several dimensions at once (region, SKU and capacity type), or to sell commits and credits, rate usage in Metronome and let Stripe collect payment.

Install in test mode

Start with a sandbox or test-mode key: a secret key (sk_test_...) or a restricted key (rk_test_...). Save it to a file and keep it in a Secret, never in --set flags or values files. From a clone of the repository:

kubectl create namespace vbilling-system kubectl -n vbilling-system create secret generic vbilling-stripe \ --from-file=api-key=./stripe-test-key helm upgrade --install vbilling deploy/helm/vbilling -n vbilling-system \ --set adapters='{stripe}' \ --set stripe.existingSecret=vbilling-stripe \ --set region=us-east-1

vBilling creates one meter per billable metric at startup, and a customer for each tenant as its usage arrives. Check the log and the destination's health:

kubectl -n vbilling-system logs statefulset/vbilling | grep '\[stripe\]' [stripe] created meter vcluster_gpu_hours (mtr_...) [stripe] created customer cus_... for tenant vcluster-team-a-team-a kubectl -n vbilling-system port-forward svc/vbilling 8080 & curl -H "Authorization: Bearer $VBILLING_TOKEN" -s localhost:8080/api/v1/status | jq '.destinations'

For CI, run stripe-mock and set stripe.apiBase to it: every request is validated against Stripe's OpenAPI spec, as in scripts/e2e-kind.sh.

Meters

At startup vBilling creates, or reactivates, one meter per billable metric: sum aggregation, customers mapped by stripe_customer_id, the quantity in value. Informational metrics (vcluster_gpu_utilization, vcluster_gpu_downtime_hours) are never sent to Stripe.

Because a meter cannot price on dimensions, each event goes to a meter for its metric and the original values of every field in splitMetersBy, created on first use. New names have a readable slug followed by a 128-bit digest of the split keys and values, including empty values. Thus org/model, org-model and case differences stay distinct. Names are at most 100 characters. In the examples below, <digest> stands for that suffix: list the actual meters before creating prices.

Upgrade: when available pre-upgrade ledger and archive history identifies one split identity for an existing meter, vBilling persists that identity's route to the existing name and its prices. A legacy name shared by multiple observed identities is not reused; new names need their own prices. Removed history cannot establish earlier collisions, so reconcile historical SKU pricing before upgrading and check GET /api/v1/pricing?destination=stripe afterwards. Existing prices and subscriptions are not rewritten to new meters automatically.

Pricing on more dimensions

Add fields to the split to give them their own meters and prices. Any event field works: sku, region, project, or a dimension such as capacity_type, billing_mode or tenant_class. Suffixes follow the order of the list:

--set stripe.splitMetersBy='{sku,capacity_type}' # vcluster_gpu_hours__nvidia_h100_80gb_hbm3__on_demand__<digest> # vcluster_gpu_hours__nvidia_h100_80gb_hbm3__spot__<digest>

Every field multiplies the meters and prices you manage. Settle the split before you go live: a new split sends new usage to new meters, and earlier usage stays on the old ones.

Customers

Each vBilling tenant gets one Stripe customer. By default a tenant is one cluster, with the ID vcluster-<namespace>-<name>; the vbilling.vcluster.com/tenant key groups several clusters under one customer, and TENANT_SOURCE=project gives each vCluster Platform project one. vBilling finds the customer in this order:

  1. A customer ID pinned with vbilling.vcluster.com/stripe-customer-id.
  2. The customer vBilling recorded earlier in state-stripe.json on its volume.
  3. A Stripe customer whose metadata[vbilling_tenant_id] is exactly the tenant ID. vBilling uses customer search, and lists customers instead (by email first) for accounts without search.
  4. A new customer, created with an idempotency key so that a retry never creates a second one.

Customer details come from labels or annotations on the cluster's StatefulSet, its namespace, or its vCluster Platform VirtualClusterInstance, and are updated when they change:

kubectl annotate namespace team-a \ vbilling.vcluster.com/tenant=acme-ai \ vbilling.vcluster.com/display-name="Acme AI" \ vbilling.vcluster.com/email=billing@acme-ai.example \ vbilling.vcluster.com/plan=vcluster-standard # reuse a customer that already exists in Stripe kubectl annotate namespace team-a vbilling.vcluster.com/stripe-customer-id=cus_EXISTING
Customer fieldValue
name, emailThe display-name (or the tenant ID) and email keys
metadata[vbilling_tenant_id]The tenant ID. vBilling only uses a customer whose value matches exactly.
metadata[vbilling_plan]The tenant's plan
metadata[vbilling_region], [vbilling_project], [vbilling_tenant_class]The region, vCluster Platform project and tenant class

vBilling never deletes customers. Do not delete them in Stripe either: to move a tenant to another customer, pin it.

Prices and subscriptions

What a GPU-hour costs is your decision. vBilling creates prices only from a price card you give it, and never changes or archives one. Without a price card, create a recurring, metered price on each meter you charge for. Quantities are hours (GPU-hours, node-hours, GiB-hours), so unit prices are per hour. Fractional GPUs are already counted in GPU-equivalents (a 1g.5gb slice of an A100 is 1/7), so one per-GPU-hour price fits every variant of a SKU, or the slices can carry a premium.

# Copy the intended meter's ID from the meter listing above. METER=mtr_REPLACE_WITH_ACTUAL_ID curl -s https://api.stripe.com/v1/prices -u "$STRIPE_KEY:" \ -d currency=usd -d unit_amount_decimal=250 \ -d "recurring[interval]=month" -d "recurring[usage_type]=metered" \ -d "recurring[meter]=$METER" \ -d "product_data[name]=H100 GPU-hours" \ -d "metadata[vbilling_plan]=vcluster-standard"

unit_amount_decimal is in cents: 250 is $2.50 per GPU-hour.

Automatic subscriptions

Without autoSubscribe, usage accrues on the meters and is invoiced once you subscribe the customer to prices yourself. With --set stripe.autoSubscribe=true, vBilling subscribes every tenant to the prices of its plan:

  • The plan is the tenant's vbilling.vcluster.com/plan, or billing.defaultPlanCode (vcluster-standard).
  • A plan's prices are the active metered prices on vBilling's meters tagged metadata[vbilling_plan]=<plan>, in the tenant's currency (vbilling.vcluster.com/currency, or billing.currency).
  • A plan holds up to 20 prices, Stripe's limit per subscription. A tenant on a larger plan is logged as rejected and not subscribed, and its usage keeps reaching its meters.
  • A new subscription starts at the tenant's first usage being delivered, or the hour the tenant was created if that is earlier today (backdate_start_date). Stripe invoices a meter only from the subscription's start: usage dated earlier is accepted and shows in meter summaries, but never reaches an invoice (checked in a Stripe sandbox). The start is never a whole billing period back, because Stripe would then close the first period at once and invoice none of it. Usage dated before a subscription's start is dead-lettered as dated before the tenant's Stripe subscription started instead of being sent.
  • An existing vBilling subscription gets missing prices added. Prices are never removed from it.
  • New prices reach new tenants within five minutes. Existing tenants get a new price with their next usage once the price check (below) finds it, and otherwise when vBilling restarts or their labels and annotations change.

Plans let each tenant pay for what it buys. A tenant that rents whole GPU machines (dedicated or private nodes) can be on a plan with node-hour prices only, and a tenant that pays per GPU-hour on a plan with GPU-hour prices. Stripe only invoices a customer for the meters its subscription has prices on.

Price card

Instead of creating each plan's prices by hand, describe them in stripe.priceCard (STRIPE_PRICE_CARD, a YAML file). At startup vBilling creates every missing meter and price, tagged with the plan (metadata[vbilling_plan]) so autoSubscribe picks them up. It never changes or archives a price: Stripe prices cannot be edited, so to change one, create the new price and archive the old one in Stripe, and vBilling logs any amount that differs from the card.

stripe: autoSubscribe: true priceCard: currency: usd # default: billing.currency interval: month # day, week, month or year plans: dedicated-a100: vcluster_gpu_hours: sku: {NVIDIA-A100-SXM4-40GB: "2.20"} # dollars per GPU-hour names: {NVIDIA-A100-SXM4-40GB: A100 40GB GPU-hour} vcluster_instance_hours: {amount: "0.10", name: Cluster control plane hour} serverless: inference_input_tokens: {per: 1000000, sku: {qwen2.5-7b-instruct: "0.20"}} inference_cached_input_tokens: {per: 1000000, sku: {qwen2.5-7b-instruct: "0.05"}} inference_output_tokens: {per: 1000000, sku: {qwen2.5-7b-instruct: "0.60"}}
  • Amounts are in the currency's main unit (dollars, not cents). per divides them: per: 1000000 with "0.60" is $0.60 per million tokens, created as 0.00006 cents per token. Stripe takes at most 12 decimal places of a cent; a card that needs more is refused at startup.
  • amount prices usage without a SKU (control plane hours, CPU, memory); sku prices each SKU's own meter (see splitMetersBy). A price on the base meter of a metric whose usage has SKUs receives nothing.
  • name and names become the product names on the invoice; the default is the meter's name.

Checked against a Stripe sandbox: a card of three prices, including a per-million token price, created exactly those amounts, and applying it again created nothing.

Invoices

Stripe sums each meter over the billing period and adds a line per price to the subscription's invoice; payment collection, tax, retries and dunning stay in Stripe. To see what a tenant owes so far, open the customer's upcoming invoice in the Dashboard, or preview it:

curl -s https://api.stripe.com/v1/invoices/create_preview -u "$STRIPE_KEY:" -d customer=cus_... \ | jq '.lines.data[] | {description, amount}'

Stripe processes meter events asynchronously, so new usage can take a few minutes to show up.

Price coverage

Stripe bills nothing for a meter without a price, and accepts its events without an error. vBilling checks, read-only, that every billable metric and every series seen in the ledger in the last 24 hours has a price. It never creates or changes a price. A series is one meter: with the default STRIPE_SPLIT_METERS_BY=sku, a metric and SKU, and with more split keys, each combination of their values.

  • priced: the series' meter exists, is active, and has an active, recurring, metered price that is not 0. With autoSubscribe, the price must also carry metadata[vbilling_plan] of the tenant's plan, or subscriptions on that plan do not include it.
  • unpriced: no meter yet, a deactivated meter, no active metered price, or (with autoSubscribe) no price tagged with the plan. The hint names the meter, for example create a metered price on meter "vcluster_gpu_hours__nvidia_b200" (mtr_...).
  • zero: every price on the meter is 0 (unit_amount_decimal 0, or tiers whose unit and flat amounts are all 0). Information, not a gap.

Without autoSubscribe, a priced series still needs its customers subscribed to the price: vBilling cannot see that, and the detail says so. When a series appears, vBilling creates its meter right away (never a price), so Finance can price it before its first event is delivered. With autoSubscribe, a series that becomes priced makes vBilling add the new price to existing subscriptions with each tenant's next usage.

Checks run at startup, every 10 minutes, within seconds of a new SKU and on POST /api/v1/pricing/check. Read gaps from GET /api/v1/pricing?destination=stripe&status=unpriced, GET /api/v1/sources?kind=pricing or vbilling_unpriced_series{destination="stripe"}. With PRICE_CHECK=hold, events of an unpriced meter wait in vBilling until the price exists. Usage held for 23 hours is released without a price and its source turns failing. Stripe finalizes an invoice one hour after its period by default and does not invoice usage that arrives later, so usage from the last day of a period can miss its invoice: price new SKUs promptly. The check reads GET /v1/billing/meters and GET /v1/prices?active=true&type=recurring&expand[]=data.tiers; the adapter's tests run both, and the meter creation, against stripe-mock.

Delivery and idempotency

Every closed window is committed to the ledger first. The Stripe destination sends it from its own cursor, so a Stripe outage never loses usage and never holds up other destinations.

ConcernWhat vBilling does
DuplicatesThe meter event identifier is the vBilling event ID: a hash of identity (tenant, metric, window, dimensions, including the persistent metering source), never quantity. Confirmed deliveries have durable receipts until the outbox result is durable. Retries of uncertain attempts are bounded to 23 hours.
Event timeThe meter event timestamp is the window start, so late deliveries and backfills land in the period they belong to.
PrecisionQuantities are plain decimals with at most 15 significant digits and 9 decimals.
RateA token bucket at maxRPS, and four workers partitioned by customer and meter, so a customer's meter never gets concurrent calls.
RetriesAuthentication errors (401, 403), 404, conflicts (409), rate limits (429), 5xx and network errors retry with backoff within the safe retry horizon. Stripe's Stripe-Should-Retry header wins when present. An unresolved attempt older than 23 hours is parked for reconciliation.
Dead lettersEvents Stripe rejects as invalid (400, 413, 422) are isolated one by one and parked with the reason; the rest of the batch goes through.
!
Stripe guarantees identifier uniqueness for at least 24 hours and accepts events up to 35 days old. These are different limits. vBilling persists an attempt before sending and a confirmation before acknowledging it. After 23 hours an uncertain outcome becomes a dead letter instead of a blind resend. Cursor rewinds containing usage older than 23 hours are refused, including for a newly added Stripe destination. Older recovery requires reconciliation; acceptance by the ingest API does not prove inclusion on a finalized invoice.

For an ambiguous delivery, inspect GET /api/v1/destinations/stripe/delivery/<event-id> and reconcile with Stripe's recorded usage and invoices. With the operator API token, PUT that URL with {"outcome":"delivered","reason":"reconciliation evidence"} to confirm acceptance, or "not_delivered" only after establishing the event was not accepted. Then replay the dead letter. A delivered outcome removes it without another meter-event POST; a not-delivered outcome permits a fresh attempt. Preserve destination state with the ledger, and never delete receipts to force a retry. Pre-upgrade unacknowledged events older than the safe horizon are also parked conservatively because older binaries left no durable delivery receipt.

After fixing what caused a rejection (often by upgrading vBilling), replay the parked events. Events Stripe still rejects stay parked (still_rejected). With API_TOKEN set, add -H "Authorization: Bearer $API_TOKEN".

curl -H "Authorization: Bearer $VBILLING_TOKEN" -s localhost:8080/api/v1/destinations/stripe/dead-letters | jq curl -H "Authorization: Bearer $VBILLING_TOKEN" -s -X POST localhost:8080/api/v1/destinations/stripe/dead-letters/replay {"replayed":12}

Reconciliation

GET /api/v1/reconcile recomputes each tenant's usage per metric from the ledger, subtracts what was dead-lettered, and compares it with Stripe's meter event summaries for the tenant's customer, summed over every split meter of the metric. A row matches within 0.1%. The default range is the previous full UTC day; from and to take RFC 3339 times or dates. tenant and metric narrow it down; sku, region, project and cluster pick the tenants and metrics with such usage, and each row still compares all of that tenant's usage of the metric, because Stripe reports totals per customer.

curl -H "Authorization: Bearer $VBILLING_TOKEN" -s 'localhost:8080/api/v1/reconcile?destination=stripe&from=2026-10-05&to=2026-10-06' | jq { "from": "2026-10-05T00:00:00Z", "to": "2026-10-06T00:00:00Z", "results": [{ "destination": "stripe", "ok": true, "rows": [ {"tenant": "acme-ai", "metric": "vcluster_gpu_hours", "ledger": 2.75, "dead_lettered": 0, "expected": 2.75, "recorded": 2.75, "difference": 0, "match": true} ] }] }

Stripe's summaries are aligned to minutes and trail ingestion by a few minutes, so reconcile closed periods rather than the current hour. Run it daily and alert when ok is false.

Webhooks and billing states

Stripe's payment events tell vBilling when to look at what a tenant owes. An event that reports a problem only raises the tenant's billing hold. A positive one (an invoice paid, a subscription back to active) never lowers it by itself: vBilling reads the customer's standing from Stripe again, and clears the hold only when nothing is owed:

  • no subscription of the customer is past_due, unpaid or incomplete, whoever created it;
  • no open invoice is past its due date, or has a failed payment (attempt_count above zero);
  • no invoice is uncollectible.

vBilling reads every subscription and every open and uncollectible invoice of the customer, page by page. Paying a small invoice while an older one is still open lifts nothing, and neither does a subscription that Stripe marks active again once its latest invoice is paid. If Stripe cannot be read, the webhook gets a 500 and Stripe retries it. With Metronome configured too, Metronome is read as well, for the customer that holds the tenant ID as an alias: a Stripe payment never resumes a tenant whose prepaid wallet is still empty. Add a webhook endpoint in Stripe for https://<your-host>/webhooks/stripe with the events below, then add its signing secret to the Secret and restart vBilling:

Stripe eventBilling state
invoice.payment_faileddelinquent
invoice.paid, invoice.payment_succeededactive, once Stripe shows nothing owed
customer.subscription.created, .updated, .resumedBy subscription status: past_due is delinquent; unpaid, canceled and incomplete_expired are suspended; active and trialing are active, once Stripe shows nothing owed
customer.subscription.deletedsuspended
billing.alert.triggered (a usage alert on a meter)warning
kubectl -n vbilling-system create secret generic vbilling-stripe \ --from-file=api-key=./stripe-test-key --from-file=webhook-secret=./stripe-webhook-secret \ --dry-run=client -o yaml | kubectl apply -f - kubectl -n vbilling-system rollout restart statefulset/vbilling

vBilling verifies the Stripe-Signature header (HMAC-SHA256 over the timestamp and the body, with the five-minute tolerance of Stripe's libraries) and applies each event once. It answers 400 to a bad signature, 200 with "applied": false for events it ignores, repeats, or customers it does not manage, and 500 when it could not record the state, so that Stripe retries.

Only the webhook path needs to be reachable from Stripe. Keep /api on the internal Service, for example with an Ingress for that one path:

apiVersion: networking.k8s.io/v1 kind: Ingress metadata: name: vbilling-webhooks namespace: vbilling-system spec: ingressClassName: nginx tls: [{hosts: [billing-hooks.example.com], secretName: billing-hooks-tls}] rules: - host: billing-hooks.example.com http: paths: - path: /webhooks/stripe pathType: Exact backend: service: {name: vbilling, port: {number: 8080}}

To try it locally, let the Stripe CLI forward events. It prints a signing secret for the session to use as webhook-secret:

stripe listen --forward-to localhost:8080/webhooks/stripe

Events fired with stripe trigger belong to new test customers that vBilling does not manage, so they come back with "applied": false. To see a state change, act on one of vBilling's customers, for example by paying its invoice with one of Stripe's declining test cards.

What a billing state does

Stripe's webhooks set billing states once webhook-secret is set. States are recorded in every mode and shown by GET /api/v1/billing-states, the metrics and the dashboard. enforcement.mode decides what else happens:

ModeEffect
observe (default)Record the state only.
annotateAlso annotate the cluster, label its namespace vbilling.vcluster.com/billing-state, and emit a Kubernetes event.
enforceAlso label suspended namespaces vbilling.vcluster.com/suspended=true. With enforcement.admissionPolicy.enabled=true (Kubernetes 1.30+), new pods are denied there while running workloads keep running. A payment lifts it once nothing is owed.
The admission policy acts in the control plane cluster, so it holds clusters on shared or dedicated nodes. Clusters with their own nodes (Private Nodes, Auto Nodes, Standalone) run their pods only inside the cluster: with enforcement.inCluster=true, vBilling installs the same policy inside each of them through the cluster's own API (see Billing-state enforcement inside the cluster), or act on their billing state with your own automation.

In enforce mode with enforcement.gateway.litellm=true, a suspended or paused tenant's LiteLLM teams are also blocked, which is how a tenant that only buys tokens is stopped. See Stopping a suspended tenant at the gateway.

Override a mapping with enforcement.rules (ENFORCEMENT_RULES), for example invoice.payment_failed=suspended to suspend on the first failed payment, or billing.alert.triggered=suspended to turn a Stripe usage alert into a hard cap, which a payment lifts once nothing is owed. Operators can also set a state by hand. Without hold, a PUT sets the operator hold, which no webhook touches; name the billing hold to clear what Stripe's webhooks raised, for a payment made outside Stripe:

curl -H "Authorization: Bearer $VBILLING_TOKEN" -s -X PUT localhost:8080/api/v1/billing-states/acme-ai -d '{"state": "active", "hold": "billing", "reason": "paid by bank transfer"}'

Grace periods. With enforcement.escalations (ENFORCEMENT_ESCALATIONS), the billing hold rises on its own: a failed payment makes the tenant delinquent, and with {from: delinquent, after: 72h, to: suspended} and {from: suspended, after: 7d, to: paused} it is suspended 72 hours later and paused 7 days after that. A payment that leaves nothing owed lifts the hold at any point. GET /api/v1/billing-states shows when the next step is due (escalation.at). See Grace periods.

Offboarding

When a tenant has had no clusters and no usage for an hour, and its last usage is delivered, vBilling offboards it. The Stripe customer and its subscription stay, so final usage is still invoiced. With stripe.cancelOnRemove=true, the subscription is set to cancel at the end of the period.

Troubleshooting

The invoice shows no usage

  • The price is on a meter that receives nothing, usually the base meter instead of the SKU meter. List the meters and compare with the event names in the log.
  • The tenant is not subscribed. With autoSubscribe, the log says [stripe] no active metered prices tagged vbilling_plan=<plan> in <currency>; tenant <id> not subscribed: check that the price is active and metered, carries the plan in its metadata, and is in the tenant's currency.
  • The usage is still being processed: Stripe aggregates meter events asynchronously.
  • The meter has no price: GET /api/v1/pricing?destination=stripe&status=unpriced lists every meter vBilling sends usage to without one, with the price to create.

Deliveries stop with 401 or 403

The key is wrong or revoked, or a restricted key lacks a permission. Nothing is lost: events wait in the ledger and are retried. Fix the Secret and restart vBilling; /api/v1/status shows each destination's failures and its oldest pending event.

Events dead-lettered as dated before the subscription started

The tenant's subscription starts after that usage, so Stripe would never invoice it: the usage is older than one billing period when the subscription was created, or a subscription was created by hand (or by an earlier vBilling) after the usage. Reconciliation reports it under dead_lettered. Bill it with a one-off invoice item if needed.

Events dead-lettered as older than 35 days

Stripe no longer accepts them. They stay in the ledger, and reconciliation reports them under dead_lettered. Bill them with a one-off invoice item if needed.

Webhooks fail with 400 or 404

400: the signing secret does not match the endpoint (every endpoint, and every stripe listen session, has its own), the clock is more than five minutes off, or a proxy rewrote the body. 404: webhook-secret is not set.

"customer search unavailable"
