Security

vBilling bills tenants for the clusters they use, so it treats tenants as untrusted. This page says who controls what, what each control in vBilling guarantees, and what operators must do.

Threat model

vBilling runs in the control plane cluster. Operators and tenants control different things.

Tenants control

  • their clusters' vcluster.yaml, and with it the labels and annotations of each cluster's StatefulSet and the targets of its exportKubeConfig;
  • everything inside their own clusters, where they are cluster admin: pods, Services and the HTTP answers those Services return, and labels on their own nodes;
  • the content of the events and records they send with ingest tokens bound to them;
  • their identities in AI gateways.

Operators control

vBilling's configuration, the control plane cluster, vCluster Platform Tenants and Projects, and the billing platform accounts.

A tenant must never be able to

  • lower or stop its own bill;
  • bill another tenant;
  • change another tenant's state;
  • read other tenants' data;
  • obtain vBilling or vCluster Platform credentials;
  • degrade vBilling for other tenants.

What each control guarantees

API token

  • Every endpoint except /healthz and /readyz needs the API token: usage and exports, billing states, destinations and cursors, reconciliation, ledger verification, /metrics, and every data call of the dashboard. Stripe and Metronome webhooks are checked by their signatures instead, and ingest by ingest tokens.
  • The API is never open. Without API_TOKEN, vBilling generates a random token at startup, writes it to DATA_DIR/api-token with mode 0600, reuses that file on later starts and logs the file's path, never the token.
  • The Helm chart puts a random token in its Secret when neither api.token nor api.existingSecret is set, and keeps it across upgrades. The ServiceMonitor sends it to /metrics. Tools that render the chart without access to the cluster (helm template) cannot keep a generated token: set api.token or api.existingSecret with them.
  • The dashboard's page loads without the token and asks for it. The page shows every value as text, never as HTML, and is served with a Content-Security-Policy that allows only its own script and style, by their hash.
  • vBilling refuses to start when a tenant's ingest token equals the API token or the shared ingest token, when INGEST_TOKENS gives one token to two tenants, and when INGEST_TOKEN is the API token, including the one vBilling generated into DATA_DIR/api-token (v0.3.0 gave gateways that token by default).
  • CSV exports (GET /api/v1/usage and GET /api/v1/events with format=csv) put a ' before every cell that starts with =, +, - or @, so a spreadsheet shows tenants, IDs, SKUs and dimensions as text and never runs them as formulas.
Read the token the chart generated
kubectl -n vbilling-system get secret vbilling -o jsonpath='{.data.api-token}' | base64 -d

Ingest tokens

  • INGEST_TOKEN is the shared ingest token. It is for the operator's gateways and emitters, which report usage for many tenants, and it is never the API token: gateways keep it in their configuration, so whoever can read that configuration can send usage, but cannot change billing states or read usage. Without it, vBilling generates one into DATA_DIR/ingest-token (mode 0600), and the chart generates one into its Secret (key ingest-token) and keeps it across upgrades. Ingest refuses the API token with 401. Never hand the shared ingest token to a tenant.
  • A token in INGEST_TOKENS is bound to one tenant. Everything sent with it is billed to that tenant, whatever the payload says. It can ingest and nothing else. Give each tenant's own gateway its own token. Each token has its own record IDs and its own count of new SKUs, so what a tenant sends with its own token never replaces or uses up what the operator's gateway sends with another token bound to the same tenant.
  • X-VBilling-Client names the emitter. It must be 1 to 64 letters, digits, dots, dashes or underscores, starting with a letter or digit; anything else gets 400. Each tenant-bound token may use 16 client names while vBilling runs, the shared token 64, and a name gets metric series and health sources only once a request under it stored usage. Request headers are limited to 64 KB.
  • SKUs, regions, projects, resource IDs and dimension values sent to POST /api/v1/events and POST /api/v1/records must not contain control characters or any of < > " ' ` &, and must be at most 256 bytes. An event or record carries at most 32 dimensions, and no dimension may take the name of a property of the usage itself (value, unit, sku, region, project, resource_id, source, window_start, window_end, schema_version, accuracy, estimate), which billing platforms receive next to the dimensions, nor metering_source, which vBilling sets itself on every event. An event's unit, its string properties, and with a tenant-bound token its own id (kept as client_event_id) are checked the same way. An event carries at most 32 properties, each a string, a number or a boolean, named like a dimension key and not after a property of the usage itself or client_event_id. A record carries at most 64 usage keys. Events and records that break this are refused, and a request with nothing valid gets 400; the answer lists the first 100 refusals and counts all of them in rejected_count. Values vBilling reads itself (Prometheus labels, gateway logs it pulls, labels of nodes) are made safe instead, so their usage is still billed.
  • A record's request ID longer than 256 bytes is stored as sha256: and its SHA-256 in hex, never refused, since clients can choose some gateways' request IDs (LiteLLM's x-litellm-call-id). Pushed and pulled copies of the request get the same ID. An ID that starts with sha256: is hashed too, so no request can take the ID a long one is stored under.
  • A record without a time is dated when it arrives. Only the arrival of a stored record is remembered (for an hour, so a retry keeps it), so refused records leave nothing in memory.
  • The built-in litellm format bills a request to its virtual key's team only. Fields the client sends, such as end_user, never decide who pays. Give every virtual key a team: a request whose key has none is refused.

kubectl -n vbilling-system get secret vbilling -o jsonpath='{.data.ingest-token}' | base64 -d

Event ID namespaces

Billing platforms deduplicate on event IDs and keep the first event with an ID. vBilling gives each source its own namespace, so an event sent through ingest can never take the ID of usage vBilling measured:

EventsID
Measured by vBilling: the collector, Prometheus, the records aggregator, fills after an outage of a cluster's APIDerived from the usage's identity, prefix vb1_
Ingested without an idDerived from the identity, the ingest source, the bound tenant and token, and the client, prefix ie1_
Ingested with an id, tenant-bound tokenThe id scoped to the token, its tenant and the client, prefix te1_
Ingested with an id, shared ingest tokenThe id as sent. It may not start with vb1_, te1_ or ie1_.

A retry gets the same ID, so it is counted once. Per-request records get IDs scoped to their client and tenant, and are summed into vBilling's own events. Records sent with a tenant-bound token get IDs of that token's own, derived from a hash of the token, never the token, so a tenant's copy of a request never takes the ID of the gateway's, even when both send with tokens bound to the same tenant. A pull pinned to a tenant (LITELLM_TENANT, or tenant: in RECORDS_PULL_FILE) stores its rows under the IDs of that tenant's bound token, so a request the pulled gateway pushed with that token and the pull reads back counts once. vBilling refuses to start when the pinned tenant has more than one token in INGEST_TOKENS, because the pin cannot tell which one the gateway uses. The token bound to a pinned tenant is the gateway's: never give it to the tenant. Rows that an earlier version stored under its IDs are still recognized: a pull checks those IDs too, and so does a push in the hour after a start.

Quotas

Ingest limits are constants, far above what real emitters need. They stop one token or one tenant from taking vBilling from the others.

LimitValueWhy
Requests, shared ingest token5,000 per second, bursts of 10,000The operator's gateways post for every tenant.

Request body10 MB and 5,000 events per POST /api/v1/events, 16 MB per POST /api/v1/recordsBodies are read into memory.
Request headers64 KBNo header is needed beyond a token and a few short names.

Usage keys per record64Each usage key of a record is a usage row of its own.
Refusals listed per answer100, with rejected_count counting allA request of refused records cannot make a large answer.
ConnectionsHeaders within 10 seconds, the whole request within 2 minutes; the answer within 2 minutes, 30 for usage, reconciliation, ledger verification, price checks, dead-letter replays and cross-checks; idle connections closed after 2 minutesA client that sends or reads slowly cannot hold connections. The raw export (GET /api/v1/events) streams for as long as the client keeps reading: its deadline moves 2 minutes ahead with every row.
New SKUs per tenant100 per UTC day for each source: the shared ingest token, each tenant-bound token, each pullEach new SKU can create a meter in the billing platform. A SKU the tenant used in the last two days, or one a billing platform prices, is never new, and a tenant's own token never uses up what the operator's gateways report for it, with the shared token or a token of their own. Usage past the cap is billed under SKU sku-limit-exceeded, never dropped, and the tenant's source records/<tenant>/sku-limit turns failing.

Over a request rate, vBilling answers 429 with Retry-After. The day's count of new SKUs is kept in memory; after a restart, the SKUs of the ledger's last two days are still known. The safeguard that checks every window for nodes billed more than they exist reads only usage vBilling measured itself, so ingested windows (up to 34 days long, of any alignment) never widen what it reads, and names that emitters report never raise findings.

Redirects

A tenant controls what its cluster's API, its Services and its own Prometheus answer. vBilling never follows a redirect from them, from the vCluster Platform API or proxy, or from a URL a cluster's settings name: the redirect comes back as an error, so no credential is sent to a host the answer names. Pulls of a gateway's own request log (RECORDS_PULL_FILE) follow redirects, but send their headers only to the origin of the configured URL.

Platform mode

With TENANT_SOURCE=platform:

  • Who pays, and every vbilling.vcluster.com/ setting, come from the vCluster Platform Tenant, else the Project, and from the operator's configuration. Settings on a cluster's workload, namespace or VirtualClusterInstance are ignored, including prometheus-url, prometheus-matchers and prometheus-source. Put those on the Tenant or Project.
  • Clusters are reached only through the Platform proxy, with the Platform access key. A vbilling-kubeconfig Secret in a cluster's namespace is not read, because the cluster's vcluster.yaml can write one that points anywhere. vBilling does not reach the API of a cluster the Platform does not know.

With TENANT_SOURCE=cluster or project, settings on the workload and namespace apply, and so does the vbilling-kubeconfig Secret. Use those modes only when operators write every vcluster.yaml.

Clusters with their own nodes

Inside a cluster with its own nodes the tenant is cluster-admin, so every Node object, label, taint and status there is theirs to write. vBilling does not let what is written there lower the bill:

  • A node counts as the control plane cluster's own only when a control plane cluster node has the same name and the same machine identity, or when the cluster's synced pods run on it. Labels such as vbilling.vcluster.com/billable=false or vCluster's placeholder label are ignored on the cluster's own nodes.
  • Downtime comes only from a node's Ready condition, never from taints.
  • A node's history is kept by cluster and node name, so deleting and recreating the Node object changes nothing. Its GPU count never drops while the node exists, and its SKU, capacity type and GPU model stay as vBilling first saw them; attributes the node showed empty are filled only during its first 10 minutes. A change shows as diverged in source health.
  • A pause stops billing only after a verified drain (see Pausing a tenant).

What vBilling cannot see: a tenant with root on its own node can mark it not Ready while workloads keep running, or set labels before vBilling first sees the node or during its first 10 minutes. For untrusted tenants, bill these nodes from your machine inventory (for example vMetal or Auto Nodes) through the ingest API, and power paused nodes off. Both are planned with vMetal: billing from its inventory (#18) and powering paused nodes off (#16).

What operators must do

  1. Keep the dashboard and the API on an operator network. The chart's Service is ClusterIP; do not expose it to tenants' networks or workloads. If a tenant's gateway must reach vBilling, expose only POST /api/v1/events and POST /api/v1/records to it, and give it a tenant-bound token. Never give a tenant the API token or the shared ingest token.
  2. Use TENANT_SOURCE=platform when tenants write their own vcluster.yaml. In the other modes, per-cluster settings and vbilling-kubeconfig Secrets decide how a cluster is metered, and whoever writes vcluster.yaml writes them.
  3. Run one replica. Each replica keeps its own ledger, billing state and quotas, so replicas would split usage and state between them. The chart's default replicaCount is 1.
  4. Keep DATA_DIR on a persistent volume. It holds the ledger, and the generated API and ingest tokens when API_TOKEN or INGEST_TOKEN is not set.
  5. Give gateways the ingest token, never the API token. Before v0.3.1 the shared ingest token defaulted to the API token; gateways that still send it get 401 and must switch to the ingest token.
  6. Watch the ledger's disk. Rates and body sizes bound each token, not the total a tenant-bound token can send over time. Alert on vbilling_ledger_bytes against the volume's size.
