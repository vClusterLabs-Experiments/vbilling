Dedicated and Private Node Billing

How vBilling bills nodes that belong to one tenant cluster for their full capacity, whether they sit in the control plane cluster (dedicated nodes) or join the tenant cluster itself (vCluster Private Nodes, Auto Nodes, Standalone), without ever billing the workloads on them twice.

What dedicated nodes are

A dedicated node is a physical server, VM or bare-metal machine assigned to one tenant cluster. AI Clouds typically sell them by SKU (for example bm.gpu.h100.8), billing the whole machine regardless of utilization. Shared nodes, by contrast, are billed by what each pod allocates.

i
Dedicated nodes are control plane cluster nodes assigned through labels. With vCluster Private Nodes, nodes join the tenant cluster directly and the control plane cluster never sees them or their pods; see Private Nodes, Auto Nodes and Standalone.

How vBilling detects them

A node is dedicated to a tenant cluster when any of these labels match. The namespace is the tenant cluster's control plane cluster namespace; the name is the tenant cluster's name.

LabelMatches
vbilling.vcluster.com/tenant-clusterThe tenant cluster ID (vcluster-<namespace>-<name>) or name. Recommended.
vcluster.loft.sh/managed-byNamespace or name (also the name with a vcluster- or vc- namespace prefix stripped)
vcluster.loft.sh/clusterAs above
VCLUSTER_NODE_LABEL patternAny key=value where %s is replaced with the candidate names, e.g. tenant=%s

Taint dedicated nodes (for example dedicated=team-b:NoSchedule) and give the tenant's workloads a matching toleration, so other tenants cannot land on them.

kubectl label node bm-h100-01 vbilling.vcluster.com/tenant-cluster=vcluster-team-b-team-b kubectl label node bm-h100-01 vbilling.vcluster.com/sku=bm.gpu.h100.8 vbilling.vcluster.com/capacity-type=reserved kubectl taint node bm-h100-01 dedicated=team-b:NoSchedule

What gets billed

Each dedicated node produces its own events every window (resource_id = node name):

MetricQuantityDimensions
vcluster_private_node_hoursHours the node was healthysku (SKU label, instance type, or <n>x<GPU model>), capacity_type, instance_type, node
vcluster_gpu_hoursGPU capacity × hoursbilling_mode=dedicated_node, sku, gpu_type
vcluster_cpu_core_hoursCPU capacity × hoursbilling_mode=dedicated_node
vcluster_memory_gb_hoursMemory capacity (GiB) × hoursbilling_mode=dedicated_node

Price either the node-hours by SKU, or the capacity components by billing_mode, whichever matches how you sell. Set the other to zero.

No double billing

Pods that run on the tenant's own dedicated nodes are not metered again as shared usage: the node allocation already covers them. (v0.1 billed both the pods and the node.) A pod from a different tenant that lands on an untainted dedicated node is billed to its own tenant as shared usage.

Downtime

If a dedicated node is NotReady, or carries a taint listed in UNHEALTHY_NODE_TAINTS, its node-hours stop and its GPUs are recorded as vcluster_gpu_downtime_hours (informational, never invoiced), from the moment the condition or taint appeared.

Private Nodes, Auto Nodes and Standalone

With Private Nodes, vCluster syncs nothing to the control plane cluster: the nodes, their pods and their volumes exist only in the tenant cluster. vBilling meters these tenant clusters through their own API. Every node the tenant cluster's API reports that the control plane cluster does not have (and that is not one of vCluster's placeholder nodes, labeled vcluster.loft.sh/fake-node) is a private node, billed like a dedicated node with billing_mode=private_node. The tenant cluster's volumes and load balancers are billed as well. Shared tenant clusters are never billed twice, even when vBilling can read their API.

vBilling reads one Secret per tenant cluster, vbilling-kubeconfig in its namespace, and its RBAC is pinned to that name. Let vCluster write it with a read-only service account:

exportKubeConfig: additionalSecrets: - name: vbilling-kubeconfig serviceAccount: name: vbilling-reader namespace: kube-system clusterRole: vbilling-reader experimental: deploy: vcluster: manifests: |- apiVersion: rbac.authorization.k8s.io/v1 kind: ClusterRole metadata: name: vbilling-reader rules: - apiGroups: [""] resources: [nodes, pods, persistentvolumeclaims, services] verbs: [get, list, watch] - apiGroups: [resource.k8s.io] resources: [resourceclaims, resourceslices] verbs: [get, list] - apiGroups: [metrics.k8s.io] resources: [pods] verbs: [get, list]

vCluster writes kubeconfigs for localhost; vBilling connects to the tenant cluster's Service and verifies TLS against <name>.<namespace>. Tenant clusters outside the control plane cluster (vCluster Standalone, or any other cluster) are listed in TENANT_CLUSTERS_FILE with their own kubeconfig.

SettingEffect
PRIVATE_NODE_BILLING=node (default)Each private node is billed whole: node-hours, whole GPUs, CPU and memory capacity.
PRIVATE_NODE_BILLING=usageThe pods on private nodes are billed instead, like shared usage (namespaces in TENANT_EXCLUDE_NAMESPACES, default kube-system, are skipped).
vbilling.vcluster.com/billable=false node labelExempts a node, for example hardware the tenant owns. Works for dedicated nodes too.
TENANT_ADMIN_FALLBACK=trueAlso accepts the tenant cluster's admin kubeconfig (vc-<name>). Requires read access to Secrets; prefer the read-only export.

Outages. If a tenant cluster's API cannot be read, everything else is still metered and the gap is recorded under DATA_DIR. As soon as the API answers, exactly the missed windows are metered and appended as late events, deduplicated by ID, up to MAX_BACKFILL.

Scale-down. Nodes deleted between two windows (Auto Nodes scaling down, a machine removed) are billed until the second they were deleted. A deletion noticed only after a watch reconnects is dated to the last time vBilling saw the node, never later.

Prometheus for clusters with their own nodes

Pods on private nodes never appear in the control plane cluster. A Prometheus there never scrapes them, and their series carry no control plane cluster namespace. Ship them to your Prometheus with a Prometheus agent, or an OpenTelemetry collector, inside the cluster that remote writes with an external label naming the cluster:

# prometheus.yml of the agent inside the cluster global: external_labels: {vcluster: private-a100} # the cluster's name remote_write: - url: http://prometheus.monitoring.example.com:9090/api/v1/write

vBilling then selects that cluster's series with vcluster="private-a100" wherever a metric uses {{selector}} or {{matchers}}, and so do the built-in egress counter and the DCGM utilization queries. The label is PROMETHEUS_SOURCE_LABEL (Helm prometheus.sourceLabel, default vcluster). If the agent's value is not the cluster's name, set vbilling.vcluster.com/prometheus-source on the cluster. examples/gke-gpu/06-prometheus-agent.yaml in the repository is a complete agent that ships DCGM this way.

vBilling knows a cluster runs on its own nodes because it reads the cluster's API with the exported kubeconfig above. A cluster it cannot read is scoped by namespace, like a cluster on shared nodes; give it vbilling.vcluster.com/prometheus-matchers instead. All scoping rules are in Usage Sources.

A Prometheus inside the cluster

A cluster can instead name a Prometheus that sees only it, with vbilling.vcluster.com/prometheus-url. vBilling queries it without extra matchers, because the source itself is the scope:

  • A URL vBilling can reach, such as https://prometheus.globex.example.com. It gets PROMETHEUS_HEADERS and the bearer token only when it is on the same host as PROMETHEUS_URL, so an annotation can never send them elsewhere. Put credentials for any other host in its URL (https://user:password@host).
  • tenant-service://NAMESPACE/NAME:PORT, with an optional path prefix after the port, for a Service inside the cluster. vBilling reaches it through the cluster's API server, so nothing is exposed. The cluster's API credentials need get on services/proxy in that namespace:
# inside the cluster, for tenant-service://monitoring/prometheus:9090 apiVersion: rbac.authorization.k8s.io/v1 kind: Role metadata: name: vbilling-prometheus namespace: monitoring rules: - apiGroups: [""] resources: [services/proxy] verbs: [get] --- apiVersion: rbac.authorization.k8s.io/v1 kind: RoleBinding metadata: name: vbilling-prometheus namespace: monitoring roleRef: apiGroup: rbac.authorization.k8s.io kind: Role name: vbilling-prometheus subjects: - kind: ServiceAccount name: vbilling-reader namespace: kube-system

Billing-state enforcement inside the cluster

In enforce mode, vBilling labels a suspended tenant's namespaces in the control plane cluster, and the chart's admission policy denies new pods there. That holds clusters on shared and dedicated nodes, whose pods are synced into those namespaces. A cluster with its own nodes schedules its pods inside itself, so the control plane cluster never sees them.

With ENFORCEMENT_IN_CLUSTER=true (Helm enforcement.inCluster=true), vBilling also acts inside each of a suspended tenant's clusters, through the cluster's own API:

  • It installs a ValidatingAdmissionPolicy and a binding, both named vbilling-suspended, that deny new pods in every namespace except kube-system and namespaces labeled vbilling.vcluster.com/enforcement-exempt. The cluster needs Kubernetes 1.30 or later.
  • The denial carries the reason: This tenant is suspended for billing (...). New workloads are blocked until the account is current; running workloads are not affected.
  • Running workloads are never stopped. When the tenant is active again, vBilling deletes the policy and the binding.
  • vBilling applies it when the tenant's state changes, and again every two minutes for every tenant. A cluster created while its tenant is suspended gets the policy within two minutes, and a cluster that could not be reached when the state changed (including when the tenant paid) converges once it answers. If a cluster cannot be reached at the change itself, the API call or webhook that changed the state also fails and names the cluster, so billing platforms retry it.
  • It needs ENFORCEMENT_MODE=enforce and TENANT_API=true. Clusters without API credentials are skipped.

This is the only enforcement that reaches clusters with their own nodes. The read-only service account vCluster exports for vBilling cannot write admission policies, so grant it that in vcluster.yaml, next to vbilling-reader:

experimental: deploy: vcluster: manifests: |- apiVersion: rbac.authorization.k8s.io/v1 kind: ClusterRole metadata: name: vbilling-reader rules: - apiGroups: [""] resources: [nodes, pods, persistentvolumeclaims, services] verbs: [get, list, watch] - apiGroups: [resource.k8s.io] resources: [resourceclaims, resourceslices] verbs: [get, list] - apiGroups: [metrics.k8s.io] resources: [pods] verbs: [get, list] --- apiVersion: rbac.authorization.k8s.io/v1 kind: ClusterRole metadata: name: vbilling-enforcer rules: - apiGroups: [admissionregistration.k8s.io] resources: [validatingadmissionpolicies, validatingadmissionpolicybindings] verbs: [create] - apiGroups: [admissionregistration.k8s.io] resources: [validatingadmissionpolicies, validatingadmissionpolicybindings] resourceNames: [vbilling-suspended] verbs: [get, update, delete] --- apiVersion: rbac.authorization.k8s.io/v1 kind: ClusterRoleBinding metadata: name: vbilling-enforcer roleRef: apiGroup: rbac.authorization.k8s.io kind: ClusterRole name: vbilling-enforcer subjects: - kind: ServiceAccount name: vbilling-reader namespace: kube-system

Kubernetes RBAC cannot limit create to a name; the other verbs only reach vbilling-suspended. Then turn it on:

helm upgrade vbilling deploy/helm/vbilling -n vbilling-system --reuse-values \ --set enforcement.mode=enforce --set enforcement.inCluster=true \ --set enforcement.admissionPolicy.enabled=true # the control plane cluster's policy, for shared and dedicated nodes

Holds

A tenant can be held for more than one reason. Billing webhooks own the billing hold. Operators set others through the API, such as abuse or support, and only an operator clears them. The tenant's state is the most severe of its holds, so a payment that clears the billing hold never lifts an operator's hold.

curl -X PUT localhost:8080/api/v1/billing-states/globex -H "Authorization: Bearer $API_TOKEN" \ -d '{"state": "suspended", "hold": "abuse", "reason": "outbound spam reported"}' # later, after the review curl -X PUT localhost:8080/api/v1/billing-states/globex -H "Authorization: Bearer $API_TOKEN" \ -d '{"state": "active", "hold": "abuse"}'

Without hold, a PUT sets the billing hold. Setting a hold to active removes it. GET /api/v1/billing-states lists each tenant's state with its holds; for a hold other than billing, the reason starts with the hold's name, and the in-cluster denial reads This tenant is suspended (abuse: outbound spam reported). New workloads are blocked until the hold is lifted; ...

✓
In a live run with ENFORCEMENT_IN_CLUSTER on, kubectl run inside a suspended tenant's cluster was denied by vbilling-suspended with the reason. A payment cleared the billing hold, and an abuse hold kept the tenant blocked until the operator lifted it.

Whole GPUs, however they are carved

Dedicated and private nodes are billed for physical GPUs. MIG slices (mixed or single strategy, GKE GPU partitions) and time-slicing replicas (NVIDIA or GKE time-sharing) are converted back: a node exposing 56 MIG slices of 1g.10gb, or 32 time-sliced devices with 4 replicas, bills 8 GPUs. GPUs offered only through DRA ResourceSlices count too.

GPU model detection

The first label present wins: nvidia.com/gpu.product, nvidia.com/gpu.machine, amd.com/gpu.product-name, cloud.google.com/gke-accelerator, k8s.amazonaws.com/accelerator, accelerator. Spaces are replaced with dashes (NVIDIA H100 80GB HBM3 becomes NVIDIA-H100-80GB-HBM3). The -SHARED and -MIG-<profile> suffixes GPU Feature Discovery adds are removed, so the SKU is always the base GPU; DRA devices use their productName attribute.
