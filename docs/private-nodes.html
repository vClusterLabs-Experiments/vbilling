Dedicated and Private Node Billing

How vBilling bills nodes that belong to one cluster for their full capacity, whether they sit in the control plane cluster (dedicated nodes) or join the cluster itself (vCluster Private Nodes, Auto Nodes, Standalone), without ever billing the workloads on them twice.

What dedicated nodes are

A dedicated node is a physical server, VM or bare-metal machine assigned to one cluster. AI Clouds typically sell them by SKU (for example bm.gpu.h100.8), billing the whole machine regardless of utilization. Shared nodes, by contrast, are billed by what each pod allocates.

i
Dedicated nodes are control plane cluster nodes assigned through labels. With vCluster Private Nodes, nodes join the cluster directly and the control plane cluster never sees them or their pods; see Private Nodes, Auto Nodes and Standalone.

How vBilling detects them

A node is dedicated to a cluster when any of these labels match. The namespace is the cluster's control plane cluster namespace; the name is the cluster's name.

LabelMatches
vbilling.vcluster.com/tenant-clusterThe cluster ID (vcluster-<namespace>-<name>) or name. Recommended.
vcluster.loft.sh/managed-byNamespace or name (also the name with a vcluster- or vc- namespace prefix stripped)
vcluster.loft.sh/clusterAs above
VCLUSTER_NODE_LABEL patternAny key=value where %s is replaced with the candidate names, e.g. tenant=%s

Taint dedicated nodes (for example dedicated=team-b:NoSchedule) and give the tenant's workloads a matching toleration, so other tenants cannot land on them.

kubectl label node bm-h100-01 vbilling.vcluster.com/tenant-cluster=vcluster-team-b-team-b kubectl label node bm-h100-01 vbilling.vcluster.com/sku=bm.gpu.h100.8 vbilling.vcluster.com/capacity-type=reserved kubectl taint node bm-h100-01 dedicated=team-b:NoSchedule

What gets billed

Each dedicated node produces its own events every window (resource_id = node name):

MetricQuantityDimensions
vcluster_private_node_hoursHours the node was healthysku (SKU label, instance type, or <n>x<GPU model>), capacity_type, instance_type, node
vcluster_gpu_hoursGPU capacity × hoursbilling_mode=dedicated_node, sku, gpu_type
vcluster_cpu_core_hoursCPU capacity × hoursbilling_mode=dedicated_node
vcluster_memory_gb_hoursMemory capacity (GiB) × hoursbilling_mode=dedicated_node

Price either the node-hours by SKU, or the capacity components by billing_mode, whichever matches how you sell. Set the other to zero.

No double billing

Pods that run on the tenant's own dedicated nodes are not metered again as shared usage: the node allocation already covers them. (v0.1 billed both the pods and the node.) A pod from a different tenant that lands on an untainted dedicated node is billed to its own tenant as shared usage.

Downtime

If a dedicated node is NotReady, or carries a taint listed in UNHEALTHY_NODE_TAINTS, its node-hours stop and its GPUs are recorded as vcluster_gpu_downtime_hours (informational, never invoiced), from the moment the condition or taint appeared. A node that stops reporting (a preempted spot VM, a host that loses power) is marked Unknown only after the node controller's grace period, 40 to 50 seconds. For such a node the downtime starts at its last proof of life instead: the later of its last status heartbeat and its last Lease renewal, which the reader role above may get. On GCP, a preempted A100 spot node was billed until its last heartbeat, not the 59 seconds more until the Unknown mark.

A cluster's own node (below) is down only while its Ready condition is False or Unknown, dated the same way. Taints on it are ignored: whoever runs the cluster writes them, and a taint can carry an effect that evicts nothing.

Private Nodes, Auto Nodes and Standalone

With Private Nodes, vCluster syncs nothing to the control plane cluster: the nodes, their pods and their volumes exist only in the cluster. vBilling meters these clusters through their own API. Every node the cluster's API reports is a private node, billed like a dedicated node with billing_mode=private_node, unless it is a control plane cluster node seen through the cluster: a node with the same name as a control plane cluster node that either reports the same machine (status.nodeInfo.systemUUID or machineID, as vCluster's copy of a synced node does), or runs pods this cluster synced (vCluster's placeholder node, which it creates only for those). A node's own labels never decide, vcluster.loft.sh/fake-node included. The cluster's volumes and load balancers are billed as well. Shared clusters are never billed twice, even when vBilling can read their API.

vBilling reads one Secret per cluster, vbilling-kubeconfig in its namespace, and its RBAC is pinned to that name. Let vCluster write it with a read-only service account:

exportKubeConfig: additionalSecrets: - name: vbilling-kubeconfig serviceAccount: name: vbilling-reader namespace: kube-system clusterRole: vbilling-reader experimental: deploy: vcluster: manifests: |- apiVersion: rbac.authorization.k8s.io/v1 kind: ClusterRole metadata: name: vbilling-reader rules: - apiGroups: [""] resources: [nodes, pods, persistentvolumeclaims, services] verbs: [get, list, watch] - apiGroups: [""] resources: [namespaces] verbs: [get, list] - apiGroups: [coordination.k8s.io] resources: [leases] verbs: [get, list] - apiGroups: [resource.k8s.io] resources: [resourceclaims, resourceslices] verbs: [get, list] - apiGroups: [metrics.k8s.io] resources: [pods] verbs: [get, list]

vCluster writes kubeconfigs for localhost; vBilling connects to the cluster's Service and verifies TLS against <name>.<namespace>. Clusters outside the control plane cluster (vCluster Standalone, or any other cluster) are listed in TENANT_CLUSTERS_FILE with their own kubeconfig.

SettingEffect
PRIVATE_NODE_BILLING=node (default)Each private node is billed whole: node-hours, whole GPUs, CPU and memory capacity.
PRIVATE_NODE_BILLING=usageThe pods on private nodes are billed instead, like shared usage. Pods in kube-system, and in namespaces of the cluster labeled vbilling.vcluster.com/exclude=true (for example the GPU operator's), are skipped.

The vbilling.vcluster.com/billable=false label exempts only dedicated nodes of the control plane cluster, which the operator labels. On a cluster's own nodes it is ignored.

vbilling.vcluster.com/exclude=true means two things, depending on where it is set:

  • On the control plane cluster, on a cluster's namespace, StatefulSet or Deployment, or VirtualClusterInstance: the whole cluster is not metered. In Platform mode this applies only to clusters the Platform does not know. For a cluster with an instance, the annotation on the cluster, its namespace or its instance is ignored, like every other vbilling.vcluster.com/ setting there; set it on the Tenant (or on a Project no Tenant owns) to stop metering all of that customer's clusters.
  • On a namespace inside a cluster, with PRIVATE_NODE_BILLING=usage: the pods in that namespace are not billed. It needs get and list on namespaces in the reader role above; without them, no namespace is skipped. It has no effect with PRIVATE_NODE_BILLING=node, which bills whole nodes whatever runs on them.

An exclusion counts from the moment vBilling sees it, within its discovery interval (30 seconds; one minute for a setting on a Platform Tenant or Project). The cluster is billed up to that moment and again from the moment vBilling sees the setting removed, to the second, so the windows the setting was changed in are billed for the part before and after. Nothing in between is billed, then or later: the excluded time is never metered afterwards, and a Prometheus counter does not bill what it counted meanwhile. A cluster vBilling finds excluded when it starts is excluded from the first window it has not committed yet.

An exclusion is never silent. The tenant in GET /api/v1/tenants lists the cluster under excluded_clusters instead of clusters, GET /api/v1/sources has an entry metering/<cluster ID> with status paused that says since when, the log records when it began and ended, and vbilling_excluded_clusters counts the clusters excluded now. A tenant whose every cluster is excluded is offboarded after an hour, like a tenant without clusters.

In usage mode the cluster decides which of its namespaces count: its admins can label a namespace, or run pods in kube-system. Use usage mode for clusters whose admins you trust, and bill other clusters' own nodes whole (the default).

Outages. If a cluster's API cannot be read, everything else is still metered and the windows it missed are recorded under DATA_DIR, before those windows are committed. If they cannot be recorded (a full or read-only volume), nothing is committed, the source tenant-api-gaps fails, and the windows are read again on the next pass. As soon as the API answers, exactly those windows are metered and appended as late events, deduplicated by ID, up to 24 hours back. That limit is fixed; a gap older than 24 hours is not filled. An API that fails, answers and fails again has only its failed windows filled: a window read in between is never billed again. A gap recorded by v0.3.0 is filled with the event IDs v0.3.0 gave, so nothing it already filled bills again.

Scale-down and deletion. Nodes deleted between two windows (Auto Nodes scaling down, a machine removed) are billed until the second they were deleted, and so are the cluster's volumes and load balancers. A deletion noticed only after a watch reconnects is dated to the last time vBilling saw the node, never later. A cluster that is deleted is metered one last time: the window it was deleted in bills its control plane until its last replica was gone, and its own nodes, volumes and load balancers (as last read) up to the second its control plane workload was deleted. Nothing is billed after that, even while its machines are still being released. Its tenant stays listed, with no clusters, until it is offboarded.

A node bills as vBilling first saw it

A cluster's admins are cluster admins inside it, so every label, taint and status of the cluster's own nodes is theirs to write. Nothing they change later lowers what a node bills:

  • Its GPU model, instance type, SKU (SKU_LABEL), capacity type and zone stay as vBilling first saw them, per node, by cluster and node name: deleting the node object and creating it again under the same name changes nothing. A GPU model first seen as unknown, before GPU Feature Discovery labeled the node, is taken from the first label that names one. An instance type, SKU, capacity type or zone first seen empty is taken from labels set within 10 minutes of the node's creation, since the cloud controller manager and Karpenter label a node seconds after its kubelet registers it; later labels never count.
  • It is billed for no fewer GPUs than it had while it lived, its GPU floor, kept in DATA_DIR/private-nodes.json. With GPU Feature Discovery's physical count (nvidia.com/gpu.count), the floor rises to what the node advertises, up to that count. Without it, two reads at least 30 seconds apart set the first floor, and a higher count raises it once it held for 10 minutes: MIG slices or time-sliced devices advertised before the labels that convert them back to physical GPUs (Node Feature Discovery relabels every 60 seconds by default) never stick. A node that later advertises fewer, or whose GPUs stop being allocatable, still bills its floor.
  • Time-slicing replicas divide its advertised GPUs only when GPU Feature Discovery's nvidia.com/gpu.count adds up with them (advertised devices equal physical GPUs times replicas). GKE's time-sharing labels are ignored there.

A change is logged, and the source private-nodes/<cluster ID> in GET /api/v1/sources turns diverged and names the node and what changed, until the node is back as it was. To bill a machine differently on purpose, give it a new node name. Records kept by node UID before v0.3.1 are moved to the node's name on upgrade, two records of one node becoming one, as first seen.

i
What vBilling sees. vBilling reads a cluster's own nodes from inside the cluster, so it trusts what it sees there the first time. A tenant with root on its own node can stop its kubelet (the node then reads as down), or set the node's labels before vBilling first sees it, GPU Feature Discovery's count among them. A machine that replaces another under the same node name bills as the first one did. For untrusted tenants, bill their nodes from your machine inventory (vMetal or Auto Nodes) through the ingest API, and keep this metering as a cross-check. Billing from vMetal's inventory directly is planned in issue #18.

vCluster Platform mode

With TENANT_SOURCE=platform (Helm tenantSource: platform), vBilling takes billing identity from vCluster Platform objects instead of labels and annotations, and reaches clusters with their own nodes through the Platform proxy instead of an exported kubeconfig. Nothing has to be added to clusters, their namespaces or their vcluster.yaml.

QuestionAnswer in Platform mode
Which Platform object is the cluster?The VirtualClusterInstance whose spec.clusterRef (cluster, namespace, virtualCluster) points at the cluster's StatefulSet or Deployment on this control plane cluster. Set PLATFORM_CLUSTER to this control plane cluster's name in the Platform, so instances on other connected clusters never match.
Which project?The Project that holds the instance (its namespace, read from the Project's loft.sh/project-namespace annotation, p-<project> by default).
Who pays?The Platform Tenant that owns the project, as customer tenant-<name>. Projects no Tenant owns, and every project on Platform versions before 4.12 (they have no Tenant resource), are customers project-<name>, the same ID TENANT_SOURCE=project uses.
Keep an existing customer ID?Set vbilling.vcluster.com/tenant on the Tenant (or on a Project no Tenant owns). Use it when you switch from label-based identity and want invoices to continue under the same customer.
What if that setting is changed later?The Tenant's usage is billed under the new ID from vBilling's next read, and a billing platform that keys customers on the ID sees another customer from then on, without the balance, commits and credits of the old one. vBilling does not stop it (whoever can edit a Tenant decides who pays) but says so: a WARNING in the log, an entry billing-id/<new ID> in GET /api/v1/sources, the counter vbilling_tenant_id_changes_total, and previous_tenant_id on the customer record. To keep one customer, give the existing customer the new ID as well before you change the setting (in Metronome: add it to the customer's ingest aliases).
Name, email, plan, currency, tenant class, customer IDsThe Tenant's display name and its vbilling.vcluster.com/ annotations (the Project's, when no Tenant owns it). For a cluster the Platform knows, these settings (tenant, tenant-class, plan, exclude, display-name and the rest) on the cluster, its namespace, its StatefulSet or its VirtualClusterInstance are ignored: the people who create clusters can set those (vcluster.yaml sets workload labels), so they never choose who pays or at what price.
Per-cluster settings such as prometheus-urlRead only from the Tenant or Project, never from the cluster, its namespace or its instance: whoever writes vcluster.yaml writes those, and they decide how a cluster is metered. See Security.
Clusters without an instanceBilled by the usual label rules (vbilling.vcluster.com/tenant, else one customer per cluster), and listed as empty in GET /api/v1/sources.

The tenant binding is read from the Project's labels: tenant.vcluster.com/owner (stamped when a tenant creates the project) or tenant.vcluster.com/exclusive-to (an operator's project assigned to one tenant) on Platform 4.13 and later, tenant.platform.vcluster.com/name on 4.12. A project carrying both current labels is treated as owned by no Tenant, as the Platform does, and flagged. Customer records get platform_account, platform_tenant (or platform_project) and its UID as metadata; every usage event in vBilling's ledger carries platform_instance and the instance, project and tenant UIDs as properties, so usage stays traceable after a name is reused. These stay in vBilling: the Metronome adapter sends an event's dimensions and vBilling's own properties only, so a Metronome event has none of the platform_ properties, and a Metronome customer holds only its name and ingest alias. To trace a Metronome event back to an instance, look its transaction ID up in GET /api/v1/events.

Set it up

Create a Platform user for vBilling, give it a global role that reads the three resources and may use virtual cluster instances, and issue an access key for it (Platform UI: Users, then Access Keys; or as objects):

apiVersion: storage.loft.sh/v1 kind: ClusterRoleTemplate metadata: name: vbilling-platform-reader spec: displayName: vBilling Platform Reader management: true clusterRoleTemplate: rules: - apiGroups: ["management.loft.sh"] resources: ["projects", "tenants", "virtualclusterinstances"] verbs: ["get", "list", "watch"] - apiGroups: ["management.loft.sh"] resources: ["virtualclusterinstances"] verbs: ["use"] --- apiVersion: storage.loft.sh/v1 kind: User metadata: name: vbilling spec: username: vbilling subject: vbilling displayName: vBilling metering clusterRoles: - name: vbilling-platform-reader
kubectl -n vbilling-system create secret generic vbilling-platform --from-literal=access-key=<key> # values.yaml tenantSource: platform platform: cluster: loft-cluster # this control plane cluster's name in the Platform url: https://platform.example.com existingSecret: vbilling-platform caSecret: platform-ca # Secret with ca.crt, when the certificate is not publicly trusted
!
The role must be global (spec.clusterRoles on the user or a team). Project membership is not enough: the Platform silently filters list results to what a key may see, so a key that is only a member of some projects reads only their instances, and clusters in the other projects fall back to label rules. If the key has an access key scope, the scope must cover every project. On Platform 4.13 and later, Tenant labels are hidden from tenant-scoped clients, so the key must belong to an operator user, not to a user of a tenant.
PermissionWhy
get, list, watch on projectsProject names, display names, UIDs, project namespaces and Tenant labels.
get, list, watch on tenantsTenant display names, UIDs and billing settings (Platform 4.12 and later; harmless before).
get, list, watch on virtualclusterinstances, all projectsWhich instance points at which cluster, instance UIDs and phases.

Read access inside each clusterNodes, pods, persistent volume claims, services, DRA claims and slices, pod metrics: the same rules as the vbilling-reader ClusterRole above. A user allowed to use an instance gets cluster admin inside it unless an access rule says otherwise, so give the vBilling user a read-only rule in every VirtualClusterTemplate (below).

Keep vBilling read-only inside each cluster. Two things are needed, and neither is created by the vBilling chart: the vbilling-reader ClusterRole inside each cluster (the same rules as above; deploy it with the template, for example through experimental.deploy.vcluster.manifests), and an access rule in the template that maps the vBilling user to it:

apiVersion: management.loft.sh/v1 kind: VirtualClusterTemplate spec: template: access: rules: - users: - vbilling # the Platform user from the step above clusterRole: vbilling-reader

The Platform then binds the group loft:user:vbilling to vbilling-reader inside every cluster created from the template, and puts the rule back within a second if someone removes it from an instance. Check it from inside a cluster: exactly one ClusterRoleBinding should name that group, and its role should hold read verbs only.

The rule is wider than the table above suggests on the Platform side. Besides use, the Platform gives the user named in an access rule the instance subresources logs, kubeconfig, shell, resourceusage and controlplanepods. vBilling calls none of them, but whoever holds the access key could, so store the key as a credential with that reach.

Clusters with their own nodes

For a cluster bound to an instance, vBilling connects to <PLATFORM_URL>/kubernetes/project/<project>/virtualcluster/<instance> with the access key, the same route and credential vcluster platform connect vcluster uses. No kubeconfig Secret and no Secret RBAC are needed, and vBilling never reads a vbilling-kubeconfig Secret in this mode: a cluster's creator can export one, pointing anywhere.

vBilling never wakes a sleeping instance to meter it. While it sleeps its control plane hours stop, and its own nodes, which stay allocated to the tenant, keep billing from the inventory vBilling read last before the instance went to sleep (see Pause: a pause vBilling did not make stops only control plane hours). Only when vBilling never read the instance before it went to sleep (it started while the instance slept) are those windows recorded as a gap and filled when it wakes, like any tenant API outage. Requests carry the user agent vbilling/<version>; add vbilling/* to the instance's sleepmode.loft.sh/ignore-user-agents annotation so metering does not count as activity.

What a Platform-side billing: true could automate

Platform mode works with any Platform 4.x today. A Platform integration could remove the remaining manual steps:

  • Identity. A billing flag on a Tenant (or a VirtualClusterTemplate) that the Platform resolves itself: it already knows the Tenant, Project and instance of every cluster, and could stamp a stable billing account ID (and the customer IDs vBilling creates) into the Tenant's configuration, so no annotation is needed at all.
  • Service account and roles. For each instance with billing on, the Platform could deploy the vbilling-reader ClusterRole and a service account inside the cluster (it already applies virtualClusterObjects) and add an instance access rule mapping the vBilling user to that role, instead of granting cluster admin through the proxy.
  • Key issuance. One Platform-issued, scoped and rotated key for the metering service (user, global read role, use on billed instances), delivered as a Secret next to vBilling, replacing the manual user and access key above.
  • Moves and lifecycle. An explicit move record (old and new project, time) on the instance, and an event or webhook when instances are created, moved, put to sleep or deleted, would replace polling and the creation-time heuristic for dating moves.
  • Sleep. A way to read node and volume inventory of a sleeping instance without waking it, so own-node usage during sleep follows the nodes the instance has, not the inventory read before it went to sleep.

Prometheus for clusters with their own nodes

Pods on private nodes never appear in the control plane cluster. A Prometheus there never scrapes them, and their series carry no control plane cluster namespace. Ship them to your Prometheus with a Prometheus agent, or an OpenTelemetry collector, inside the cluster that remote writes with an external label naming the cluster:

# prometheus.yml of the agent inside the cluster global: external_labels: {vcluster: private-a100} # the cluster's name remote_write: - url: http://prometheus.monitoring.example.com:9090/api/v1/write

vBilling then selects that cluster's series with vcluster="private-a100" wherever a metric uses {{selector}} or {{matchers}}, and so do the built-in egress counter and the DCGM utilization queries. The label is PROMETHEUS_SOURCE_LABEL (Helm prometheus.sourceLabel, default vcluster). If the agent's value is not the cluster's name, set vbilling.vcluster.com/prometheus-source on the cluster. examples/gke-gpu/06-prometheus-agent.yaml in the repository is a complete agent that ships DCGM this way.

vBilling knows a cluster runs on its own nodes because it reads the cluster's API with the exported kubeconfig above. A cluster it cannot read is scoped by namespace, like a cluster on shared nodes; give it vbilling.vcluster.com/prometheus-matchers instead. All scoping rules are in Usage Sources.

A Prometheus inside the cluster

A cluster can instead name a Prometheus that sees only it, with vbilling.vcluster.com/prometheus-url. vBilling queries it without extra matchers, because the source itself is the scope:

  • A URL vBilling can reach, such as https://prometheus.globex.example.com. It gets PROMETHEUS_HEADERS and the bearer token only when it is on the same host as PROMETHEUS_URL, so an annotation can never send them elsewhere. Put credentials for any other host in its URL (https://user:password@host).
  • tenant-service://NAMESPACE/NAME:PORT, with an optional path prefix after the port, for a Service inside the cluster. vBilling reaches it through the cluster's API server, so nothing is exposed. The cluster's API credentials need get on services/proxy in that namespace:
# inside the cluster, for tenant-service://monitoring/prometheus:9090 apiVersion: rbac.authorization.k8s.io/v1 kind: Role metadata: name: vbilling-prometheus namespace: monitoring rules: - apiGroups: [""] resources: [services/proxy] verbs: [get] --- apiVersion: rbac.authorization.k8s.io/v1 kind: RoleBinding metadata: name: vbilling-prometheus namespace: monitoring roleRef: apiGroup: rbac.authorization.k8s.io kind: Role name: vbilling-prometheus subjects: - kind: ServiceAccount name: vbilling-reader namespace: kube-system

Billing-state enforcement inside the cluster

In enforce mode, vBilling labels a suspended tenant's namespaces in the control plane cluster, and the chart's admission policy denies new pods there. That holds clusters on shared and dedicated nodes, whose pods are synced into those namespaces. A cluster with its own nodes schedules its pods inside itself, so the control plane cluster never sees them.

One namespace can hold clusters of more than one tenant. vBilling then labels it suspended while any of them is blocked, and annotates it vbilling.vcluster.com/active.<cluster> for each of the others: the chart's policy still lets their synced pods start, so one tenant's suspension never blocks another, and another tenant's payment never lifts it.

With ENFORCEMENT_IN_CLUSTER=true (Helm enforcement.inCluster=true), vBilling also acts inside each of a suspended tenant's clusters, through the cluster's own API:

  • It installs a ValidatingAdmissionPolicy and a binding, both named vbilling-suspended, that deny new pods in every namespace except kube-system. No label exempts a namespace. The kubelet's mirror pods of static pods are let through, so a static pod stays visible, and billed. The cluster needs Kubernetes 1.30 or later.
  • The denial carries the reason: This tenant is suspended for billing (...). New workloads are blocked until the account is current; running workloads are not affected.
  • Running workloads are never stopped. When the tenant is active again, vBilling deletes the policy and the binding.
  • vBilling sets the policy and the binding to its own spec when the tenant's state changes, and again every two minutes for every tenant, whoever created or changed them: a binding that only audits, or one that matches nothing, gets vBilling's spec back. A cluster created while its tenant is suspended gets the policy within two minutes, and a cluster that could not be reached when the state changed (including when the tenant paid) converges once it answers. If a cluster cannot be reached at the change itself, the API call or webhook that changed the state also fails and names the cluster; the state is stored either way.
  • It needs ENFORCEMENT_MODE=enforce and access to the cluster's API. Clusters without API credentials are skipped.

A tenant's admins are cluster admins inside its clusters: they can delete the policy between two passes, or start pods in kube-system. Suspension inside a cluster is best effort against them. Pausing is the hard stop: it stops the cluster's control plane, which they cannot start again.

This is the only enforcement that reaches clusters with their own nodes. The read-only service account vCluster exports for vBilling cannot write admission policies, so grant it that in vcluster.yaml, next to vbilling-reader:

experimental: deploy: vcluster: manifests: |- apiVersion: rbac.authorization.k8s.io/v1 kind: ClusterRole metadata: name: vbilling-reader rules: - apiGroups: [""] resources: [nodes, pods, persistentvolumeclaims, services] verbs: [get, list, watch] - apiGroups: [coordination.k8s.io] resources: [leases] verbs: [get, list] - apiGroups: [resource.k8s.io] resources: [resourceclaims, resourceslices] verbs: [get, list] - apiGroups: [metrics.k8s.io] resources: [pods] verbs: [get, list] --- apiVersion: rbac.authorization.k8s.io/v1 kind: ClusterRole metadata: name: vbilling-enforcer rules: - apiGroups: [admissionregistration.k8s.io] resources: [validatingadmissionpolicies, validatingadmissionpolicybindings] verbs: [create] - apiGroups: [admissionregistration.k8s.io] resources: [validatingadmissionpolicies, validatingadmissionpolicybindings] resourceNames: [vbilling-suspended, vbilling-paused] verbs: [get, update, delete] # optional: lets workloads come back at once when a suspension is lifted - apiGroups: [apps] resources: [replicasets, statefulsets, daemonsets] verbs: [list, patch] - apiGroups: [batch] resources: [jobs] verbs: [list, patch] --- apiVersion: rbac.authorization.k8s.io/v1 kind: ClusterRoleBinding metadata: name: vbilling-enforcer roleRef: apiGroup: rbac.authorization.k8s.io kind: ClusterRole name: vbilling-enforcer subjects: - kind: ServiceAccount name: vbilling-reader namespace: kube-system

Kubernetes RBAC cannot limit create to a name; the other verbs only reach vbilling-suspended and the pause policy, vbilling-paused. Without them for vbilling-paused, pauses of clusters with their own nodes are never verified (see Pausing a tenant).

The last two rules are optional. While a tenant is suspended, the controllers inside its cluster keep failing to create pods and back off, for up to about 16 minutes: after a suspension of six minutes a Deployment came back five and a half minutes after the suspension was lifted. With list and patch on those workload kinds, vBilling writes one annotation (vbilling.vcluster.com/unblocked-at) on every ReplicaSet, StatefulSet, DaemonSet and Job that waits for pods when it lifts a suspension or a pause policy, so their controllers try again at once. It changes nothing else on them, never a pod template. Without the rules nothing else changes: workloads come back when their controllers next retry, and the log says once per cluster that the access is missing.

A cluster whose API refuses vBilling (the rules above are missing, or were removed) is reported, not waited for: the source enforcement-access/<cluster ID> in GET /api/v1/sources names the cluster and the rule that grants access, and a pause of such a cluster stops its control plane at once instead of first waiting out the drain (see When a pause cannot be verified). Then turn it on:

helm upgrade vbilling deploy/helm/vbilling -n vbilling-system --reuse-values \ --set enforcement.mode=enforce --set enforcement.inCluster=true \ --set enforcement.admissionPolicy.enabled=true # the control plane cluster's policy, for shared and dedicated nodes

Holds

A tenant can be held for more than one reason. Billing webhooks own the billing hold. Operators set others through the API: operator by default, or one they name, such as abuse or support. No webhook touches those, and only an operator clears them. The tenant's state is the most severe of its holds, so a payment that clears the billing hold never lifts an operator's hold.

curl -X PUT localhost:8080/api/v1/billing-states/globex -H "Authorization: Bearer $API_TOKEN" \ -d '{"state": "suspended", "hold": "abuse", "reason": "outbound spam reported"}' # later, after the review curl -X PUT localhost:8080/api/v1/billing-states/globex -H "Authorization: Bearer $API_TOKEN" \ -d '{"state": "active", "hold": "abuse"}'

Without hold, a PUT sets the operator hold. A portal that wants a payment to lift its hold names it: "hold": "billing". Setting a hold to active removes it. GET /api/v1/billing-states lists each tenant's state with its holds; for a hold other than billing, the reason starts with the hold's name, and the in-cluster denial reads This tenant is suspended (abuse: outbound spam reported). New workloads are blocked until the hold is lifted; ...

An operator's PUT sets any state. Billing webhooks follow stricter rules, so that nothing short of a payment that leaves nothing owed releases a tenant:

  • A webhook can only raise the billing hold. Only a payment that succeeded, a paid invoice or an active subscription can clear it: Stripe's invoice.paid and invoice.payment_succeeded, a subscription event whose status is active or trialing, and Metronome's payment_gate.payment_status with paid. A declined card on a suspended account, or an alert that arrives after the one that paused a prepaid tenant, changes nothing.
  • A positive webhook never lowers the hold by itself. vBilling keeps no record of what raised it: it reads the billing platforms again, the paying one for the paying customer and any other for the tenant's own customer there, and clears the hold only when none shows anything owed. Stripe owes nothing when no subscription of the customer is past due, unpaid or incomplete, whoever created it, no open invoice is past its due date or has a failed payment, and no invoice is uncollectible. Metronome owes nothing when no threshold notification of the customer that a rule maps above warning is in alarm or still evaluating. Anything still owed keeps the hold as it is, so paying a small invoice never lifts a suspension while an older invoice is open, and a Stripe payment never resumes a tenant whose Metronome wallet is still empty. If a platform cannot be read, the webhook fails and the platform retries it: vBilling never lowers a hold on a guess.
  • The same rule holds for a billing hold an operator set with "hold": "billing", and for billing holds stored by v0.3.0. A PUT replaces the hold.
  • Webhooks apply in the order the billing platform says they happened, whatever order they arrive in: Stripe's created, and Metronome's timestamp (at the top level, or under properties for alert and payment gate notifications). A Metronome notification without one is ordered by its signed X-Metronome-Date header, the time it was sent. An event older than the newest one applied to the hold is ignored, so a retried old event never undoes a newer payment, and an old payment never lifts a newer suspension.
  • Each event applies once. vBilling keeps the IDs of applied events in DATA_DIR/billing-state.json for 30 days, so a redelivery after a restart is still a duplicate. Billing states are written to disk, and synced, before they take effect.
  • A webhook names a billing customer. When the billing platform lists the customer's ingest aliases (Metronome), the signal applies to the tenant the customer is mapped to and to every alias that is a tenant vBilling knows (discovered from a cluster, named by the records configuration, holding a state, or sent usage under), or to all of the aliases when none is; never to one alias alone. One customer's prepaid commit can fund several tenants, so an empty wallet pauses each of them. If the aliases cannot be read, the webhook fails and the billing platform retries it.
✓
In a live run with ENFORCEMENT_IN_CLUSTER on, kubectl run inside a suspended tenant's cluster was denied by vbilling-suspended with the reason. A payment cleared the billing hold, and an abuse hold kept the tenant blocked until the operator lifted it.

Pausing a tenant

Suspension stops growth: running workloads keep running and keep billing. A prepaid wallet that reaches zero needs more: a hard stop the tenant cannot undo, and a state in which usage stops accruing. That is the paused state. Set it through the API, or map a billing event to it with ENFORCEMENT_RULES:

# a Metronome low-balance alert pauses the tenant; a successful top-up resumes it ENFORCEMENT_RULES="alerts.low_remaining_commit_balance_reached=paused" # or by hand: "hold": "billing" lets a top-up that leaves nothing owed resume it; without it, only another PUT does curl -X PUT localhost:8080/api/v1/billing-states/acme -H "Authorization: Bearer $API_TOKEN" \ -d '{"state": "paused", "hold": "billing", "reason": "prepaid balance reached zero"}'

In enforce mode, vBilling then pauses each of the tenant's clusters, in this order:

  1. It marks the cluster paused with vbilling.vcluster.com/paused-by, vbilling.vcluster.com/paused-at and vbilling.vcluster.com/paused-replicas. The marks say who paused the cluster and how to resume it; they never stop billing.
  2. Inside a cluster with its own nodes (with ENFORCEMENT_IN_CLUSTER=true), it first installs the pause admission policy, vbilling-paused, which denies every new pod in every namespace, kube-system included, and every update that removes a pod's scheduling gates. Only the kubelet's mirror pods get through: a static pod runs from a file on its node whatever the API says, and its mirror pod is how vBilling sees it. Then it installs the suspension policy, taints each of the cluster's own nodes vbilling.vcluster.com/paused=true:NoSchedule, and deletes every pod on them, whatever the pod tolerates, except node infrastructure. Each pod gets at most 30 seconds of termination grace; whatever is left at the drain timeout (2 minutes) is deleted without any. A pod counts as running until it is gone, terminating or not. Node infrastructure is a DaemonSet pod in a PAUSE_KEEP_NAMESPACES namespace (kube-system, gpu-operator, the CNI's) that requests no GPU or other extended resource and sets no GPU visibility variable (NVIDIA_VISIBLE_DEVICES, CUDA_VISIBLE_DEVICES, AMD_VISIBLE_DEVICES, ROCR_VISIBLE_DEVICES, HIP_VISIBLE_DEVICES) to anything but empty, void or none: the GPU driver and the CNI keep running, so the cluster serves again soon after it resumes. If the cluster's API refuses a call (installing the pause policy included) or cannot be reached, vBilling keeps the control plane up and tries again within 15 seconds, because once stopped it could no longer stop the pods on the cluster's own nodes; the cluster runs and bills meanwhile. After 2 minutes of failures it stops the control plane anyway. Nodes of the control plane cluster are never tainted.
  3. It saves the cluster's nodes, volumes and load balancers under DATA_DIR/paused-inventory. While the control plane is stopped its API is down and nothing in it can change, so vBilling meters the paused cluster from that copy.
  4. It scales the control plane to zero and deletes the pods the cluster synced to the control plane cluster, as vcluster pause does, with the same grace period cap.
  5. It verifies that nothing of the cluster runs any more: its synced pods are gone, its control plane is down, and its own nodes, found empty with the pause policy in place once the drain is done, stay so until the cluster's API goes away. They are checked again, with the pause policy, while the control plane stops, and the pause is verified only when the API is then seen to go away with the control plane: the connection is refused or reset, ends early, or the proxy in front of it answers 503. Through vCluster Platform's proxy (TENANT_SOURCE=platform) a stopped cluster's API never refuses: the proxy holds each call until it times out, so a call that gets no answer (a timeout, or a 502 or 504 from the proxy) counts too, once the control plane cluster shows no pod of the cluster's control plane left, not even a terminating one. A check that finds a workload or a changed pause policy, or that the API refuses (Forbidden, Unauthorized, TooManyRequests: a tenant's admins can revoke vBilling's access inside its cluster, or throttle it), leaves the pause unverified. Checks that time out or fail in a way that says nothing leave it unverified for now, and a later pass (every 15 seconds) completes it once it sees the API gone with the control plane down. Checks that end while the API still answers, because the control plane takes longer than the drain timeout to stop, show nothing of what ran afterwards: a later pass must find the own nodes empty itself before the API going away counts. Capacity stops billing from the second the checks succeed, and only then: when a later pass completes them, the time before keeps billing.

vBilling does not set vcluster pause's own loft.sh/paused annotation, on purpose: vcluster connect silently resumes a cluster that carries it. A cluster vBilling paused is only scaled down, so vcluster connect refuses it (scaled down to zero replicas) and an operator who connects to debug cannot lift a billing pause by accident.

The pause runs in the background, so the API call or webhook returns at once. GET /api/v1/billing-states shows each cluster's progress under pauses (pausing, paused, resuming, running, with any error), whether the pause is verified or why it is not (unverified), and when capacity stopped billing, to the second, under pause_spans. Every step is idempotent, so repeated pauses and resumes are safe to retry.

When a pause cannot be verified

Capacity stops billing only once vBilling's own checks found nothing of the cluster running. A pause cannot be verified when vBilling has no write access to the cluster's API (ENFORCEMENT_IN_CLUSTER off) and the cluster has nodes of its own that are billed, when the cluster's API refuses a check, when it went away with no check watching it after it last answered, when the pause policy was removed or changed, when pods survive the drain or start while the control plane stops, or when synced pods do not go. vBilling still stops the control plane, a hard stop the tenant cannot undo, but capacity keeps billing: the cluster's own nodes and every workload left on them (with PRIVATE_NODE_BILLING=usage, the workloads as last read), as if it ran. The pause status shows verified: false and the reason. A later pass that can verify the pause (synced pods that finally went, or the API seen gone after checks that timed out) stops capacity billing from then. Such a pause is the failing source pause/<cluster ID> in GET /api/v1/sources, with the reason, for as long as it lasts, so the shipped alert VBillingSourceUnhealthy fires for it; pauses[].unverified in GET /api/v1/billing-states says the same.

The checks see what the cluster's API shows, and nothing else. On a cluster's own nodes they cannot see processes started outside Kubernetes: a privileged pod that ran before the pause can start host processes, or containers the kubelet does not manage, and those survive every pod deletion. A pod started in the last second before the API stopped, by an admin who removed the pause policy and put it back within that second, would not be seen either. When checks time out while the control plane stops, that last moment stretches until the API is seen gone. The pause policy also denies removing a pod's scheduling gates, so a gated pod made before the pause cannot start during it, but it does not cover binding: a pod made before the pause that still waits for a node can be bound to one through pods/binding in that last moment, by an admin, or by the cluster's scheduler when the pod tolerates the pause taint. And a cluster whose API server runs without the ValidatingAdmissionPolicy admission plugin enforces no pause policy at all: only the checks stand, until the API is gone. Only powering the nodes off, or reimaging them, stops all of that; see Limits for tenants you do not trust.

v0.3.0 opened a pause span when it marked the cluster, before its drain and whatever the drain left running. Such a span carries no verification mark, so after the upgrade it stops no capacity billing: the first pause pass ends it and verifies the pause again. Until a pass verifies it, the pause status reads an older version opened this pause, followed by the reason.

A cluster whose API refuses vBilling's in-cluster steps (forbidden or unauthorized: the access rule is missing, for example on a cluster created while its tenant is paused) is not waited for. In the same pass vBilling saves what it can, scales the control plane to zero, and reports the pause as unverified with the reason, or as verified when metering knows the cluster has no nodes of its own. Up to v0.3.2 such a cluster ran for about two and a half minutes first, the drain timeout plus the checks around it. Give every cluster the access rule from its template, so its own nodes can be drained and the pause verified.

The tenant cannot restart it

A paused cluster has no control plane, so the tenant has nothing to connect to. vBilling checks the clusters of paused tenants every 15 seconds: if anything brings one back while its tenant is still paused (an operator scaling the StatefulSet, a vCluster Platform wake-up), or the tenant creates a new one, vBilling pauses it again. A cluster that runs again bills from the last time vBilling saw it stopped, until its new pause is verified. Holds work as above: a payment clears the billing hold once nothing is owed, but never an operator's pause (operator, abuse, ...).

What bills while paused

UsageWhile paused
CPU, memory and GPUs of workloadsBilled until the pause is verified, which is once they are gone: a workload's termination grace period, at most 30 seconds, is billed. If the pause cannot be verified, they keep billing.
Control plane hoursStop when the control plane's last replica is gone, which is some seconds before the pause is verified, and start again when a replica is ready after a resume. A pause made outside vBilling (vcluster pause, an operator, vCluster Platform's sleep mode) stops them the same way, to about a second. With PAUSE_KEEP_BILLING=control_plane they also bill for the paused time.
Dedicated and private nodesStop when the pause is verified; if it cannot be, they keep billing. The nodes stay joined and idle; returning them to a pool is the node provider's job (vMetal, Auto Nodes), and they are not billed either way.
Volumes and load balancersKeep billing: they still hold storage and addresses, and the tenant gets them back on resume.
Per-request records and Prometheus countersBilled as reported. A gateway should refuse a paused tenant's requests.

PAUSE_KEEP_BILLING (Helm enforcement.pause.keepBilling) lists what keeps billing once a pause is verified: any of storage, load_balancers, nodes, control_plane, workloads, or none. The default is storage,load_balancers.

A cluster counts as paused only while its control plane is scaled to zero with no replica ready; annotations never pause billing. A pause vBilling did not make (vcluster pause, an operator, vCluster Platform's sleep mode, or a control plane scaled to zero by whoever writes vcluster.yaml) stops only the control plane's hours, from the time vBilling sees it. vBilling cannot verify that the cluster's workloads stopped: a stopped control plane leaves the kubelets on the cluster's own nodes running theirs. So its nodes and workloads keep billing, the last known workloads with PRIVATE_NODE_BILLING=usage. vBilling never resumes a pause it did not make.

Resume

Clearing the hold resumes the cluster: a PUT with "state": "active" for the hold that paused it (without hold, the operator hold), or a payment webhook that clears the billing hold once nothing is owed. vBilling scales the control plane back to its replica count, and once the cluster's API answers it removes the pause policy, lifts the taint and removes the suspension policy. Workloads come back on their own: on shared nodes the cluster still has every pod and syncs them again; on its own nodes, Deployments, StatefulSets and Jobs recreate theirs. Bare pods deleted by the drain do not come back.

A hold lifted while the pause is still running ends the pause where it is. vBilling checks the tenant's state before every step that stops something (each node taint, each round of deletions, the control plane's scale-down) and, when the tenant is no longer paused, stops and undoes what that pass did: the taint and the pause policy go, and the control plane is scaled back only if it had been stopped. Pods that were already told to stop cannot be saved; their controllers recreate them.

A pause lowered to a suspension (the billing hold is paid while an abuse hold at suspended remains) first restores the cluster and then suspends it: suspended means that what runs keeps running and nothing new starts, and after a pause nothing runs. vBilling resumes the cluster, holds the suspension back until the workloads it stopped have their pods again, and then blocks new pods. That takes as long as the workloads need, at most 2 minutes after the cluster's API answers again (12 minutes after the resume if it never does); pauses[].restoring_until in GET /api/v1/billing-states shows the limit. During that time the cluster accepts any pod. Only a pause recorded by vBilling starts a restore, once per pause: no annotation or label on the cluster can start or extend one.

Limits

  • vBilling never deletes a cluster. For a grace period followed by deletion, use the since of the tenant's state and pause_spans from GET /api/v1/billing-states in your own automation.
  • A cluster vBilling reaches only through its own API (vCluster Standalone, TENANT_CLUSTERS_FILE) has no control plane in the control plane cluster to stop. Its pause is the pause policy plus drained nodes, applied and checked again every 15 seconds. A cluster admin inside it can undo that between two checks: capacity stops billing only between checks that found nothing running and the pause policy in place, and a check that cannot drain the cluster stops none.
  • A workload whose pods tolerate the pause taint is deleted like any other. If its controller schedules it again before the control plane stops, the pause is not verified and the cluster keeps billing.
  • Kept DaemonSets keep running while paused, and a tenant's admins are cluster admins inside its clusters: they can run a privileged container in a kept namespace and reach a node's GPUs without requesting them. PAUSE_KEEP_NAMESPACES=none stops kept DaemonSets, but not what a privileged pod started outside Kubernetes before the pause (see When a pause cannot be verified). For tenants you do not trust on nodes of their own, add nodes to PAUSE_KEEP_BILLING, so their nodes keep billing while paused, and have the node provider (vMetal, Auto Nodes) power paused nodes off or release them.
  • vBilling keeps a cluster's pause state under its ID, vcluster-<namespace>-<name>, which two clusters can share (namespace a-b with cluster c, and namespace a with cluster b-c). Pausing such clusters never stops their billing, and vBilling logs a warning: rename one of them.
  • Resume time is the cluster's start-up time plus each workload's own. Keep model weights on a volume or a node-local cache rather than an emptyDir, or an inference server downloads them again on every resume.
  • With vCluster Platform, its sleep mode and wake-up are separate from vBilling's pause. A Platform wake-up of a paused cluster is paused again within 15 seconds.

Pausing needs more access than suspending. In the control plane cluster, the chart grants delete on pods in enforce mode. Inside clusters with their own nodes, add to vbilling-enforcer:

- apiGroups: [""] resources: [nodes] verbs: [get, update] # add and lift the pause taint - apiGroups: [""] resources: [pods] verbs: [delete] # stop workloads on the paused nodes

Whole GPUs, however they are carved

Dedicated and private nodes are billed for physical GPUs. MIG slices (mixed or single strategy, GKE GPU partitions) and time-slicing replicas (NVIDIA or GKE time-sharing) are converted back: a node exposing 56 MIG slices of 1g.10gb, or 32 time-sliced devices with 4 replicas, bills 8 GPUs. GPUs offered only through DRA ResourceSlices count too. On a cluster's own nodes, time-slicing replicas count only when GPU Feature Discovery's GPU count adds up with them, and a node never bills fewer GPUs than it had (A node bills as vBilling first saw it).

GPU model detection

The first label present wins: nvidia.com/gpu.product, nvidia.com/gpu.machine, amd.com/gpu.product-name, cloud.google.com/gke-accelerator, k8s.amazonaws.com/accelerator, accelerator. Spaces are replaced with dashes (NVIDIA H100 80GB HBM3 becomes NVIDIA-H100-80GB-HBM3). The -SHARED and -MIG-<profile> suffixes GPU Feature Discovery adds are removed, so the SKU is always the base GPU; DRA devices use their productName attribute. A node whose labels name no model has the GPU model unknown; its SKU still comes from the SKU label or the instance type, and only without both is it <n>xunknown.
