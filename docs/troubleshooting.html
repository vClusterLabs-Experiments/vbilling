Troubleshooting

Common issues you might encounter when running vBilling, with step-by-step solutions.

No Tenant Clusters Discovered

"[controller] window ...: 0 events for 0 tenant cluster(s)"

Symptoms

vBilling starts but meters no clusters. No customers or events appear in your billing platform, and every window logs [controller] window ...: 0 events for 0 tenant cluster(s).

Cause

vBilling discovers clusters by scanning for StatefulSets and Deployments with the label app=vcluster. If your clusters use different labels, or if RBAC prevents listing these resources, discovery will find nothing.

Fix Check that clusters have the expected labels

# List StatefulSets with the vcluster label kubectl get statefulsets --all-namespaces -l app=vcluster # Should list your tenant clusters, e.g.: # NAMESPACE NAME READY AGE # vcluster-team-alpha my-vcluster 1/1 3d # Also check Deployments (some vCluster configs use Deployments) kubectl get deployments --all-namespaces -l app=vcluster

Fix Check RBAC permissions

The vBilling ServiceAccount needs permission to list StatefulSets, Deployments, Pods, Services, PVCs, Nodes, and PodMetrics across all namespaces (or the specific namespaces configured in WATCH_NAMESPACES).

# Verify the ServiceAccount can list StatefulSets kubectl auth can-i list statefulsets --as=system:serviceaccount:vbilling-system:vbilling --all-namespaces # Should return: yes # If RBAC is the issue, check the ClusterRole kubectl get clusterrolebinding | grep vbilling

Fix Check vCluster Platform enrichment (optional)

Workloads are the source of truth: vBilling finds clusters by their StatefulSets and Deployments. With vCluster Platform, it also reads VirtualClusterInstance resources (management.loft.sh/v1) to add the project and display name, and logs:

[discovery] enriched 3 tenant cluster(s) from vCluster Platform

Without vCluster Platform this line never appears. That is expected: discovery does not depend on it.

Fix Check namespace filter

# If WATCH_NAMESPACES is set, only those namespaces are scanned # Make sure your vCluster namespace is included kubectl get configmap -n vbilling-system -o yaml | grep WATCH_NAMESPACES

Metrics Unavailable

"[metrics] warning: cannot get pod metrics for <namespace>"

Symptoms

vBilling discovers clusters but CPU and memory metrics are always zero. The log shows warnings about failing to get pod metrics.

Cause

vBilling requires the Kubernetes metrics-server to be installed and functioning. Without it, the PodMetrics API is unavailable.

Fix Install metrics-server

# Check if metrics-server is running kubectl get pods -n kube-system -l k8s-app=metrics-server # If not installed, install it: kubectl apply -f https://github.com/kubernetes-sigs/metrics-server/releases/latest/download/components.yaml # For development clusters (minikube, kind) with self-signed certs: kubectl apply -f https://github.com/kubernetes-sigs/metrics-server/releases/latest/download/components.yaml kubectl patch deployment metrics-server -n kube-system \ --type=json \ -p '[{"op":"add","path":"/spec/template/spec/containers/0/args/-","value":"--kubelet-insecure-tls"}]'

Fix Verify the metrics API works

# Test the metrics API directly kubectl top pods -n <vcluster-namespace> # Should show CPU and memory usage: # NAME CPU(cores) MEMORY(bytes) # my-vcluster-0 25m 128Mi # If this fails, metrics-server is not working

GPU Type Empty

GPU events show gpu_type "unknown"

Symptoms

GPU hours are being reported, but the gpu_type property in Lago events shows "unknown" instead of the actual GPU model.

Cause

vBilling reads the GPU type from node labels. If none of the expected labels are present, it falls back to "unknown".

Fix Check which GPU labels exist on your nodes

# Check all GPU-related labels on your GPU nodes kubectl get nodes -l nvidia.com/gpu -o jsonpath='{range .items[*]}{.metadata.name}{"\t"}{.metadata.labels}{"\n"}{end}' # vBilling checks these labels in order: # 1. nvidia.com/gpu.product (NVIDIA GPU Operator) # 2. nvidia.com/gpu.machine (alternative) # 3. amd.com/gpu.product-name (AMD GPU Operator) # 4. cloud.google.com/gke-accelerator (GKE specific) # 5. k8s.amazonaws.com/accelerator (EKS) # 6. accelerator (generic) # The first label present wins. The instance type is not a fallback: # a node with none of these labels has the GPU type "unknown".

Fix Install the NVIDIA GPU Operator

The easiest way to get GPU labels is to install the NVIDIA GPU Operator, which automatically labels nodes with nvidia.com/gpu.product:

helm repo add nvidia https://helm.ngc.nvidia.com/nvidia helm install gpu-operator nvidia/gpu-operator --namespace gpu-operator --create-namespace

Fix Manually label your GPU nodes

# If you know the GPU model, label manually kubectl label node <gpu-node> nvidia.com/gpu.product="NVIDIA-A100-SXM4-80GB"

Dedicated Nodes Not Detected

Dedicated nodes labeled but not appearing in billing events

Symptoms

You have labeled control plane cluster nodes with vcluster.loft.sh/managed-by but vBilling does not bill them as dedicated nodes. No vcluster_private_node_hours events with billing_mode=dedicated_node appear. (For nodes that join a cluster through vCluster Private Nodes, see Private Nodes Not Metered.)

Cause

The most common cause is a label value mismatch between the node label and the vCluster namespace name. vBilling tries multiple label values, but they must correspond to the namespace.

Fix Understand the label matching logic

For a cluster in namespace vcluster-team-gpu, vBilling searches for nodes with these selectors:

# Selector 1: full namespace name vcluster.loft.sh/managed-by=vcluster-team-gpu vcluster.loft.sh/cluster=vcluster-team-gpu # Selector 2: namespace with "vcluster-" prefix stripped vcluster.loft.sh/managed-by=team-gpu vcluster.loft.sh/cluster=team-gpu # Selector 3: custom VCLUSTER_NODE_LABEL (if set)

Fix Verify the node labels

# Check what value your nodes are actually labeled with kubectl get nodes -l vcluster.loft.sh/managed-by -o custom-columns="NAME:.metadata.name,MANAGED-BY:.metadata.labels.vcluster\.loft\.sh/managed-by" # NAME MANAGED-BY # gpu-node-001 team-gpu # Make sure the label value matches one of the selectors above # For namespace "vcluster-team-gpu", either of these will work: kubectl label node gpu-node-001 vcluster.loft.sh/managed-by=vcluster-team-gpu # OR kubectl label node gpu-node-001 vcluster.loft.sh/managed-by=team-gpu

Fix Test the exact selector vBilling uses

# Simulate what vBilling does internally: kubectl get nodes -l vcluster.loft.sh/managed-by=team-gpu # If this returns your nodes, vBilling will find them # If empty, the label value doesn't match

Private Nodes Not Metered

Nodes joined with vCluster Private Nodes produce no events

Symptoms

A cluster has private nodes, but no vcluster_private_node_hours events with billing_mode=private_node appear, or GET /api/v1/status lists the cluster under failed tenant APIs.

Cause

vBilling reads private nodes through the cluster's own API, with the kubeconfig in the Secret vbilling-kubeconfig in the cluster's namespace. Without that Secret, or with the cluster's control plane down, there is nothing to read.

Fix Export the read-only kubeconfig

Add exportKubeConfig.additionalSecrets with the vbilling-reader service account to the cluster's vcluster.yaml (see Private Nodes), then check the Secret exists:

kubectl -n <tenant-namespace> get secret vbilling-kubeconfig

Fix The cluster's control plane exits

An error naming the feature 'Private Nodes' (vcp-distro-private-nodes) as not available means the cluster has no license: register it with vCluster Platform (vcluster platform add vcluster <name> -n <namespace>). denied by loft access key scope means the CLI's access key is scoped and cannot register clusters; log in with a key that can. vCluster 0.36.2 and later need Platform 4.11.3 or later.

Fix GPU-hours missing right after a node reboot

While a driver container rebuilds (after a reboot, a spot restart or a MIG change), a Ready node advertises no GPUs. vBilling bills the node and records its installed GPUs (GPU Feature Discovery's nvidia.com/gpu.count) as vcluster_gpu_downtime_hours with the reason "GPUs installed but not allocatable" until they are allocatable again.

Suspended Tenants on Private Nodes Can Still Start Pods

A suspended tenant's cluster with its own nodes still accepts new pods

Symptoms

GET /api/v1/billing-states shows the tenant as suspended, and its namespace in the control plane cluster carries vbilling.vcluster.com/suspended=true. Yet kubectl run inside one of its clusters with Private Nodes, Auto Nodes or Standalone still starts a pod.

Cause

The chart's admission policy runs in the control plane cluster, so it only sees pods synced there: clusters on shared or dedicated nodes. A cluster with its own nodes schedules its pods inside itself.

Fix Turn on enforcement inside the cluster

helm upgrade vbilling deploy/helm/vbilling -n vbilling-system --reuse-values \ --set enforcement.mode=enforce --set enforcement.inCluster=true

vBilling then installs a ValidatingAdmissionPolicy and binding named vbilling-suspended inside each of the tenant's clusters, through the cluster's own API. It needs enforcement.inCluster=true and write access for those two objects inside the cluster: the extra rules for the vbilling-reader role in Billing-state enforcement inside the cluster, reached through the cluster's vbilling-kubeconfig Secret or, in Platform mode, through the role the template's access rule binds. Nothing grants them automatically: a cluster created from a template without those rules is metered but not enforced inside. There is no tenantAPI.enabled value any more; clusters with their own nodes are always read through their API.

Fix Let the exported service account manage the policy

The read-only service account vCluster exports for vBilling cannot write admission policies. Grant it that with the ClusterRole and binding in Billing-state enforcement inside the cluster. Until then, the state change reports an error like:

vcluster-globex-private-a100 (inside the cluster): read admission policy: validatingadmissionpolicies.admissionregistration.k8s.io "vbilling-suspended" is forbidden: ...

Fix Apply the state again

vBilling installs the policy when a tenant's state changes and re-applies every state every two minutes, so after fixing access the cluster converges on its own. To apply it right away, send the state again:

curl -H "Authorization: Bearer $VBILLING_TOKEN" -X PUT localhost:8080/api/v1/billing-states/globex -H "Authorization: Bearer $API_TOKEN" \ -d '{"state": "suspended", "reason": "invoice unpaid"}' # inside the cluster kubectl get validatingadmissionpolicy/vbilling-suspended validatingadmissionpolicybinding/vbilling-suspended

New pods outside kube-system are then denied with the reason (no label exempts a namespace). Running pods keep running.

GPU Utilization or Energy Missing

No vcluster_gpu_utilization events, or a DCGM metric reads zero or too high

Cause

DCGM behaves differently from what a query might assume:

  • For GPUs in MIG mode DCGM reports no DCGM_FI_DEV_GPU_UTIL. The default query falls back to each instance's DCGM_FI_PROF_GR_ENGINE_ACTIVE; a custom GPU_UTIL_QUERY needs the same fallback.
  • Device-level fields (power, energy, framebuffer) repeat on every MIG instance: summing them bills the GPU once per slice. Keep one series per GPU with max by (modelName, UUID, ...) first.
  • The exporter refreshes every 30 seconds by default (DCGM_EXPORTER_INTERVAL), so increase() over a 30 second window can read zero. Integrate a gauge instead: avg_over_time(...[{{window}}]) * {{window_seconds}}.
  • DCGM on private nodes runs inside the cluster. Ship it to your Prometheus with an agent that adds an external label naming the cluster (vcluster, see PROMETHEUS_SOURCE_LABEL). The default utilization queries then select those series, and your own queries can use {{selector}}.

The GKE example has working queries for all four cases.

A Prometheus Metric Returns Nothing

"[health] prometheus/<metric>/<cluster> returned no data"

Symptoms

A metric from prometheus.metrics, or egress, has no events for a cluster. The dashboard's Usage sources panel shows the source as empty, and the log says:

[health] prometheus/inference_output_tokens/vcluster-globex-private-a100 returned no data (1 in a row): no series for vcluster-globex-private-a100 (own nodes, selected by vcluster label) (hint: the selector matched nothing with {{matchers}} = vcluster="private-a100". ...)

Cause

  • The query uses {{namespace}}. That is the cluster's namespace on the control plane cluster, and it matches only series scraped there, from clusters on shared or dedicated nodes. A cluster with its own nodes has no pods in that namespace.
  • The cluster runs on its own nodes, but its series do not carry vcluster="<cluster name>": the Prometheus agent that remote writes them has no such external label, or uses another name.
  • vBilling cannot read the cluster's own API, so it does not know the cluster has its own nodes and selects it by namespace. The message then says shared nodes, selected by namespace.
  • The series has no sample in the window or in the 10 minutes before it: it is scraped less often than that, or it stopped.

Fix Read what vBilling tried

curl -H "Authorization: Bearer $VBILLING_TOKEN" -s 'localhost:8080/api/v1/sources?kind=prometheus' \ | jq '.sources[] | select(.status != "ok") | {name, status, message, hint, last_success, last_error_message}'

message says how the cluster was scoped: its own Prometheus, the vCluster Platform labels, matchers from the annotation, the source label for its own nodes, or the namespace for shared nodes. hint says what to change. A failing source has the error in last_error_message, for example an HTTP 401 from Prometheus. Run the selector from the message in Prometheus yourself, such as vllm:generation_tokens_total{vcluster="private-a100"}, to see what it matches.

Fix Use {{selector}}

# matches only clusters on shared or dedicated nodes counter: vllm:generation_tokens_total{namespace="{{namespace}}"} # matches every cluster, whatever its tenancy model counter: vllm:generation_tokens_total{{selector}} # your own matchers as well counter: vllm:generation_tokens_total{model_name="llama-3.1-70b",{{matchers}}}

Fix Label the cluster's series

Give the cluster's Prometheus agent the external label vcluster: <cluster name> (see Prometheus for clusters with their own nodes). If the label value differs from the cluster's name, set vbilling.vcluster.com/prometheus-source on the cluster. If the series carry other labels, set vbilling.vcluster.com/prometheus-matchers. If the cluster has a Prometheus of its own, point vbilling.vcluster.com/prometheus-url at it.

Fix Scrape more often

vBilling looks 10 minutes back for a counter's starting sample: scrape billed series more often than that, including any remote-write delay. A counter that was out of reach keeps its last sample, so the usage is billed once a sample is found again.

Token Counts Have Decimals

A window shows 1199.976 tokens

Symptoms

Token quantities have decimals, the dashboard marks the metric with ≈, and the windows do not add up to what the engine's counter shows.

Cause

The metric is a query: with increase() or rate(). They extrapolate from the samples inside a window to its edges, so the result is an estimate: every event carries estimate: true, and GET /api/v1/catalog reports accuracy: estimate. In a live run, increase() on a counter that grew by 20,500 tokens over 17 windows came to 20,700.13, and a partial window read 921.8 tokens where the counter grew by 800.

Fix Bill the counter itself

# before: an estimate query: sum by (model_name) (increase(vllm:generation_tokens_total{namespace="{{namespace}}"}[{{window}}])) # after: exact counter: vllm:generation_tokens_total{{selector}} dimensions: [model_name] skuLabel: model_name

A counter takes a plain series selector: no functions, no range. vBilling reads the raw samples and sums the series per dimension itself. Windows committed before the change keep their estimates; from the next window on, each window is exact, and the counter's earlier history is not billed again. See How counters are billed.

Per-Request Usage Is Undercounted

"same tenant, metric, window and dimensions as event 0 and no id"

Symptoms

A gateway posts one event per request to POST /api/v1/events, without an id, and billed usage is lower than the gateway's own logs. Responses reject events with same tenant, metric, window and dimensions as event 0 and no id: ..., or warn that 3 event(s) without an id matched usage already in the ledger and were not counted again.

Cause

POST /api/v1/events takes window totals. An event without an id gets one derived from its tenant, metric, window and dimensions, so two requests in the same minute look like one event sent twice. v0.2 dropped the second one silently; v0.3 rejects it within a request and warns across requests.

Fix Send records instead

Post each request with its request ID to POST /api/v1/records (for LiteLLM, ?format=litellm). vBilling sums the records per window and drops only real retries. See Per-request records.

Fix Or send real window totals

Sum the requests per tenant, metric and window yourself, and send one event per window with a stable id.

Records Billed to an Unknown Tenant

"billed to tenants vBilling does not know (...)"

Symptoms

POST /api/v1/records answers with unknown_tenants and a warning such as billed to tenants vBilling does not know (e2f1c0de-7b1a-4c55-9a7e-2d4f8b3c6a10); map gateway identities with the vbilling.vcluster.com/aliases annotation or the format's tenantMap. Source health shows records/litellm/unknown-tenants as empty, and a customer with that ID appears in your billing platform.

Cause

The record's tenant value is neither a tenant ID vBilling knows nor an alias of one. LiteLLM sends the team ID of the virtual key, a generated UUID unless the team was created with a team_id. A request whose key has no team is refused: fields the client sends never decide who pays. By default records for an unknown team are accepted and billed to that raw ID.

Fix Map the identity to the tenant

kubectl annotate namespace globex --overwrite \ vbilling.vcluster.com/aliases=e2f1c0de-7b1a-4c55-9a7e-2d4f8b3c6a10

Set it on the tenant's cluster or its namespace in the control plane cluster; several identities are comma-separated. vBilling reads it at the next discovery, within 30 seconds. A custom format can map identities with tenantMap instead. A gateway that serves one tenant can use a token bound to it in INGEST_TOKENS, which wins over the payload.

Fix Refuse instead of accept

With RECORDS_UNKNOWN_TENANTS=reject (Helm records.unknownTenants=reject), such records are refused and listed in the response's rejected with the reason tenant, and vbilling_records_rejected_total{client,reason} counts them (a client that never had a push accepted counts under client="_unaccepted"). The same setting refuses window totals sent to POST /api/v1/events for a tenant vBilling does not know. An emitter that does not read the response loses them, so map identities first.

Records already accepted keep the tenant they were stored with: the ledger is append-only. Settle that usage in the billing platform.

Pushed Usage Is Refused

"is measured by vBilling itself", "is not a cluster vBilling knows for tenant", "older than ... the oldest usage destination metronome accepts"

Symptoms

POST /api/v1/events or POST /api/v1/records lists items under rejected with a reason, or answers 400 when nothing in the request was stored. vbilling_ingest_events_rejected_total{client,reason} and vbilling_records_rejected_total{client,reason} count them.

Cause and fix, by reason

  • reserved_metric: the metric is one vBilling measures itself (GPU, CPU, memory, node, control plane, storage, load balancer or egress usage, or a metric read from Prometheus), or one that only records may write. Push under a metric code of your own, declared in metering.customMetrics. An operator's correction to measured usage goes to POST /api/v1/events?operator_adjustment=true with the API token.
  • cluster: tenant_cluster names a cluster that is not this tenant's, that vBilling never saw, or that did not exist during the usage's window (a cluster is known while it runs and for 7 days after its last metered window). Name the cluster by its ID, as in the tenant_cluster of its metered usage, or leave it out to bill the tenant without a cluster.
  • tenant: with RECORDS_UNKNOWN_TENANTS=reject, the tenant is not one vBilling knows. See Records billed to an unknown tenant.
  • too_old: the window is older than the oldest usage a configured destination accepts (33 days 23 hours with Metronome). Such usage would be acknowledged and then dead-lettered, so it is refused here; bill it in the billing platform.

A 503 with Retry-After is not a refusal: vBilling is starting and has not discovered tenants or read its ledger yet. Retry.

The Ledger Mirror Is Failing, Behind or Not Kept

"the mirror is 42s behind the ledger", "the mirror leaves 10% of the volume to the archive and has stopped copying", "no live second copy of the ledger is kept"

Symptoms

The source ledger-mirror in GET /api/v1/sources is failing or paused, vbilling_ledger_mirror_lag_seconds grows, or the alert VBillingLedgerMirrorLagging fires. Metering and delivery go on in every case: what is at stake is the second copy of the newest records.

Cause and fix

  • The volume has no room. The mirror leaves a tenth of the archive volume to the archive and stops copying before it would take that. The message says how much it still has to copy and how much is free. Grow the archive volume; the mirror continues by itself.
  • The volume is not mounted, read-only or not writable by vBilling's user (65532 in the chart). The hint names which. The source archive-volume fails for the same reason.
  • A pass hangs. "A pass has been running for ... without writing anything" means the volume does not answer; look at the storage behind it.
  • Paused: the archive is a bucket. With LEDGER_MIRROR=auto no mirror is kept on a FUSE mount. Give the archive a disk or a file share to have one, or set persistence.archive.mirror=on for a FUSE filesystem that appends and renames in place.
  • Paused: switched off. LEDGER_MIRROR=off, or persistence.archive.mirror: off.
  • On the same filesystem as the ledger. The source is ok but says so: such a mirror protects against a damaged file, not a lost node or disk. Put the archive volume on other storage.
  • ledger-mirror-set-aside. vBilling found a mirror of another ledger, kept it unchanged under mirror-set-aside-<time> and started a new one. Restore it with vbilling ledger restore if it is the ledger to keep, otherwise delete the directory.

See The ledger mirror for what a restore brings back.

Lago Connection Failed

"HTTP 401" from Lago, or connection refused

Symptoms

vBilling logs show errors like HTTP POST /api/v1/events/batch: ... connection refused, GET /api/v1/plans/vcluster-standard: HTTP 401: ... or, at startup, [pipeline] lago: bootstrap failed (delivery paused, will retry): create billable metric "vcluster_cpu_core_hours": POST /api/v1/billable_metrics: HTTP 401: .... Each error names the Lago request and its HTTP status, followed by Lago's response body. Delivery to Lago waits and is retried; the usage stays in the ledger.

Fix Check the Lago URL

# If running in-cluster, verify the service exists kubectl get svc -n lago-system # Test connectivity from inside the cluster kubectl run test-curl --rm -it --image=curlimages/curl -- \ curl -s http://lago-api.lago-system.svc.cluster.local:3000/api/v1/billable_metrics \ -H "Authorization: Bearer $LAGO_API_KEY" # If running locally, check that Lago is running curl -s http://localhost:3000/api/v1/billable_metrics \ -H "Authorization: Bearer $LAGO_API_KEY"

Fix Check the API key

# Verify the API key is correct curl -s -o /dev/null -w "%{http_code}" \ http://localhost:3000/api/v1/billable_metrics \ -H "Authorization: Bearer $LAGO_API_KEY" # 200 = API key is valid # 401 = API key is wrong # 000 = Connection failed (Lago not running or wrong URL)

Fix Check the Kubernetes secret

# If using lago.existingSecret, verify the secret exists and has the right key kubectl get secret vbilling-lago-secret -n vbilling-system -o jsonpath='{.data.api-key}' | base64 -d

Unpriced Usage

"[pricing] <destination>: <metric> sku=<sku> (plan <plan>) is unpriced"

Symptoms

The status API warns about pricing/<destination>/...: unpriced sources, the dashboard's Price coverage tile shows unpriced series, or vbilling_unpriced_series is above 0.

Cause

A billing platform has no price for usage vBilling sends it: a new SKU, region, metric or plan reached vBilling before Finance priced it. Billing platforms bill such usage at $0 without an error, so invoices, prepaid balances and spend alerts undercount. vBilling reads each platform's pricing (Metronome rate cards, Stripe prices, Lago charges) at startup, every 10 minutes, and within seconds of a new series. It never writes a price.

Fix Add the missing price

curl -H "Authorization: Bearer $VBILLING_TOKEN" -s 'localhost:8080/api/v1/pricing?status=unpriced' | jq '.destinations[] | {destination, series: [.series[] | {plan, metric, sku, hint, held_events}]}'

Each row's hint names what to create: a rate for a product on a Metronome rate card, a metered price on a Stripe meter, or a price for a SKU in a Lago charge. Once it exists, run curl -H "Authorization: Bearer $VBILLING_TOKEN" -s -X POST localhost:8080/api/v1/pricing/check or wait for the next check; the log says is priced now and the source recovers. A billable metric with no usage yet shows with "no_usage_yet": true: price it before its first event, or price it at 0 if it is free. Statuses: priced, unpriced, zero (a price of 0, which can be intentional, so it is not a gap) and unknown (the check cannot tell, for example Metronome without METRONOME_RATE_CARD).

Holding unpriced usage (PRICE_CHECK=hold)

In hold mode, the events of an unpriced series (metric, SKU, plan, and any other dimension the platform prices on) are not sent to that destination:

  • They stay in the ledger, and are also written to DATA_DIR/held (fsynced) before the destination's cursor moves past them, so a restart loses nothing.
  • Other series, and other destinations, keep flowing. Later events of a held series are held behind the earlier ones.
  • A series is held until a check finds its price. A new series is checked before its first delivery (up to 20 seconds), so a series that is priced already never waits. While a destination has held events it is checked every minute, and once the price exists the held events ship in ledger order, before newer usage of the series. The log says released N held event(s).
  • Events ship once: destinations deduplicate on event IDs, and vBilling does not resend events a release delivered. Rejections during a release are dead-lettered like any other.
  • The tenant is created in the billing platform when its usage is held, so its subscription or contract period covers the usage.
  • If a check fails, series confirmed as priced keep flowing, and series never confirmed stay held (price not confirmed yet: last check failed). Series the check cannot decide (unknown) are not held, because nothing could release them.
  • Setting PRICE_CHECK back to warn releases what is held for a price after the next start. Metronome usage no billable metric counts stays held with warn (see Metronome). off releases everything held, and Metronome never bills usage sent before a billable metric counts it.

Held counts: held_events in GET /api/v1/pricing (per series, with held_since), in GET /api/v1/destinations, in the dashboard, and vbilling_held_events{destination}.

Usage cannot wait for its price for long. A billing platform finalizes an invoice period once the period ends plus a grace period (Metronome: 24 hours by default), and usage that reaches it after that is not invoiced for that period, priced or not. So events whose window started more than 23 hours ago are released without a price, oldest first, together with any older held events of their series; younger usage stays held. The log says WARNING: ... released N held event(s) of ... WITHOUT A PRICE, the series' source turns failing with Finance must add the price ... so it re-rates the released usage, its row in GET /api/v1/pricing shows released_unpriced_events, and vbilling_events_released_unpriced_total{destination} counts them. Add the price before the period is final, so the billing platform rates the released usage (Lago applies a new price to the usage of the open billing period when it computes it; with Metronome and Stripe, check that the period's draft invoice picks it up), and the source recovers. Usage released after its period is final is not invoiced for that period: Stripe's grace period is 1 hour by default, so usage from the last hours of a Stripe billing period can reach it too late. Price a new SKU before its usage starts. Alert on:

vbilling_unpriced_series > 0 vbilling_held_events > 0 increase(vbilling_events_released_unpriced_total[1h]) > 0

Events Sent But $0.00 in Lago

Usage events appear in Lago but invoices show $0.00

Symptoms

vBilling is successfully sending events (you can see them in the Lago UI under the customer's events tab), but the current usage and invoices all show $0.00.

Cause

When vBilling bootstraps the vcluster-standard plan, all charge amounts default to $0.00 per unit. This is by design: vBilling creates the plan structure, and the prices are yours to set. A price card (lago.priceCard) sets the amounts vBilling uses when it creates charges; see Prices as code.

Fix Configure pricing in Lago

  1. Open the Lago UI (e.g., http://localhost:80)
  2. Navigate to Plans in the left sidebar
  3. Click on vCluster Standard
  4. For each charge, click the edit icon and set a non-zero price per unit

Duplicate Subscriptions

Duplicate or missing subscriptions after controller restart

Symptoms

After restarting the vBilling controller, you see warnings about subscription creation failing, or duplicate subscriptions appear in Lago.

Cause

vBilling is designed to be idempotent on restart. When it discovers a cluster, it first probes for an existing subscription using the GetCurrentUsage API call. If the subscription already exists, Lago returns usage data and vBilling reuses the subscription. If the probe fails (404), vBilling creates a new subscription.

How it works

# vBilling's subscription detection logic: # 1. Try GetCurrentUsage(customerID, subscriptionID) # 2. If success: subscription exists, reuse it # 3. If error: subscription does not exist, create it [controller] subscription sub-vcluster-ns-name already exists, reusing # OR [controller] created subscription sub-vcluster-ns-name -> plan vcluster-standard

Fix This is normally self-healing

If you see "subscription already exists" warnings, the controller is correctly detecting and reusing existing subscriptions. No action needed.

Fix Clean up duplicates in Lago

If actual duplicates exist (multiple subscriptions for the same vCluster), you can terminate the extra ones via the Lago UI or API:

# List subscriptions for a customer curl -s http://localhost:3000/api/v1/subscriptions\?external_customer_id=vcluster-ns-name \ -H "Authorization: Bearer $LAGO_API_KEY" | jq '.subscriptions[].external_id' # Terminate a duplicate subscription curl -X DELETE http://localhost:3000/api/v1/subscriptions/<duplicate-external-id> \ -H "Authorization: Bearer $LAGO_API_KEY"

CORS Issues with Dashboard

Browser console shows CORS errors when accessing Lago UI or vBilling dashboard

Symptoms

When accessing the Lago UI or any vBilling dashboard from a browser, you see errors like: Access to fetch at 'http://localhost:3000/...' from origin 'http://localhost:8081' has been blocked by CORS policy.

Cause

The browser enforces Cross-Origin Resource Sharing (CORS) restrictions when the frontend and API are served from different origins (different ports or domains).

Fix Configure Lago CORS settings

In the Lago Docker Compose setup, ensure the LAGO_FRONT_URL environment variable matches your frontend URL:

# In lago/.env or docker-compose.yml LAGO_FRONT_URL=http://localhost LAGO_API_URL=http://localhost:3000

Fix Use a reverse proxy

For production, put both the API and frontend behind the same domain using a reverse proxy (nginx, Traefik, etc.) so CORS is not an issue.

Fix Port-forward with matching origins

# If accessing in-cluster Lago from your machine: kubectl port-forward svc/lago-front -n lago-system 80:80 & kubectl port-forward svc/lago-api -n lago-system 3000:3000 & # Then access the frontend at http://localhost

General Debugging Tips

i
Enable verbose logging: vBilling logs to stdout with the [component] prefix convention. Key prefixes to filter:
  • [controller]: metering windows, backfills and tenant changes
  • [discovery]: vCluster Platform enrichment
  • [metrics]: collection (CPU, memory, GPUs, Prometheus)
  • [tenantapi]: clusters read through their own API (Private Nodes, Standalone)
  • [pipeline]: delivery to each adapter, retries and dead letters
  • [health]: usage sources that fail, return nothing, diverge or recover
  • [records]: late per-request records billed as adjustments
  • [stripe], [metronome], [lago], [bootstrap], [noop]: the billing adapters
  • [enforcement], [api]: billing states, webhooks and the HTTP API

Useful commands

# Stream vBilling logs kubectl logs -n vbilling-system -l app=vbilling -f # Filter for errors only kubectl logs -n vbilling-system -l app=vbilling | grep -i "error\|warning\|fatal" # Check vBilling pod status kubectl get pods -n vbilling-system # Describe pod for events and conditions kubectl describe pod -n vbilling-system -l app=vbilling # Check cluster-wide vCluster StatefulSets kubectl get statefulsets --all-namespaces -l app=vcluster # Check Lago health curl -s http://localhost:3000/api/v1/billable_metrics \ -H "Authorization: Bearer $LAGO_API_KEY" | jq '.billable_metrics | length' # Should return: 11 (9 built-in metrics, inference_input_tokens and inference_output_tokens), plus one per custom metric # Check which customers exist in Lago curl -s http://localhost:3000/api/v1/customers \ -H "Authorization: Bearer $LAGO_API_KEY" | jq '.customers[] | {external_id, name}'
