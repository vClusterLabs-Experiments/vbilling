How Metering Works

Every quantity vBilling bills comes from one of three places: the Kubernetes API, per-request records from an AI gateway, or Prometheus counters you choose. This page shows where each number comes from, what you install for it, which numbers are exact and which are estimates, and what has been checked on real hardware.

Three sources

Always on

Kubernetes API

Pods, nodes, volumes, LoadBalancer Services and node Leases, read from the control plane cluster and, for clusters with their own nodes, from each cluster's API. GPU-hours, node-hours, CPU, memory, storage, load balancers and control plane hours all come from here.

Install: nothing. vBilling reads the API with read-only RBAC.

For tokens

AI gateway records

One record per request with its input and output tokens, pushed by the gateway (POST /api/v1/records) and pulled back from the gateway's own logs to fill gaps. Records are deduplicated by request ID and summed per window.

Install: a gateway in front of your models. LiteLLM works out of the box; any gateway that logs requests works through a pull mapping.

Optional

Prometheus

Counters you declare, read sample by sample: network egress by default, and anything else, such as an inference engine's own token counters. Also the DCGM exporter's GPU utilization, which is informational only.

Install: a Prometheus that scrapes the exporters (cAdvisor for egress, your engine, DCGM).

ⓘ
GPU-hours are allocated time, not utilization. A GPU is billed while it is allocated to the tenant, read from Kubernetes. That is how AI Clouds and dedicated inference endpoints bill: per second or per minute while a replica runs, with autoscaling and scale to zero keeping idle replicas off the bill. Shared (serverless) inference bills tokens instead. DCGM's utilization is recorded next to GPU-hours for showback; to put energy or utilization in the price, declare it as a Prometheus metric (DCGM's energy is a counter, so exact; utilization is an estimate). A cluster with no Prometheus at all is fully billable for GPUs, nodes, CPU, memory, storage and load balancers.

  1. Windows. Every billing.collectionInterval (60 seconds by default), vBilling measures the window that just closed. Each quantity is the overlap of a resource's lifetime with the window, to the second.
  2. Ledger. The window's events are committed to an append-only, hash-chained ledger in one write. An event's ID is derived from what it measures, so measuring the same window twice produces the same IDs, and billing platforms drop the repeat.
  3. Delivery. Each billing platform reads the ledger from its own cursor. An outage of one platform holds up nothing else, and nothing is lost while it is down.
  4. Checks. GET /api/v1/reconcile compares the ledger with what each platform recorded, cross-checks compare two sources of the same usage (gateway tokens against the engine's own counter), and GET /api/v1/sources reports any source that is failing.

Known limits

  • CPU and memory on usage. metrics-server reports usage now, not over a window. With cpuMemoryBasis: usage, a window collected late (after a restart or an outage) bills no CPU or memory; vBilling logs it and counts it in vbilling_cpu_memory_unmeasured_total. The default, requests, is exact. A pod that requests nothing is billed nothing for CPU and memory: vBilling logs and counts such pods (vbilling_pods_without_requests); give them default requests with vCluster's policies.limitRange.
  • A node that dies suddenly. Kubernetes marks it Unknown 40 to 50 seconds after its last heartbeat. vBilling dates the downtime from the last heartbeat or Lease renewal, but with the default 5-second billing.collectionDelay the window in which the node died is usually committed before the mark, so up to one window (60 seconds) after the death can still be billed. On spot or preemptible GPUs, set billing.collectionDelay: 75s.
  • Late usage on Stripe. Stripe accepts usage for a period whose invoice is already finalized but does not invoice it. vBilling delivers within seconds, so this needs vBilling to be down or backlogged past a period's end plus Stripe's grace period (one hour by default).
  • Gateways apply blocks late. LiteLLM applies a team block when its key cache expires (60 seconds by default), and a gateway that retries requests while a cluster is paused can bill requests no client received. Set LiteLLM's user_api_key_cache_ttl: 5 with enforcement.gateway.litellm, and blocks take effect within 5 seconds.
  • Tenants with root on their own nodes. A tenant who is cluster-admin on a cluster with its own nodes can run privileged containers, or processes outside Kubernetes, that no drain can stop. A pause stops billing only once vBilling has verified the drain, and DaemonSets that may use GPUs are always stopped; for untrusted tenants set PAUSE_KEEP_NAMESPACES=none, or power paused nodes off (for example with vMetal) to make the stop physical.
  • Counters that appear with history. A Prometheus series vBilling has not seen before is billed from zero only when its _created sample shows it started after the previous read, or its target's process_start_time_seconds does and its first value is plausible for the time since that start; otherwise from its first sample, and its source says so. For exporters whose process outlives the workloads they report (cAdvisor), the start time is weak evidence.
  • One instance. vBilling runs as a single replica. A restart loses nothing (the ledger keeps every committed window and missed windows are backfilled); a replacement waits up to 30 seconds for the previous instance's Lease.
  • Estimates are labeled, not removed. query: metrics, DCGM utilization and usage-based CPU and memory are estimates. Do not let an estimate be the only evidence for an amount a customer may dispute.
