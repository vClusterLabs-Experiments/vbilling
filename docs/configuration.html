Configuration

Every setting for vBilling v0.3: environment variables, Helm chart values, and pricing setup in your billing platform.

Environment Variables

vBilling reads its configuration from environment variables; the Helm chart sets them from values.yaml. Credentials come from Kubernetes Secrets (see existingSecret in each section of the chart).

Most installs set about ten: ADAPTERS, that billing platform's credentials, REGION, CLUSTER_NAME, TENANT_SOURCE (with the Platform URL and key for platform), ENFORCEMENT_MODE and, for usage from Prometheus or AI gateways, PROMETHEUS_URL or the records settings. Everything else has a default that is right for billing. Settings removed in v0.3.1 are listed below.

Destinations

VariableDescriptionDefault
ADAPTERS Comma-separated destinations usage fans out to: stripe, metronome, lago, webhook, noop. Each destination reads the ledger through its own cursor. lago

Identity and region

VariableDescriptionDefault
REGION Region stamped on every event (for example ap-southeast-2). Run one vBilling per control plane cluster. default
CLUSTER_NAME Name of this control plane cluster; used as the CloudEvents source. control-plane
TENANT_SOURCE cluster: one customer per cluster. project: one per vCluster Platform project. With both, the vbilling.vcluster.com/tenant label always wins. platform: the vCluster Platform Tenant that owns the cluster's project, else the project, read from the Platform API; labels on clusters and namespaces never choose the customer (see vCluster Platform mode). cluster
PLATFORM_CLUSTER vCluster Platform cluster name of this control plane cluster, so Platform enrichment only applies to local clusters. Set it with TENANT_SOURCE=platform: instances on other connected clusters then never match. (none)
PLATFORM_URL TENANT_SOURCE=platform: vCluster Platform URL, the one vcluster platform login uses. (none)
PLATFORM_ACCESS_KEY Access key of a Platform user with a global role that reads Projects, Tenants and VirtualClusterInstances and may use instances. From a Secret. With TENANT_SOURCE=platform, clusters with their own nodes are reached only through the Platform proxy with this key, and vbilling.vcluster.com/ settings come only from Tenants and Projects. (none)
PLATFORM_CA_FILE / PLATFORM_INSECURE CA that signed the Platform's certificate, or skip verification (test installs with self-signed certificates only). (system roots) / false
WATCH_NAMESPACES Comma-separated namespaces to discover clusters in. Empty watches all namespaces. (all)

Ledger

VariableDescriptionDefault
DATA_DIR Directory for the ledger and adapter state. Keep it on a persistent volume. /var/lib/vbilling
ARCHIVE_DIR Long-term archive. Before compaction deletes a segment, vBilling gzips it into this directory and records it in archive.jsonl. See Retention and disputes. (none)
LEDGER_MIRROR The live copy of the data directory in ARCHIVE_DIR/mirror, from which vBilling restores itself after losing the data volume. auto: kept, except where the archive directory is a bucket mounted through FUSE. on: kept on any filesystem (needs ARCHIVE_DIR). off: not kept. See The ledger mirror. auto

Metering

VariableDescriptionDefault
COLLECTION_DELAY How long after a window ends it is metered (at least 5s, at most 10m). On spot or preemptible GPUs use 75s: Kubernetes marks a node that died without warning 40 to 50 seconds after its last heartbeat, and with the longer delay the window it died in is billed only up to that heartbeat. Usage reaches billing platforms that much later. Helm: billing.collectionDelay. 5s
CPU_MEMORY_BASIS requests (exact), usage (a metrics-server reading per window, an estimate), or max of both. Pods that request nothing bill no CPU or memory under requests; vbilling_pods_without_requests counts them. v0.2 defaulted to usage. requests
METER_CONTROL_PLANE Also bill the cluster's own control plane pods and data PVCs (normally covered by instance hours). false
METER_BY_NAMESPACE Add the namespace inside the cluster as a dimension, for tenant-side chargeback. false
GPU_RESOURCES Full-GPU resource names. MIG (nvidia.com/mig-*) and nvidia.com/gpu.shared are always detected. nvidia.com/gpu,amd.com/gpu
SKU_LABEL Node label whose value is the SKU (for example vbilling.vcluster.com/sku): of a whole node's node-hours, of the GPU hours on the node, and, with sku in their pricing keys, of CPU and memory hours. (none)
CAPACITY_TYPE_LABEL Node label for on-demand, spot, preemptible or reserved; beats cloud-provider labels. vbilling.vcluster.com/capacity-type
UNHEALTHY_NODE_TAINTS Taints that mark a node down: its GPU time is recorded as downtime, not billed. Add your GPU health taints. node.kubernetes.io/not-ready,node.kubernetes.io/unreachable
VCLUSTER_NODE_LABEL Extra dedicated-node selector, key=%s where %s is the cluster name. See Dedicated nodes. (none)
CUSTOM_METRICS Operator metrics in the v0.2 string form, code:unit[:key|key],.... All of them are billable. (none)
CUSTOM_METRICS_FILE Path of a YAML list of operator metrics: code, name, unit, description, groupKeys and billable (default true; false keeps a metric informational). Helm renders metering.customMetrics into it. See Custom metrics. (none)
ALLOWANCES_FILE Path of a YAML list of storage allowances: metric (vcluster_storage_gb_hours, the only metric that takes one), included (GiB, above 0), per (node, cluster or volume) and, optionally, storageClasses (the listed classes share the allowance, the first listed taking from it first). With any allowance, storage above it is billed as vcluster_storage_overage_gb_hours, every storage class included, and vcluster_storage_gb_hours becomes informational. Helm renders billing.allowances into it; vbilling check-config checks it. See Included storage. (none)
PROMETHEUS_URL Any Prometheus HTTP API (Prometheus, Thanos, Mimir, VictoriaMetrics). Enables egress and GPU utilization metrics. (none)
EGRESS_QUERY PromQL query for egress bytes. Without it, egress is read as a counter, container_network_transmit_bytes_total{{selector}}, and billed exactly; a query makes it an estimate. none turns egress off. Placeholders: {{selector}}, {{matchers}}, {{namespace}}, {{vcluster}}, {{instance}}, {{project}}, {{tenant}}, {{tenant_cluster}}, {{window}} (e.g. 60s), {{window_seconds}} (e.g. 60). (none: a counter)
GPU_UTIL_QUERY, GPU_COUNT_QUERY Replace the GPU utilization queries (same placeholders, results grouped by modelName or gpu_type). none disables utilization. For clusters with their own nodes, a Prometheus of their own or PROMETHEUS_PRESET, the defaults select DCGM series with {{matchers}}. DCGM, namespace or exported_namespace
PROMETHEUS_HEADERS Extra query headers, Name=value,..., e.g. X-Scope-OrgID for Mimir or Authorization. Basic auth also works in the URL. (none)
PROMETHEUS_PRESET vcluster-platform reads vCluster Platform fleet observability: {{matchers}} becomes the vcluster_platform_instance and vcluster_platform_project labels for every Prometheus metric, egress and GPU utilization included. (none)
PROMETHEUS_METRICS_FILE Metrics read from Prometheus for every cluster and window: counter: (raw samples, exact) or query: (PromQL, an estimate). Billable ones are created in the billing platforms. See Usage Sources. (none)
PROMETHEUS_SOURCE_LABEL Label that names the source cluster on series from clusters with their own nodes, an external label their Prometheus agent adds when it remote writes. For those clusters {{matchers}} becomes <label>="<cluster name>". See Scope series to a cluster. vcluster
PROMETHEUS_BEARER_TOKEN_FILE Bearer token file, re-read on every query (for example a service account token for an OpenShift Thanos querier). (none)

Per-request records and cross-checks

Records from AI gateways and inference servers (POST /api/v1/records), and comparisons of two sources of the same usage. See Usage Sources.

VariableDescriptionDefault
RECORDS_MAPPINGS_FILEPath of a YAML map of payload formats besides vbilling and litellm: field paths for the request ID, time, tenant and quantities of each gateway.(none)
RECORDS_LITELLMEnable the built-in litellm format for LiteLLM's generic API logger. It declares inference_input_tokens and inference_output_tokens, which every billing adapter then creates.false
RECORDS_UNKNOWN_TENANTSaccept: bill pushed usage (records and POST /api/v1/events) for a tenant vBilling does not know to that tenant ID, and report it in the response and in source health. reject: refuse it, so an ingest token can never create usage, or a customer at the billing platform, for a tenant that does not exist. production-values.yaml sets reject.accept
RECORDS_PULL_FILEYAML list of gateway request logs to read back as records, for any gateway with a logs API: URL with a time range, headers (${RECORDS_PULL_...} variables only), rows path and paging. Pushed and pulled copies count once. Helm: records.pull and records.pullEnv. See Pulling any gateway's request log.(none)
LITELLM_URLBase URL of a LiteLLM proxy (v1.103.0 or later, with a database) whose spend logs vBilling reads back as records, to fill what the generic API logger's push lost. Pushed and pulled copies of a request count once. Enables the litellm format. See Pulling LiteLLM's spend logs.(none)
LITELLM_API_KEYA LiteLLM key that can read every team's spend logs: the master key or a proxy admin key. Required with LITELLM_URL.(none)
LITELLM_TENANTBill every pulled request to this tenant. Set it when LiteLLM's push uses an ingest token bound to one tenant, so pulled copies of pushed requests get the same IDs and count once.(none)
LITELLM_CLIENTThe client name the push sends (X-VBilling-Client), for the same reason.litellm
CROSS_CHECKSCompare two sources of the same usage per tenant and hour, primary=secondary[:tolerance%],..., for example inference_output_tokens=vllm_output_tokens:2%. Both metrics must be declared. Divergence above the tolerance shows in source health and /metrics.(none), tolerance 1%
!
Records settle for 30 seconds after their window ends and are kept for 7 days. Both are fixed: RECORDS_SETTLE and RECORDS_RETENTION are in the removed settings, and windows are always 60 seconds.

Price coverage

A billing platform bills usage it has no price for at $0, without an error. vBilling reads (never writes) each billing platform's products, rates, prices and charges, and reports every billable metric and recent series it cannot price in GET /api/v1/pricing, source health and vbilling_unpriced_series. See Unpriced usage and the Metronome, Stripe and Lago pages.

VariableDescriptionDefault
PRICE_CHECKwarn: report usage a billing platform has no price for, and hold Metronome usage no billable metric counts yet, which Metronome would never bill. hold: also keep the events of an unpriced series (metric, SKU, plan) out of that destination. They stay in the ledger and in DATA_DIR/held, and ship in ledger order once the price exists, or without a price after 23 hours, before their invoice period can be final; other series and destinations are not delayed. off: no checks, and nothing held. Switching from hold back to warn releases what is held for a price; off releases everything held.warn

Pricing keys

Each built-in metric has the keys a rate card prices it on (its group keys, such as region and sku for GPU hours). PRICING_KEYS adds more, from the dimensions the metric's events carry: an instance profile with a public IP and one without, GPU hours per profile and per GPU model, CPU and memory per node SKU. Pricing keys on the metrics page lists the keys each metric takes.

VariableDescriptionDefault
PRICING_KEYSMore pricing keys for built-in metrics, metric:key|key,metric:key, for example vcluster_private_node_hours:public_ip|zone,vcluster_gpu_hours:gpu_type. A key the metric's events do not carry is refused at start-up and by vbilling check-config, with the keys it takes. An event with no value for a key carries none at Metronome, which requires every group key on every event. Custom metrics declare their own group keys. Not with the stripe adapter: Stripe meters cannot price on dimensions, so split them with STRIPE_SPLIT_METERS_BY. On Metronome a new key set needs a new billable metric: read Changing pricing keys before you change it on a running install.(none)

API and enforcement

VariableDescriptionDefault
LISTEN_ADDR HTTP listen address for the API, dashboard, metrics and webhooks. :8080
API_TOKEN Bearer token for every endpoint except /healthz and /readyz: the API, the dashboard's data, /metrics. The API is never open: without a token vBilling generates one into DATA_DIR/api-token (mode 0600) and logs the file's path. The chart generates one into its Secret unless api.token or api.existingSecret is set. See Security. (generated)
INGEST_TOKEN Shared bearer token for POST /api/v1/events and POST /api/v1/records, for the operator's gateways. It is never the API token: vBilling refuses to start when the two are equal, and answers ingest sent with the API token with 401. Without it, vBilling generates one into DATA_DIR/ingest-token (mode 0600) and logs the file's path. The chart generates one into its Secret (key ingest-token, kept across upgrades) unless api.ingestToken or api.existingSecret is set. Before v0.3.1 it defaulted to API_TOKEN: gateways that still send the API token must switch to this one. See Security. (generated)
INGEST_TOKENS Ingest tokens bound to one tenant, token=tenant,.... Usage sent with such a token is billed to that tenant whatever the payload says, so a gateway inside a tenant's cluster can never bill another tenant. Helm: api.tenantIngestTokens ({tenant: token}) or the ingest-tokens key of api.existingSecret. (none)
ENFORCEMENT_MODE observe, annotate or enforce. See the README. observe
ENFORCEMENT_RULES Overrides, event.type=state,... (for example alerts.spend_threshold_reached=suspended, or alerts.low_remaining_commit_balance_reached=paused to pause a tenant whose prepaid commit balance runs out; alerts.low_remaining_contract_credit_balance_reached watches credits only). A key alert:<name or ID> names one Metronome threshold notification and wins over a rule on its type, for a low-balance warning next to a zero-balance pause: alert:Wallet below $50=warning. (none)
ENFORCEMENT_ESCALATIONS Grace periods, from:after:to,...: a billing hold that stays at from for after is raised to to, for example delinquent:72h:suspended,suspended:7d:paused. after takes d, h, m and s, at least 1m. Only delinquent and suspended escalate, by one rule each, to a more severe state. The clock starts when the hold reached its state and survives restarts; a payment that lifts the hold ends it. Operator holds never escalate. GET /api/v1/billing-states shows each tenant's next escalation (escalation.to, escalation.at). Helm: enforcement.escalations, a list of {from, after, to}. See Grace periods. (none)
ENFORCEMENT_IN_CLUSTER In enforce mode, also install the vbilling-suspended admission policy inside each of a suspended tenant's clusters, through their own API. The only enforcement that reaches clusters with their own nodes. Needs write access to admission policies in each cluster. See Billing-state enforcement inside the cluster. false
ENFORCEMENT_LITELLM In enforce mode, block a suspended or paused tenant's LiteLLM teams and unblock them when it is active again (only blocks vBilling set). Uses LITELLM_URL and LITELLM_API_KEY. Helm: enforcement.gateway.litellm. See Stopping a suspended tenant at the gateway. false
PAUSE_KEEP_BILLING What keeps billing while a cluster is paused (state paused): any of storage, load_balancers, nodes, control_plane, workloads, or none. Without workloads, the usage of a paused cluster's pods stops once vBilling has verified they are gone (each gets at most 30 seconds of grace). A pause vBilling cannot verify keeps billing the cluster's own nodes. Helm: enforcement.pause.keepBilling. See Pausing a tenant. storage,load_balancers
PAUSE_KEEP_NAMESPACES Namespaces whose DaemonSets keep running on a paused cluster's own nodes: node infrastructure such as the GPU driver, device plugin and CNI, so nothing is reinstalled on resume. Every other pod is stopped, including DaemonSets elsewhere and any DaemonSet pod that requests a GPU or another extended resource. none stops every DaemonSet. Helm: enforcement.pause.keepNamespaces. kube-system, kube-flannel, calico-system, tigera-operator, cilium, gpu-operator, nvidia-gpu-operator, network-operator, nvidia-network-operator

Example Helm install

helm upgrade --install vbilling deploy/helm/vbilling \ -n vbilling-system --create-namespace \ --set adapters='{metronome,webhook}' \ --set metronome.existingSecret=metronome-credentials \ --set metronome.rateCard=payg-aud --set metronome.provision=true \ --set stripe.existingSecret=stripe-credentials \ --set webhook.url=https://data.example.com/usage \ --set region=ap-southeast-2 --set api.existingSecret=vbilling-api

Operations

Check a configuration before it rolls out

vBilling is one pod. A configuration it refuses at start-up (an invalid metric definition, an enforcement rule it cannot parse, a price card with a typo) used to stop all metering until someone reverted it, because the old pod was already gone. Two things prevent that now.

vbilling check-config loads and checks the configuration exactly as start-up does: the environment and every file start-up parses (Prometheus metric definitions, custom metrics, records formats and pull definitions, price cards, the list of external clusters, enforcement rules, cross-checks, ingest tokens). It contacts nothing, takes no Lease, opens no ledger and writes nothing, so it also runs in the live pod. It exits 0 with the list of what it checked, or 1 with the same error text start-up would stop with:

kubectl -n vbilling-system exec vbilling-0 -- /vbilling check-config vBilling 0.3.3: checking the configuration as start-up reads it ok settings: adapters metronome, region ap-southeast-2, tenant source platform, enforcement enforce, price check hold ok PROMETHEUS_METRICS_FILE: /etc/vbilling/prometheus/metrics.yaml, 3 metric(s) ok ENFORCEMENT_RULES: 2 rule(s) The configuration is valid: 6 check(s) passed, 0 warning(s).

The chart runs it for you. With configCheck.enabled (the default), every helm install and helm upgrade first runs a Job with the new configuration, as a pre-install and pre-upgrade hook. If the check fails, the upgrade fails with the error, and the running pod, its StatefulSet and its configuration are untouched: metering goes on with the configuration it had. Read the reason with kubectl -n vbilling-system logs job/vbilling-config-check, fix the values, and upgrade again.

  • The Job gets the same image, security context, resources and placement as the vBilling pod, needs no RBAC and mounts neither the ledger nor the archive volume.
  • Credentials from a Secret you manage (existingSecret) are checked when the Secret exists. Credentials the chart itself puts in its Secret are not: on an install that Secret does not exist yet, and on an upgrade it still holds the previous values. A credential the check cannot see is a warning, not an error.
  • Argo CD runs Helm hooks as PreSync hooks, so a failed check fails the sync before anything is applied.
  • helm rollback runs no hooks, and --no-hooks or configCheck.enabled=false skips the check. Tools that apply helm template output without hook support should render with --no-hooks.

Start-up itself now checks everything before it takes the Lease, and gives the Lease up if it still has to stop afterwards, so a pod that cannot start never holds the Lease that a working one waits for.

Placement

vBilling meters the compute plane, so it should not live or die with it. Run its pod on nodes that are not the GPU nodes it meters, and put its two volumes in different failure domains:

  • The ledger volume (persistence.storageClass) on replicated or network-attached storage, so the pod can move to another node with its ledger. A node-local volume ties the ledger to one node.
  • The archive volume (persistence.archive) on a different storage class, in another failure domain. It holds the second copy of the ledger: the ledger mirror, a live copy of the data volume from which vBilling restores itself, and the archive for disputes. A bucket holds the archive, but no mirror.
  • The pod with affinity or nodeSelector (and tolerations where your management nodes are tainted). production-values.yaml keeps it off nodes labelled nvidia.com/gpu.present=true and names placeholders for both storage classes; the pod stays Pending until you replace them, on purpose.

After an install the chart's notes say what is fragile: the archive is off, the mirror is off, both volumes share a storage class, no placement is set, or the configuration check is off. The chart refuses values that still hold a REPLACE_WITH_ placeholder, so a region or cluster name is never billed as written in the example file.

The ledger mirror: when the data volume is lost

The data volume holds everything vBilling knows: the usage ledger, the per-request records, each destination's cursor, held events, dead letters, counter baselines, pause spans, billing states, and the metering source identity that event IDs are built from. The archive only receives segments older than seven days, so without more, the newest week exists once. The ledger mirror is the second copy of that week: with ARCHIVE_DIR set, vBilling keeps a live copy of the whole data directory in <ARCHIVE_DIR>/mirror, on the archive volume.

  • A second or two behind. A pass runs within about a second of every committed window, and every 5 seconds for files that change in between. A pass ends by replacing MIRROR.json, the recovery point: it names exactly the bytes that belong together, so a copy that was interrupted is never restored half.
  • Never in the way. The mirror runs next to metering. A mirror volume that is slow, read-only, full or gone makes the source ledger-mirror fail and the lag grow. Metering, delivery and the archive go on.
  • Checked. Every ledger line is checked against its hash and its link to the line before it is copied. vbilling ledger verify --dir <ARCHIVE_DIR>/mirror verifies the copy and its recovery point at any time.
  • Visible. vbilling_ledger_mirror_lag_seconds is the age of the oldest committed record the mirror does not hold (0 when in step), vbilling_ledger_mirror_errors_total counts failed passes, and the source ledger-mirror in GET /api/v1/sources says where the mirror stands, or why none is kept. The alert rule VBillingLedgerMirrorLagging fires after 5 minutes of a lag above 5 minutes.

Where a mirror is kept

LEDGER_MIRROR (Helm persistence.archive.mirror)What happens
auto (default)Kept wherever ARCHIVE_DIR is set, except on a bucket mounted through FUSE (Cloud Storage FUSE, Mountpoint for Amazon S3, BlobFuse). The mirror appends to its newest segment and replaces its recovery point after every window, and a bucket uploads the whole object again for that, or refuses. The archive itself works there: it writes each segment once.
onKept on any filesystem. For a FUSE filesystem that appends and renames in place.
offNot kept. Losing the data volume then loses every record that is not archived or delivered yet.

Where none is kept, the source ledger-mirror is paused and says why, and the chart's notes warn when the mirror is switched off. To have the mirror, give the archive a disk or a file share on other storage than the data volume. In a values file, a bare on or off is a YAML boolean; the chart takes both spellings.

Space. The archive volume now holds the archive and a copy of everything on the data volume: size it for both. The mirror leaves a tenth of the volume to the archive and stops copying before it would take that, because a segment that cannot be archived stays on the data volume. The source then says how much it still has to copy and that the volume has to grow; the mirror continues by itself afterwards. A first copy that does not fit is not started. Retention is followed: a segment that compaction removed from the ledger leaves the mirror with the next pass.

Access. The mirror holds what the data volume holds, including the API and ingest tokens vBilling generated. Protect the archive volume like the data volume.

After the data volume is lost

vBilling restores itself. When it starts on a data directory that holds no ledger and finds its mirror with a recovery point, it copies the recovery point back before it opens anything, verifies the restored ledgers, and continues the same ledger under the same metering source identity. So the procedure is to give the pod a new, empty volume and keep the archive volume:

# The node or disk under the data volume is gone. Keep the archive claim. kubectl -n vbilling-system delete pvc data-vbilling-0 --wait=false kubectl -n vbilling-system delete pod vbilling-0 # The StatefulSet creates a new claim and pod. vBilling says what it did: kubectl -n vbilling-system logs vbilling-0 | grep '\[mirror\]' [mirror] /var/lib/vbilling holds no ledger, but the mirror in /var/lib/vbilling-archive/vbilling-0/mirror does: the data volume was lost or replaced. Restoring it [mirror] restored /var/lib/vbilling/ledger: seq 1-48211, 48211 record(s), verified [mirror] restored /var/lib/vbilling as it was at 2026-11-26T10:05:00Z, 3m12s ago (the mirror's last complete pass), with 23 state file(s). ...

What happens next:

  • Metering. Every window since the restored watermarks is metered again from the lifetimes of the objects vBilling finds, up to 24 hours back, and marked backfilled. Prometheus counters continue from the restored baselines: the increase since the recovery point is billed once.
  • Delivery. Each destination is sent everything after its restored cursor. What a billing platform already received in the mirror's last seconds is sent again under the same event ID and deduplicated there. A paused destination stays paused, and one that waits for a start decision still waits.
  • State. Held events, dead letters, pause spans and billing states are as of the recovery point. A paused tenant stays paused and unbilled from its recorded second.
  • Not restored. Usage pushed to vBilling after the recovery point (the ingest API, per-request records), normally a second or two of it. Senders that retry, and request logs that vBilling pulls, fill it in: a retried push is counted once, whether or not its first copy was restored.
!
Restore soon. The restore log says how old the recovery point is and warns above a day: windows older than 24 hours are not metered again, and a billing platform that deduplicates by event ID for a day (Stripe) no longer recognizes what was being delivered when the copy was made. Compare GET /api/v1/reconcile with the billing platform for those hours. If the restore itself fails, vBilling stops instead of starting as a new install next to the copy of a ledger it lost; the log line names what to fix.

vBilling restores only a mirror it keeps. With LEDGER_MIRROR=off, or on a bucket in auto, a copy from earlier is named in the log and left alone, because nothing says how old it is. To start as a new install on purpose, empty the data directory and remove the mirror directory.

Restore by hand

vbilling ledger restore does the same from the command line: to another directory, from a copy that was set aside, or over a damaged ledger. It verifies the whole mirror before it changes anything, and refuses a target that holds a ledger unless you pass --force. vBilling must not run on the target: scale the StatefulSet to zero and run the command in a pod of the same image with both volumes mounted.

vbilling ledger restore --from /var/lib/vbilling-archive/vbilling-0/mirror --to /var/lib/vbilling Restored /var/lib/vbilling from /var/lib/vbilling-archive/vbilling-0/mirror recovery point 2026-11-26T10:05:00Z, 3m12s ago (the mirror's last complete pass) metering source a6ebc8ab6b7a7200bf6be9fcdcb5eb8d ledger seq 1-15, 15 records in 3 segment(s), verified; last committed seq 15 written 2026-11-26T10:05:00Z cursor metronome 15 (in step) cursor stripe 12 (3 record(s) to send) ...

The report lists every cursor, what vBilling will do when it starts, and a note when --force replaced a ledger that metered under another identity: the windows that ledger delivered are metered again under other event IDs, so remove them at the billing platform.

A mirror of another ledger. vBilling never overwrites a mirror that holds records its own ledger lacks, for example after a new install was started next to an old archive volume. It renames that copy to mirror-set-aside-<time>, starts a new mirror, and reports the source ledger-mirror-set-aside until you restore the copy or delete it.

Move the ledger to another volume

The same restore moves the ledger to another storage class, for example from a node-local volume to replicated storage. Kubernetes refuses to change the volume claim template of an existing StatefulSet, so the StatefulSet is removed and the upgrade creates it again. Start when the source ledger-mirror is ok:

# 1. Stop vBilling. A clean stop ends with a last pass: the mirror is in step. kubectl -n vbilling-system scale statefulset vbilling --replicas=0 kubectl -n vbilling-system wait --for=delete pod/vbilling-0 --timeout=120s # 2. Remove the StatefulSet and the old data claim. Keep the archive claim. kubectl -n vbilling-system delete statefulset vbilling kubectl -n vbilling-system delete pvc data-vbilling-0 # 3. Upgrade with the new class. The pod starts on an empty volume and restores itself. helm upgrade vbilling deploy/helm/vbilling -n vbilling-system -f values.yaml --set persistence.storageClass=replicated-ssd kubectl -n vbilling-system logs vbilling-0 | grep '\[mirror\]'

To keep the old volume until the new one is checked, set the reclaim policy of its PersistentVolume to Retain before step 2. vBilling is down for the minutes this takes, and meters the windows in between afterwards.

Retention and disputes

Customers dispute invoices months after the usage happened, so the evidence behind a bill has to outlive the bill. vBilling keeps its hash-chained ledger in two tiers.

Seven days is how long raw ledger segments stay on the ledger volume after every destination has consumed them. The period is fixed: RETENTION was removed in v0.3.1, and a value still set only logs a warning. Hourly compaction deletes older ones; a segment a destination has not consumed yet is never deleted. Size persistence.size for this window (see Sizing below).

ARCHIVE_DIR keeps the evidence after that. Before compaction deletes a segment, it writes a gzip of the segment's exact bytes to seg-<first seq>.log.gz (temporary file, fsync, rename), appends a line to archive.jsonl with the segment's sequence range, times, the hash it links to, its last hash and the gzip file's sha256 and size, and only then deletes the segment. If archiving fails, the segment stays and the next compaction retries. vBilling never deletes from the archive. The files are plain gzip and JSON lines: each ledger line is the sha256 of its record, a tab, and the record, which names the hash of the record before it, so sha256sum and zcat are enough to inspect them.

With Helm, persistence.archive.enabled=true mounts a volume and sets ARCHIVE_DIR to <mountPath>/<pod name>. For object storage, bind a PersistentVolumeClaim to a bucket through a CSI driver (Cloud Storage FUSE, Mountpoint for Amazon S3) and set persistence.archive.existingClaim. The mount must let the pod user (65532) create, rename and append to files. On a bucket vBilling keeps the archive only; the ledger mirror needs a disk or a file share.

!
Without existingClaim, the chart adds a volumeClaimTemplate, which Kubernetes cannot add to an existing StatefulSet. On an existing install, run kubectl -n vbilling-system delete statefulset vbilling --cascade=orphan first: pods, volumes and the ledger stay, and the upgrade recreates the StatefulSet.

Verify

vbilling ledger verify checks every archived segment (the gzip file's sha256, every record's hash, the links across segments) and then the live ledger, which must continue exactly where the archive ends. It only reads files, prints a JSON report and exits 1 on any failure. Inside the pod, --dir and --archive default to the controller's DATA_DIR and ARCHIVE_DIR:

kubectl -n vbilling-system exec vbilling-0 -- /vbilling ledger verify { "ok": true, "records": 18, "archived_segments": 3, "live_segments": 3, "first_seq": 1, "last_seq": 18, "first_at": "2026-10-05T10:01:00Z", "last_at": "2026-10-05T10:06:00Z", "anchor": "", "head": "823ba93bdcec1b82d732117c6d363dde578df4dde161fdfd26e89c6d378a3b72" }

An empty anchor means the chain is intact back to the ledger's first record; otherwise it starts where retention had already deleted segments before ARCHIVE_DIR was set. The chain shows that no record was changed, removed or inserted unless every record after it was rewritten as well, so keep each report's head somewhere outside vBilling, for example with the invoice. To check a copy elsewhere, run the binary with --archive on the copied bucket, with or without --dir. The running API does the same check with GET /api/v1/ledger/verify?archive=true.

Export the usage behind an invoice

kubectl -n vbilling-system exec vbilling-0 -- /vbilling ledger export \ --from 2026-01-01 --to 2026-02-01 --tenant acme-ai > acme-ai-2026-01.ndjson

Each line is a usage event exactly as it was recorded, for every window that overlaps [--from, --to), from the archive and then the ledger in ledger order. --metric narrows it further. Export checks each event against its hash, and a missing archived segment fails the export rather than returning less usage; run verify first for the whole chain.

Sizing

Measured on one full segment (20,025 records) of GPU cluster usage, eight metrics per cluster per minute with the dimensions and properties the collector sets: 821 bytes per event in the ledger, 86 bytes in the archive, 9.5 times smaller. For 100 clusters (48,000 events an hour) that is about 0.95 GB a day on the ledger volume, so 6.6 GB for the default 7 days, and about 3 GB a month in the archive, 39 GB for 13 months. Verification reads about 165 MB of ledger a second on one core (Apple M1 Max), so those 13 months verify in about 40 minutes. Reproduce with go test -run X -bench ArchiveSegment ./internal/spool/.

Those figures describe resource aggregates. Request metering also stores one raw row per nonzero request metric: estimate hot storage as requests/second × metric rows/request × measured bytes/row × retention seconds, then add aggregates, delivery outages, the dedupe index and growth headroom. At 100 requests/second, two rows/request and 1 KiB/row, raw rows alone take about 124 GB for seven days. Measure your own rows and sustained fsync throughput; the chart's 5 GiB and 256 MiB defaults are for small installations. With the ledger mirror, add the data volume's used space to the archive volume: the mirror is an uncompressed copy of it.

production-values.yaml supplies an initial production configuration: a 100 GiB hot volume, a separately provisioned archive PVC, larger CPU and memory allocations, strict tenant validation, price holds and a 75-second collection delay. The example needs sizing for your traffic and a real archive PVC: it names existingClaim: vbilling-archive, and the pod stays Pending until a claim of that name exists in the release namespace. The file is not in the packaged chart or the release assets, so for an install without a clone download it from the tag (https://raw.githubusercontent.com/vClusterLabs-Experiments/vbilling/v0.3.3/deploy/helm/production-values.yaml). The shipped alert rules cover a stopped or stale vBilling, delivery, prices, sources, volumes, enforcement and webhooks.

Usage and reconciliation queries can only include retained ledger and archive data. Without archival, month-to-date totals become incomplete after consumed segments pass retention. Enabling archival later cannot reconstruct segments already deleted. Verify the archive's chain and retain the full data directory, including source.json, destination state, cursors and held usage, together in backups. The ledger mirror is such a copy, kept current by vBilling itself.

Lago Pricing Configuration

vBilling bootstraps a billable metric for each of its 10 built-in metrics and for every custom metric, among them inference_input_tokens and inference_output_tokens, which v0.3 always declares, and a vcluster-standard plan on startup. With storage allowances it also creates vcluster_storage_overage_gb_hours (field name: the code), which then carries storage: price that charge, not vcluster_storage_gb_hours. All charges default to $0.00 per unit unless a price card sets them. You must configure pricing in the Lago UI or API to actually generate non-zero invoices.

For an AI Cloud selling GPU compute to AI teams, you might set higher GPU prices and include a premium for dedicated infrastructure:

For an IDP (Internal Developer Platform) team doing internal chargebacks, use lower prices that reflect shared infrastructure costs:

# Internal platform team (chargeback) pricing CPU Core-Hours: $0.02 # internal cost only Memory GB-Hours: $0.005 # shared cluster memory Storage GB-Hours: $0.0005 # network-attached storage Instance Hours: $0.05 # minimal overhead fee GPU Hours (default): $1.00 # amortized GPU cost Network Egress/GB: $0.01 # internal network LoadBalancer Hours: $0.01 # shared ingress Private Node Hours: $0.50 # bare-metal amortization
!
If you see usage events in Lago but invoices show $0.00, it means the charge amounts are still set to their defaults ($0). Edit the plan charges in the Lago UI.

To price H100 hours differently from L40S hours in Lago, add charge filters on the sku (or gpu_type) event property. vBilling sends every dimension as an event property: sku, region, capacity_type, billing_mode, tenant_class and tenant_cluster. Spot and preemptible discounts are a filter on capacity_type. For a key in PRICING_KEYS, vBilling adds the values usage carries to the billable metric's filters, as it does for SKUs, so a charge filter can price them; the price check reads each combination against the charge filters.

Stripe and Metronome Pricing

Stripe: vBilling creates a Billing Meter per metric and, because Stripe meters cannot price on dimensions, a meter per SKU as new SKUs appear (for example vcluster_gpu_hours__nvidia_h100_80gb_hbm3). Create a metered price on each meter you charge for. To subscribe new tenants automatically, tag the prices metadata[vbilling_plan]=vcluster-standard (or the tenant's plan annotation) and enable stripe.autoSubscribe.

Metronome: vBilling's billable metrics are SUM metrics on value, one per metric code (with METRONOME_PROVISION=true vBilling creates them, named <Metric> [<code>]; otherwise vbilling metronome billable-metrics prints them for your catalog), each with one compound group key: region, sku, capacity_type, billing_mode, tenant_cluster for GPU hours. On your rate card, add a usage product per metric with pricing_group_key set to the dimensions you price on and presentation_group_key: [tenant_cluster] for invoice lines per cluster; together the two must form the metric's group key (for GPU hours, pricing_group_key: [region, sku, capacity_type, billing_mode]). PRICING_KEYS adds keys to that group key. Rate cards carry the currency, so use one rate card per currency. Point metronome.rateCard or a tenant's plan annotation at it.
