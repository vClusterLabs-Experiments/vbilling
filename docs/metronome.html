Metronome

The Metronome billing adapter sends vBilling usage to Metronome, which rates it, draws down prepaid balances and invoices. By default vBilling treats the Metronome account as yours: your portal creates customers and contracts, Finance manages billable metrics, products and rate cards as configuration, and vBilling only sends usage and reads. With METRONOME_PROVISION=true it creates what it needs itself.

✓
Run against a live Metronome sandbox. v0.3.2 ran the default mode end to end against a Metronome sandbox account: three teams' clusters and inference tokens, and a dedicated A100 cluster, metered on GKE with vCluster Platform; the pricing gate, price coverage, the prepaid wallet loop with a low-balance warning, a zero-balance pause and a top-up, reconciliation and draft invoices. See What is verified for what ran, the timings measured, and what did not run live.

Two modes

An AI Cloud that already bills with Metronome owns its account: its portal creates each customer at signup, and the contract that holds the customer's prepaid commits, and Finance applies billable metrics, products and rate cards from configuration. In the default mode vBilling fits into that account without changing it. A Metronome account that exists only for vBilling can let vBilling create its objects instead.

Three Metronome rules make the default mode work:

  • Usage can arrive first. Metronome keeps usage sent under an ingest alias that no customer holds yet, and attributes it to the customer that gets the alias later. vBilling never waits for the portal. In a live sandbox, a customer counted every event sent earlier under an alias within 90 seconds of getting it.
  • Aliases are resolved when usage is read. Removing an alias from a customer takes the usage sent under it off that customer again (seen live on the customer's usage totals), so never move an alias from one customer to another: add a new one next to it.
  • An alias belongs to one customer. Creating a customer with an alias another customer holds, archived customers included, fails with 409 until the alias is removed from that customer.
  • A customer can hold several aliases, for example an identity alias the portal uses and a compute alias that metering events key on.

The tenant ID is the compute alias

Usage events key on the vBilling tenant ID: vbilling.vcluster.com/tenant on the cluster's StatefulSet, its namespace or its VirtualClusterInstance; with TENANT_SOURCE=platform, the ID of its vCluster Platform Tenant (see vCluster Platform mode); otherwise vcluster-<namespace>-<name>. Give each customer that tenant ID as its compute alias at signup, next to its identity alias. Do not change it afterwards: usage under a new ID goes to whichever customer holds that alias, or stays unattributed.

To move a customer from another compute plane, add the tenant ID to the existing customer's ingest aliases next to the old compute alias, before its first usage from vBilling. Keep the old alias until every invoice with usage under it is final: Metronome resolves aliases when it reads usage, so removing the old alias takes that usage off the customer's open invoice. Its wallet, contract, rate card and Stripe customer stay as they are.

With TENANT_SOURCE=platform the tenant ID is tenant-<Tenant name>. vCluster Platform never renames a Tenant (its display name can change), so the ID survives renames, and a project moved to another Tenant bills to the new one from the minute it moved, while the minutes before stay with the old one (seen live). A Tenant deleted and created again under the same name gets the same ID; Metronome refuses that alias to a new customer while the old customer holds it, archived or not, so give the new Tenant an ID of its own with vbilling.vcluster.com/tenant.

Upgrading from v0.3.0

v0.3.0 always created billable metrics and customers, and contracts when metronome.rateCard was set. That now takes METRONOME_PROVISION=true (metronome.provision=true), which metronome.stripeLink=true still turns on. Without it, the customers, metrics and contracts vBilling created earlier stay as they are and keep receiving usage, because those customers hold the tenant ID as alias. METRONOME_RATE_CARD without provisioning only logs a warning. A tenant pinned to a customer with vbilling.vcluster.com/metronome-customer-id needs the tenant ID among that customer's aliases: the default mode sends usage under the alias and does not use the pin.

Install

Add the billable metrics to Metronome first. Metronome counts usage toward a billable metric only once the metric exists, so print the definitions vBilling's events need with the vBilling image, before you install it (pass the settings that declare custom metrics, such as CUSTOM_METRICS, as you will set them for vBilling), and add them to your Metronome configuration with a usage product and a rate for each one you sell (Billable metrics as configuration):

docker run --rm ghcr.io/vclusterlabs-experiments/vbilling:v0.3.3 metronome billable-metrics > billable-metrics.json

In the default mode vBilling creates nothing, so this is what your Metronome configuration and portal create, and what happens to usage while a piece is missing:

CreateExactlyWhile it is missing

A usage product per billable metric you sellIts pricing group key and presentation group key together form a compound group key of the billable metric (Pricing on dimensions).Unpriced.
A rate cardAn entitled rate for each product and pricing group value you sell; a rate of 0 for what is included.Unpriced.

Unpriced usage is held with PRICE_CHECK=hold and delivered and counted with warn; either way GET /api/v1/pricing names the missing piece (Price coverage). With METRONOME_PROVISION=true vBilling creates the billable metrics, the customers and the contracts; the usage products and the rate card stay yours.

Then install vBilling. You need a Metronome API token. Keep it in a Secret; values passed with --set are stored in the Helm release. The webhook secret for the billing-state loop does not exist yet: it belongs to a webhook that can only point at vBilling once vBilling is installed and reachable, so it is added to the same Secret afterwards (Webhooks and billing state). Until then vBilling meters and delivers as usual and answers /webhooks/metronome with a 404.

kubectl create namespace vbilling-system kubectl -n vbilling-system create secret generic vbilling-metronome \ --from-file=api-token=./metronome-token helm upgrade --install vbilling deploy/helm/vbilling -n vbilling-system \ --set adapters='{metronome}' \ --set metronome.existingSecret=vbilling-metronome \ --set enforcement.rules='alerts.low_remaining_commit_balance_reached=paused' \ --set region=ap-southeast-2

Then point a Metronome webhook at vBilling and add its secret (Webhooks and billing state).

Usage of a metric no billable metric counts yet, for example a custom metric added later, is held in vBilling, in both modes and with PRICE_CHECK=warn as with hold: Metronome would never bill it. Price coverage reports it unpriced with "uncounted": true and the hint no billable metric counts this event type yet: add it (vbilling metronome billable-metrics prints it). It is held the way PRICE_CHECK=hold holds unpriced usage (see Price coverage): durably, in DATA_DIR/held, before the delivery cursor moves past it, and shown in GET /api/v1/pricing, GET /api/v1/usage (held), /api/v1/destinations and source health. Within a minute of the billable metric appearing (or at once on POST /api/v1/pricing/check), vBilling sends what it held, in ledger order, before newer usage of the series. Usage held for 23 hours is released anyway, before its invoice period can be final, and the pricing/metronome/... source turns failing: Metronome keeps that usage but bills none of it, and only its support can reflow it into a billable metric added later. An event Metronome refuses, such as one older than its 34-day window, is dead-lettered, never dropped.

Two cases are not held for want of a billable metric. While a SQL billable metric is active, usage no other billable metric counts is reported unknown and sent: a SQL billable metric may count any event type, and vBilling cannot tell which. Usage that the property filters of every billable metric on its event type leave out, for example a new SKU, is a price gap like a missing rate: unpriced, and held only with PRICE_CHECK=hold. With PRICE_CHECK=off nothing is held, and usage no billable metric counts is sent and never billed.

To let vBilling create its own objects instead, on a Metronome account that exists for it, turn on METRONOME_PROVISION with the chart value metronome.provision=true. vBilling then creates or adopts billable metrics by name, so do not also create them by hand: two billable metrics with the same name leave it to Metronome's list order which one vBilling uses.

helm upgrade vbilling deploy/helm/vbilling -n vbilling-system --reuse-values \ --set metronome.provision=true \ --set metronome.rateCard=payg-usd

To also link each customer to a Stripe customer, add metronome.stripeLink=true and stripe.existingSecret. metronome.stripeLink turns provisioning on by itself, so it is the only way to get the Stripe link, not a requirement for provisioning. The chart reads it although values.yaml does not list it.

kubectl -n vbilling-system create secret generic vbilling-stripe --from-file=api-key=./stripe-key helm upgrade vbilling deploy/helm/vbilling -n vbilling-system --reuse-values \ --set metronome.stripeLink=true \ --set stripe.existingSecret=vbilling-stripe

Event contract

vBilling posts usage to POST /v1/ingest in batches of 100: one event per tenant, metric, 60-second window and set of dimensions, sent within seconds of the window closing. In a live run Metronome had processed each event a median of 7 seconds and at most 35 seconds after its window closed, so usage reached Metronome at most 95 seconds after it happened. Property values are strings, as Metronome recommends for numeric precision. One window of a private node with 8 GPUs and a public IP:

{ "transaction_id": "vb1_7c4e9a0d5b...", "customer_id": "tenant-acme", "event_type": "vcluster_private_node_hours", "timestamp": "2026-11-19T10:00:00Z", "properties": { "value": "0.016666667", "unit": "node-hours", "window_start": "2026-11-19T10:00:00Z", "window_end": "2026-11-19T10:01:00Z", "schema_version": "vbilling.usage/v1", "source": "collector", "region": "ap-southeast-2", "sku": "gpu-h100-8", "resource_id": "gpu-node-1", "capacity_type": "reserved", "billing_mode": "private_node", "node": "gpu-node-1", "tenant_cluster": "vcluster-acme-train", "vcpus": "208", "memory_gib": "2014.8", "gpu_count": "8", "public_ip": "true" } }
FieldMeaning
transaction_idvBilling's event ID: vb1_ and a hash of the tenant, metric, window, region, project, SKU, resource and dimensions. The same window always gets the same ID (the quantity is not part of it), and Metronome drops a repeated transaction_id for 34 days, so retries and replays never count twice.
customer_idThe tenant ID, which Metronome resolves as an ingest alias. With METRONOME_PROVISION=true, the customer ID vBilling created, found or was pinned to.
event_typeThe metric code, such as vcluster_private_node_hours (see Billable metrics as configuration).
timestampThe start of the window, in UTC.
valueThe quantity in the metric's unit, up to 9 decimals. Billable metrics sum it.
unit, window_start, window_end, schema_version, sourceThe unit, the window, vbilling.usage/v1, and where the quantity comes from (collector for Kubernetes objects, prometheus, records, ...).
region, sku, project, resource_idThe region, the SKU (the node's SKU_LABEL label, else its instance type or GPU model; the storage class for storage), the project, and the node name on per-node events (the cluster ID otherwise).
tenant_cluster, capacity_type, billing_mode, ...The event's dimensions: the cluster, on-demand, spot, preemptible or reserved, shared, dedicated_node or private_node, and where they apply the GPU type and profile, node, instance type, zone and tenant class.
vcpus, memory_gib, gpu_count, public_ipOn vcluster_private_node_hours only, for dedicated and private nodes: the node's CPU capacity in cores, its memory capacity in GiB (one decimal), its physical GPUs (MIG and time-slicing converted back to whole GPUs), and true when it has an ExternalIP address. They describe the instance and are not group keys.
accuracyestimate on quantities that are estimates: metrics the catalog marks as estimates (PromQL query: metrics, CPU and memory with CPU_MEMORY_BASIS other than requests, egress from EGRESS_QUERY), and any event that marks itself as an estimate. Absent on exact quantities. The webhook adapter adds the same property for its consumers.

A dimension never replaces a property vBilling sets from the event itself (value, unit, window_start, window_end, schema_version, region, project, sku, resource_id, source, accuracy): one with such a name is not sent, and the log says so once per name. A group-key property an event does not carry is sent as none, so every event passes the billable metric's filters. Metronome accepts events up to 34 days old: vBilling dead-letters older ones before sending them (with an hour of margin), so a rewound cursor or a longer outage shows in the dead-letter list and in reconciliation instead of disappearing.

Check delivery, list dead letters and replay them (add your API token as a bearer token):

kubectl -n vbilling-system port-forward svc/vbilling 8080 curl -H "Authorization: Bearer $VBILLING_TOKEN" -s localhost:8080/api/v1/destinations | jq '.destinations[] | select(.name == "metronome")' curl -H "Authorization: Bearer $VBILLING_TOKEN" -s localhost:8080/api/v1/destinations/metronome/dead-letters | jq curl -H "Authorization: Bearer $VBILLING_TOKEN" -s -X POST localhost:8080/api/v1/destinations/metronome/dead-letters/replay

A replay sends every dead letter again. What Metronome takes is removed, what it still refuses stays, and the call answers 200 with replayed, still_rejected and the reasons; fix the cause and replay again. It answers 502 with replay failed, dead letters kept only when Metronome could not be asked at all. To hold delivery on purpose, pause the destination instead of removing the adapter, and see Delivery operations for what happens when an adapter is removed and added again.

Adding Metronome to a running vBilling starts delivery at the next committed window. To send the retained ledger as well, rewind its cursor, to its start or to everything committed since a time; transaction IDs keep the overlap from counting twice:

curl -H "Authorization: Bearer $VBILLING_TOKEN" -s -X POST localhost:8080/api/v1/destinations/metronome/cursor -d '{"seq": 0}' curl -H "Authorization: Bearer $VBILLING_TOKEN" -s -X POST localhost:8080/api/v1/destinations/metronome/cursor -d '{"from": "2026-11-20T00:00:00Z"}'

Billable metrics as configuration

vbilling metronome billable-metrics prints the billable metrics vBilling's events need, as a JSON array of bodies for Metronome's POST /v1/billable-metrics/create: one per billable metric, the SUM of value, filtered on the event type and requiring value and every group-key property, with one compound group key. It does not call Metronome. Run it with vBilling's settings, so custom metrics are included: before the install with the image (see Install), and afterwards in vBilling's pod. Add the entries to the configuration Finance applies to Metronome. Metronome's billable metrics are not retroactive ("billable metrics only match usage events sent after the billable metric is created"), so vBilling holds a metric's usage until one counts it:

kubectl -n vbilling-system exec vbilling-0 -- /vbilling metronome billable-metrics > billable-metrics.json jq '.[] | select(.event_type_filter.in_values[0] == "vcluster_private_node_hours")' billable-metrics.json { "name": "Dedicated Node Hours [vcluster_private_node_hours]", "aggregation_type": "SUM", "aggregation_key": "value", "event_type_filter": { "in_values": ["vcluster_private_node_hours"] }, "property_filters": [ { "name": "value", "exists": true }, { "name": "region", "exists": true }, { "name": "sku", "exists": true }, { "name": "capacity_type", "exists": true }, { "name": "tenant_cluster", "exists": true } ], "group_keys": [["region", "sku", "capacity_type", "tenant_cluster"]] }

Pricing on dimensions

Add a usage product on each billable metric you sell. A product prices on a pricing group key and splits invoice lines with a presentation group key; together they must form a compound group key of the billable metric, so split its keys between them:

# Usage product on the vcluster_private_node_hours billable metric pricing_group_key: [region, sku, capacity_type] presentation_group_key: [tenant_cluster] # Usage product on the vcluster_gpu_hours billable metric pricing_group_key: [region, sku, capacity_type, billing_mode] presentation_group_key: [tenant_cluster]
  • Instance profile: sku on node-hours is the node's profile when SKU_LABEL names the node label that carries it, else its instance type or GPU model, so each profile gets its own rate.
  • Region: region is the vBilling instance's region (REGION), stamped on every event. It is never read from a node: run one vBilling per region to price regions differently.
  • Capacity type: capacity_type is on-demand, spot, preemptible or reserved. A discount is a lower rate; quantities stay physical.
  • Public IP: a second billable metric on the same event type counts the node-hours of nodes with a public address, one per node:
{ "name": "Public IP Hours", "aggregation_type": "SUM", "aggregation_key": "value", "event_type_filter": { "in_values": ["vcluster_private_node_hours"] }, "property_filters": [ { "name": "value", "exists": true }, { "name": "public_ip", "in_values": ["true"] } ] }

Price whole nodes either by node-hours or by their GPU, CPU and memory hours, not both (see what gets billed). Node disks are not metered. vBilling sends quantities only: the rate card sets prices and currency.

The prepaid wallet loop

An AI Cloud that sells prepaid capacity keeps the wallet in Metronome: the portal's contract carries prepaid commits, and a top-up adds a commit. vBilling closes the loop around that wallet:

  1. Usage reaches Metronome within seconds of each one-minute window closing, and Metronome draws the commit balance down as it arrives, so the balance trails the cluster by about a minute.
  2. A threshold notification on the commit balance fires. A rule maps it to paused: in enforce mode vBilling pauses each of the tenant's clusters, and their workloads, control plane and node capacity stop billing once vBilling has verified the workloads are gone, while volumes and load balancers keep billing by default (see Pausing a tenant). Metronome puts the notification in alarm, and sends its webhook, some time after the balance crosses its threshold: allow 1.5 to a little over 3 minutes. The customer keeps spending through that delay and until the pause is verified, about a minute more, so set the threshold above zero by at least the spend of those minutes.
  3. The customer tops up. When the payment for the payment-gated commit succeeds, Metronome sends payment_gate.payment_status with payment_status: paid. A payment does not say whether it refilled the wallet, so vBilling reads the customer's threshold notifications again (POST /v1/customer-alerts/list, each notification's real-time status for the customer, page by page). The billing hold clears, and the clusters resume, only when no notification that a rule maps above warning is in alarm or still evaluating. A top-up too small to lift the balance over the threshold leaves the notification in alarm, and the tenant paused. Metronome evaluates a notification again within minutes of a commit change, so for an hour after the payment vBilling answers it with a 500 while such a notification is still in alarm, and Metronome delivers it again; after that the payment is applied and the pause stays until another payment, or an operator, lifts it. Holds an operator set (operator, support, abuse) stay.
  4. A wallet refilled without a payment, a commit or credit Finance adds to the contract or a promotional grant, sends no payment webhook. Every minute vBilling reads Metronome for the tenants a threshold notification paused, and lifts the hold once no notification that a rule maps above warning is in alarm or evaluating. A hold that a failed payment raised still waits for a payment, and holds an operator set or the portal set through the API are never lifted this way. Metronome sends no webhook when a notification clears, so this read is what resumes such a tenant. Metronome clears a notification within about a minute of the commit being added, and vBilling lifts the hold at its next read after that, so allow up to two minutes from the top-up to the resume starting.
# values.yaml enforcement: mode: enforce rules: "alerts.low_remaining_commit_balance_reached=paused"

A low-balance warning and the zero-balance pause are usually the same notification type at two thresholds. Give the one that only warns a rule of its own, by its name or its ID (alert:<name or ID>), which wins over the rule on its type: it then sets warning, and it does not keep a pause once the wallet is above zero again.

enforcement: rules: "alerts.low_remaining_commit_balance_reached=paused,alert:Wallet below $50=warning"

A name in a rule may hold = but not a comma; use the notification's ID for a name that has one.

New customers that start disabled. To keep a customer's clusters paused until its first payment, have the portal set a billing hold at signup: PUT /api/v1/billing-states/<tenant> with {"state": "paused", "hold": "billing", "reason": "awaiting first payment"}. It applies to clusters created later too. The first payment_gate.payment_status paid lifts it once Metronome shows nothing owed; the minute-by-minute read does not, because no notification raised it.

Pick the notification that watches the balance the wallet is made of:

WalletNotification type for the rule
Prepaid commits (the portal's top-ups)alerts.low_remaining_commit_balance_reached
Commits and credits togetheralerts.low_remaining_contract_credit_and_commit_balance_reached
Credits only (promotional or free credits)alerts.low_remaining_contract_credit_balance_reached. It watches credits only, so it never fires for a commit balance: do not use it for a prepaid commit wallet.

When a top-up is read, a notification counts whichever of its names the rule uses: Metronome lists the credit balance notification as low_remaining_contract_credit_balance_reached, while its webhook example reads alerts.low_remaining_credit_balance_reached, and a rule on either keeps the hold while that notification is in alarm.

Metronome sends a threshold notification when the customer goes into alarm, so the pause follows the balance crossing the threshold, plus Metronome's notification delay. The balance falls one window's usage at a time, so keep a warning threshold and a pause threshold further apart than a few minutes of the customer's spend: closer than that, both can be crossed in one step and the warning does not arrive first. A rule on a notification's name matches the name Metronome sends in the webhook's properties.alert_name. A webhook for a customer whose tenant vBilling has not seen yet (signed up, no cluster) is not resolved: have the portal hold and release such a tenant with PUT /api/v1/billing-states/<tenant>. Without hold, the PUT sets the operator hold, which only another PUT lifts; with "hold": "billing", a top-up that leaves nothing owed lifts it too.

Price coverage

Metronome rates usage it has no rate for at $0, without an error: a new GPU model or region that reaches Metronome before its rate does is missing from invoices, prepaid drawdown and spend alerts. vBilling checks, read-only, that each tenant's usage has a rate where Metronome rates it. It never creates products or rates and never writes to a rate card.

In the default mode a series (a metric, SKU and the values of the metric's other group keys) is priced when:

  • a billable metric sums value for its event type and its property filters let the series through (filters on the SKU and the metric's other group keys are checked; filters on properties that vary within a series, such as public_ip or resource_id, are assumed to pass);
  • a usage product meters that billable metric;
  • an active contract of the tenant's own customer, the customer that holds the tenant ID as ingest alias, has a rate card with an entitled rate for that product, in effect now, whose pricing_group_values match the series on every key of the product's pricing_group_key. Values an event does not carry match none, as vBilling sends them. A product without a pricing group key prices every SKU with one rate.

METRONOME_RATE_CARD and the tenant's plan play no part: the customer's contracts decide. vBilling reads each tenant's customer and contracts when its usage first appears, and again at a check once that read is 5 minutes old; tenants on the same rate card share their series. With METRONOME_PROVISION=true the same holds: the check reads the rate card of the contract that rates the tenant's usage, the one vBilling created from the tenant's vbilling.vcluster.com/plan, else METRONOME_RATE_CARD, and the billable metric is the one vBilling created. A contract stays on the rate card it was created on. If the alias in that setting is later pointed at another rate card, the tenant's usage is still rated, and checked, on the contract's card; vBilling logs a WARNING and puts a note on the tenant's rows that names both cards. A tenant moves to another rate card only when its setting changes: the new contract then starts at 00:00 UTC that day and the old one ends there.

StatusMeaning
pricedA rate applies and is not 0.
unpricedNothing rates the usage: no billable metric counts it ("uncounted": true: held in every mode, see Install), no usage product meters it, the rate card has no entitled rate for the product and pricing group values, or the tenant has no customer with its ID as ingest alias, or no active contract with a rate card. The hint names what to add, for example add a rate for product "Compute Instance Hours" (pricing group sku=gpu-b200-8) to rate card "AI Cloud AUD", or create a Metronome customer with the ingest alias "tenant-acme".
zeroThe rate is 0 (flat 0, or every tier 0). This can be intentional, so it is information, not a gap, and the usage is delivered. Every series rated at 0 has its own row and is counted in vbilling_price_series{status="zero"}, so a rate of 0 is never hidden behind another series.
unknownThe check cannot decide: an active SQL billable metric may count the usage, the product is priced on a key vBilling does not track, or the metric is not in vBilling's catalog. Such usage is delivered in every mode (nothing could release it), and it is never silent: the series has an entry with status unchecked in GET /api/v1/sources?kind=pricing, with what to check in Metronome.

Every series has its own row and its own status in GET /api/v1/pricing: the plan (the rate card), the metric, the SKU and, under dims, the values of the other pricing keys. CPU hours on a rate card that prices on-demand at 0 and has no rate for spot are two rows, one zero and one unpriced; the counts per destination (priced, unpriced, zero, unknown) and the gauges count series. A series that is no longer used stays listed for 24 hours. vBilling logs every change of a series' status once, a change to a rate of 0 included.

Checks run at startup, every 10 minutes, within seconds of a new series appearing in the ledger, and on POST /api/v1/pricing/check. Gaps show in GET /api/v1/pricing, as unpriced entries in GET /api/v1/sources?kind=pricing with the hint (named pricing/metronome/<rate card>/<metric>/<SKU>/<key=value,...>), in the dashboard's Price coverage card, and as vbilling_unpriced_series{destination="metronome"}:

curl -H "Authorization: Bearer $VBILLING_TOKEN" -s 'localhost:8080/api/v1/pricing?destination=metronome' | jq '.destinations[].series[] | select(.status != "priced")'

A rate card that prices a whole node twice is flagged too: every dedicated or private node emits node hours and, for the same hardware, GPU, CPU and memory hours, so a plan with rates above 0 for both charges the node about twice. The destination's warnings in GET /api/v1/pricing name such a plan; price either node hours per profile or the per-resource metrics.

With PRICE_CHECK=hold, events of an unpriced series wait in vBilling until the rate exists, then ship in ledger order (see Unpriced usage). That includes the usage of a tenant that has no customer or no contract yet: it is held until both exist, and never delivered unrated. Metronome never changes an invoice once it is final (24 hours after its period, by default), so usage held for 23 hours is released without a rate, before its period can be final, and the pricing/metronome/... source turns failing.

With PRICE_CHECK=warn (the default) nothing is held for want of a rate: the check reports the series unpriced and the usage is delivered with everything else. Metronome stores that usage (its usage queries show it) but puts it on no invoice line, so it bills nothing. It is not lost yet: add an entitled rate that starts at or before the hour of the usage, and the draft invoice picks the usage up at that rate. That only works until the invoice is final, so in warn mode treat an unpriced series as something to fix the same day.

With PRICE_CHECK=off vBilling does not read Metronome's prices at all. It says so at startup (a [pricing] PRICE_CHECK=off log line) and in GET /api/v1/pricing, which answers "mode": "off" with a note and no destinations. There is no pricing/... source in GET /api/v1/sources and no vbilling_unpriced_series metric, and POST /api/v1/pricing/check reads nothing. Setting off to silence the warnings therefore removes every way to see, from vBilling, what Metronome will not price; the only place left to find it is Metronome's draft invoice.

The check reads, and the adapter's tests validate its requests and fixtures against the schemas of these pages:

  • GET /v1/billable-metrics: List all billable metrics
  • POST /v1/contract-pricing/products/list with {"archive_filter": "NOT_ARCHIVED"}: List products
  • POST /v1/contract-pricing/rate-cards/list, for names and aliases: List rate cards
  • POST /v1/contract-pricing/rate-cards/getRates with the rate card, at = now and one selector per product: Get rates
  • In the default mode, per tenant: GET /v1/customers?ingest_alias=<tenant> (List customers) and POST /v2/contracts/list with covering_date = now (List customer contracts)

Not covered: contract-level overrides (the check reads the contract's rate card, so a rate that exists only as an override is reported as a gap, and held in hold mode), SQL billable metrics (usage no other billable metric counts is unknown while one is active, never held, and listed as unchecked in the sources), pricing per tenant_cluster, and rates scheduled to start later (they count from their starting_at). When several billable metrics count the same usage, the series is priced if any of them has a rate.

Reconciliation

GET /api/v1/reconcile?destination=metronome recomputes each tenant's usage from the ledger and compares it with what Metronome's usage API (POST /v1/usage) recorded for the tenant's customer, found by ingest alias, on a billable metric that sums the value of every event of the type (one without filters on values, such as vBilling's definition). Metronome reports whole UTC days only, so from and to must be UTC midnights (YYYY-MM-DD works). Without them, the previous full UTC day is checked. Narrow it with tenant or metric; each row compares all of that tenant's usage of the metric, because Metronome reports totals per customer.

curl -H "Authorization: Bearer $VBILLING_TOKEN" -s 'localhost:8080/api/v1/reconcile?destination=metronome&from=2026-11-18&to=2026-11-19' | jq { "from": "2026-11-18T00:00:00Z", "to": "2026-11-19T00:00:00Z", "results": [{ "destination": "metronome", "ok": true, "rows": [{ "tenant": "tenant-acme", "metric": "vcluster_private_node_hours", "ledger": 24, "dead_lettered": 0, "expected": 24, "recorded": 24, "difference": 0, "match": true }] }] }

expected is the ledger total minus dead letters and minus before_start, and a row matches within 0.1%. before_start is usage the ledger recorded before the destination started (it was added at the ledger head, or an operator positioned it): the destination was never meant to receive it, so it is listed and never counts as missing. The result's start says where that was. A destination that existed before v0.3.3 has no recorded start and is compared from the beginning, as before. Reconcile once a day has closed and lag_records on /api/v1/destinations is back to 0. Usage of a tenant that no customer holds yet reads 0 in Metronome until the portal adds the alias, and two tenants that are aliases of one customer are not reconciled, because Metronome reports one total for both; the rows of such tenants say so in note.

Webhooks and billing state

Create a webhook in Metronome pointing at https://<your vBilling host>/webhooks/metronome and put its secret in the Secret as webhook-secret. The Service is ClusterIP; expose only the /webhooks/ paths to the internet.

Do this after the install, in this order:

  1. Expose /webhooks/metronome (an Ingress or a gateway route to the vBilling Service). The path answers POST only: a browser or a plain curl gets a 404, which says nothing about whether the route works. Until the secret is set, a POST also gets a 404, with metronome webhooks are not enabled (set METRONOME_WEBHOOK_SECRET).
  2. Add the webhook in Metronome's web app, under Developer, Notifications, Webhooks. Each webhook has its own secret, set when the webhook is configured; copy it.
  3. Add the secret to the Secret vBilling already uses, next to the token, and restart vBilling, which reads Secrets at startup:
    kubectl -n vbilling-system create secret generic vbilling-metronome \ --from-file=api-token=./metronome-token --from-file=webhook-secret=./metronome-webhook-secret \ --dry-run=client -o yaml | kubectl apply -f - kubectl -n vbilling-system rollout restart statefulset/vbilling
    If an operator such as External Secrets owns the Secret, add the key at its source instead: a key added by hand is removed at the operator's next sync.
  4. Check it: an unsigned POST to the public URL now gets a 400 for the bad signature, not a 404.

Webhooks are acted on only while the metronome adapter is enabled: vBilling resolves the customer in a webhook through that adapter. With metronome removed from adapters, for example to stop delivery for a while, Metronome's notifications change no billing state.

vBilling verifies Metronome-Webhook-Signature: hex HMAC-SHA256 with the secret over X-Metronome-Date (or Date), a newline and the raw body, within 5 minutes of that date. A bad signature gets a 400. A webhook names the customer by its Metronome ID; vBilling reads the customer's ingest aliases (cached for a minute) and applies the webhook to every alias it knows as a tenant, the compute aliases, whatever order the aliases are in. A customer whose prepaid commit funds several tenants holds each of their tenant IDs as an alias, so its empty wallet pauses all of them, and a top-up resumes all of them. Verified events that carry no billing signal, belong to a customer with no ingest alias at all, or repeat an event already applied get a 200 with "applied": false; other failures return a 500 so Metronome retries. A customer that has aliases, none of which vBilling knows as a tenant, is not skipped: the webhook is applied to every one of its aliases, and a billing state is recorded under each alias ("applied": true). That is what lets a webhook arrive before a tenant's first usage, and it also means a webhook for an unrelated or archived Metronome customer in the same account leaves a billing state behind under its alias. Such a state affects no cluster and can be set back to active with PUT /api/v1/billing-states/<alias>, but the API has no call that deletes it.

Metronome eventBilling state
alerts.*, for example alerts.low_remaining_commit_balance_reached or alerts.spend_threshold_reachedwarning, with the notification's name as the reason, unless a rule maps its type, or the notification itself by name or ID
payment_gate.payment_status with payment_status: faileddelinquent
payment_gate.payment_status with payment_status: paidactive, once Metronome, read again, shows nothing owed (see The prepaid wallet loop)

A webhook only raises the tenant's billing hold. A payment never lowers it by itself: vBilling reads the customer's threshold notifications again, and clears the hold only when none that a rule maps above warning is in alarm or still evaluating. A failed payment-gated top-up leaves nothing owed (Metronome voids its invoice and adds no commit), so the next successful one is judged by the notifications alone. If Metronome cannot be read, the webhook gets a 500 and Metronome retries it. Webhooks never touch holds an operator set. A hold a threshold notification raised also lifts without a webhook: vBilling reads Metronome every minute for such tenants, and lifts it on the same terms once the notifications are clear (The prepaid wallet loop).

What became of every webhook is counted, and a payment that did not unlock its tenant never stays in the log alone:

  • vbilling_webhooks_total{source,result} counts webhooks by billing platform (metronome, stripe) and result: applied, duplicate, ignored (no billing signal), unknown_customer, invalid (bad signature or body), error, and the two that matter for unlocks: unsettled (a payment arrived while a notification was still in alarm; vBilling answers 500 so the billing platform sends it again) and refused (a payment was applied, and the tenant stays blocked because something is still owed).
  • For such a payment the source billing-unlock/<tenant> in GET /api/v1/sources fails until the billing hold is lifted, across restarts, with the reason. The shipped alert VBillingWebhooksRefused fires on it.
  • The reason of a hold that a rule on another event type set names that event type, for example invoice.finalized (rule: warning).

Map any event type, or one threshold notification by its name or ID (alert:<name or ID>=state, which wins over a rule on its type), to another state with enforcement.rules (ENFORCEMENT_RULES): paused for a prepaid wallet (The prepaid wallet loop), or suspended for a hard spend cap (alerts.spend_threshold_reached=suspended), which blocks new workloads and keeps running ones; a payment lifts it only once that notification is no longer in alarm.

enforcement.modeEffect
observe (default)Records the state. It appears in GET /api/v1/billing-states, the metrics and the dashboard.
annotateAlso annotates the cluster, labels its namespace vbilling.vcluster.com/billing-state and emits a Kubernetes event.
enforceAlso acts on the state: suspended denies new pods (see Enforcement), paused pauses the tenant's clusters.

Stripe: payment failures on invoices Stripe collects reach vBilling through Stripe's webhooks, not Metronome's. With the Stripe link (METRONOME_PROVISION=true), point Stripe's webhooks at /webhooks/stripe too; vBilling resolves them through the linked Stripe customers (see Stripe webhooks). A payment through either then reads both: a Stripe invoice paid, a top-up's charge among them, never resumes a tenant whose Metronome wallet notification is still in alarm. To set a state by hand, use PUT /api/v1/billing-states/<tenant>: {"state": "active", "hold": "billing", "reason": "..."} clears the billing hold, and without hold the PUT sets or clears the operator hold.

What is verified

  • Request shapes. Every request body vBilling sends to Metronome is validated in tests against request schemas extracted from Metronome's published OpenAPI specification (ingest, customers, billable metrics, contracts, usage, billing provider configurations), strictly: an unknown field fails. The price check's requests and response fixtures are validated against the schemas of their endpoints too.
  • A fake Metronome. An in-process fake (internal/destinations/metronome/metronometest) implements what vBilling uses, as Metronome documents it: ingest with transaction_id dedupe and usage attached to the customer that gets its alias later; customers with several aliases and 409 on a taken alias, archived customers included; billable metrics, products, rate cards and rates; contracts per customer; usage aggregation; threshold notifications in alarm for a customer, as POST /v1/customer-alerts/get and POST /v1/customer-alerts/list report them, paged; and webhooks signed with Metronome's scheme. It validates request bodies against the same schemas.
  • The loop. A test runs the default mode end to end against the fake: the portal creates a customer with an identity alias and a compute alias and a contract with a prepaid commit; vBilling delivers an hour of ledger usage under the compute alias and creates nothing; price coverage reads the customer's contract; a signed alerts.low_remaining_commit_balance_reached webhook pauses the tenant through a rule, and a signed payment_gate.payment_status paid webhook resumes it once the notification is ok again (delivered while it is still in alarm, it gets a 500), both through vBilling's webhook handler; and reconciliation against /v1/usage matches the ledger.
  • Webhook signatures are checked against Metronome's documented test vector.

Troubleshooting

The pod exits at startup

initialize adapters: METRONOME_API_TOKEN is required when the metronome adapter is enabled means the token did not reach the pod. The chart mounts Secret keys as optional, so a wrong Secret name or key shows up here: the key must be api-token in the Secret named by metronome.existingSecret. METRONOME_STRIPE_LINK needs STRIPE_API_KEY to create Stripe customers is the same problem with the key api-key in stripe.existingSecret.

Delivery fails with 401

Metronome rejected the token. Usage keeps accumulating in the ledger and other destinations keep delivering. Fix the token, then restart vBilling, which reads Secrets at startup. With METRONOME_PROVISION=true the log reads bootstrap failed (delivery paused, will retry) instead.

Usage does not show on the customer

The customer does not hold the tenant ID as an ingest alias. GET /api/v1/pricing reports no customer for this alias yet for the tenant's series. Add the tenant ID to the customer's ingest aliases: Metronome attributes the usage sent earlier, and the next price check finds the customer.

A webhook is not applied

"applied": false with customer is not a vBilling tenant: ... has no ingest alias means the Metronome customer has no ingest alias, so vBilling cannot tell whose it is. Add the tenant ID as an alias, or set the state with PUT /api/v1/billing-states/<tenant>.

"applied": true but the tenant's clusters did not change: the customer's aliases do not include the tenant ID, so the state was recorded under the aliases it does have. GET /api/v1/billing-states shows a state under an ID that is not one of your tenants. Add the tenant ID to the customer's ingest aliases and have Metronome send the notification again, or set the state by hand. A webhook that is answered with a 404 means the webhook secret is not set.

Creating a customer fails with 409 (provisioning)

Another customer holds the tenant ID as alias. vBilling adopts an active one; for an archived one it logs ingest alias "..." belongs to archived customer ... and creates nothing. Remove the alias from the archived customer, or pin the tenant with vbilling.vcluster.com/metronome-customer-id.

A tenant's usage is not delivered (provisioning)

With METRONOME_PROVISION=true, a tenant whose customer cannot be created waits alone: its events are parked, every other tenant is delivered, and the cursor moves on. tenants_not_set_up on /api/v1/destinations names the tenant and Metronome's error, the source provisioning/metronome/<tenant> fails, and vbilling_tenants_blocked{destination="metronome"} counts it. A common cause is an account limit, for example a Metronome trial account's limit of five active customers. Free a customer or raise the limit; vBilling retries by itself and then ships the tenant's parked events in ledger order. Events parked for 23 hours move to the dead letters, from where they can be replayed. (Up to v0.3.2 one such tenant held delivery back for every tenant.)

Tenants get no contract

vBilling creates contracts only with METRONOME_PROVISION=true; without it, METRONOME_RATE_CARD only creates contracts with METRONOME_PROVISION=true is logged at startup. With it, contract errors name the tenant and rate card (create contract for <tenant> on <rate card>): check that the alias or ID exists in Metronome, and the tenant's vbilling.vcluster.com/plan if it has one. A new contract starts at UTC midnight of the day of the usage it is created for, so a backlog delivered after midnight is rated; when another vBilling contract of the tenant still runs, the new one takes over today.

Dead letters older than 34 days

older than Metronome's 34-day ingest window comes from a cursor rewind or an outage longer than Metronome accepts backdated events. Metronome cannot take them. They stay in the dead-letter list, and reconciliation reports them as dead_lettered.

A series is unpriced

[pricing] metronome: vcluster_private_node_hours sku=gpu-b200-8 (plan ...) is unpriced: ... and the pricing/metronome/... source name the billable metric, product or rate card, and the hint names what to add. Add it in Metronome, then run curl -H "Authorization: Bearer $VBILLING_TOKEN" -s -X POST localhost:8080/api/v1/pricing/check or wait for the next check.

Reconciliation fails or reads 0

metronome reconciliation needs whole UTC days (got ... to ...) means from or to is not a UTC midnight. A recorded total of 0 means no customer holds the tenant's alias yet, or no billable metric sums every event of the type: the log says which.
