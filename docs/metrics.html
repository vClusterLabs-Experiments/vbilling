Metrics Reference

Every metric vBilling v0.3 emits, how it is measured, and the dimensions billing platforms can price on.

i
vBilling meters closed windows (60s by default) aligned to the wall clock. Allocation metrics come from object lifetimes, to the second, so missed windows can be backfilled exactly after a restart. Every event also carries tenant, region, project, resource_id, tenant_cluster, tenant_class and a deterministic id. Schema: usage-event.v1.json.

Exact and estimated metrics

Each metric in GET /api/v1/catalog has an accuracy and a source. Exact quantities come from object lifetimes, Prometheus counter samples, per-request records or window totals you send, and they add up across windows. Estimates come from PromQL functions that extrapolate between samples (increase(), rate(), avg_over_time()); their events carry estimate: true, and the dashboard marks them with ≈. Do not let an estimate be the only evidence for usage a customer may dispute. See Usage Sources.

1. GPU Hours

vcluster_gpu_hours

Shared nodes Dedicated nodes
Source
Pod nvidia.com/gpu, amd.com/gpu, nvidia.com/mig-* and nvidia.com/gpu.shared requests, and GPUs allocated through DRA ResourceClaims; node labels (or DRA productName) for the GPU model
Unit
gpu-hours
Quantity
devices × GPU fraction × seconds running in the window / 3600

Billing starts at the first container start (image pulls and scheduling are free) and stops when the last container finishes. Pods that started or finished mid-window are billed for exactly the seconds they ran.

Fractional GPUs: a MIG slice counts as slices/7 of a GPU (A30: /4), e.g. mig-1g.10gb = 1/7. This works for the MIG mixed strategy (nvidia.com/mig-* resources), the single strategy (slices exposed as nvidia.com/gpu, product label ending in -MIG-<profile>) and GKE GPU partitions (cloud.google.com/gke-gpu-partition-size). On time-sliced nodes (nvidia.com/gpu.replicas > 1, or GKE cloud.google.com/gke-max-shared-clients-per-gpu with time-sharing or MPS) a device counts as 1/replicas. A DRA claim counts the devices allocated to it (a MIG device at its profile's fraction), split across the pods it is reserved for. The SKU becomes <model>-mig-<profile> or <model>-timeslice-<n>, always against the base GPU model (the -SHARED and -MIG- label suffixes are dropped).

Dedicated and private nodes: the node's GPU capacity is billed in whole GPUs with billing_mode=dedicated_node (control plane cluster nodes assigned to the tenant) or billing_mode=private_node (vCluster Private Nodes, Auto Nodes and Standalone, metered through the cluster's own API): MIG slices and time-slicing replicas are converted back, so 8 GPUs shared 4 ways bill as 8, not 32. Pods on those nodes are not billed again. See Dedicated and Private Nodes.

Fair metering: GPU time on a node that is NotReady or carries an UNHEALTHY_NODE_TAINTS taint is emitted as vcluster_gpu_downtime_hours instead. So is a dedicated or private node's GPU time while its GPUs are installed (GPU Feature Discovery's nvidia.com/gpu.count) but not allocatable, for example while the driver rebuilds after a reboot or a MIG change. A node whose kubelet stopped reporting is down from its last status heartbeat or Lease renewal, whichever is later, not from the Unknown mark that follows 40 to 50 seconds later. Two limits apply on a cluster's own nodes (Private Nodes, Auto Nodes, Standalone): only the Ready condition counts there, because the cluster's admins write its taints, and such a node keeps billing the most GPUs it ever had, with no downtime, when its GPUs stop being advertised (see A node bills as vBilling first saw it).

Downtime is dated to the second at both ends: from when the node was marked not ready to when it was marked ready again, as vBilling's watch saw it. A node that is ready again when its window is collected is billed only for the part of the window it was ready. An outage that began and ended while vBilling itself was down is not seen. Two limits apply. On a cluster's own nodes (Private Nodes, Auto Nodes, Standalone) only the Ready condition makes a node down; taints are ignored there, including node.kubernetes.io/unreachable and node.kubernetes.io/not-ready, because the cluster's admins write them. And such a node is billed for the most GPUs it ever had: when its device plugin goes away and it advertises fewer GPUs, or none, it keeps billing that count as GPU hours with no downtime, and the private-nodes/<cluster ID> source turns diverged (see A node bills as vBilling first saw it).

2. CPU Core-Hours

vcluster_cpu_core_hours

Shared nodes Dedicated nodes
Source
CPU_MEMORY_BASIS: metrics-server usage, container requests, or the larger of both; node capacity for dedicated nodes
Unit
core-hours
Quantity
cores × seconds in the window / 3600

usage samples metrics-server for the live window only and is never extrapolated into backfilled windows. requests is computed from pod lifetimes, so it is backfilled exactly. max bills the larger of usage and requests per pod.

The cluster's own control plane pods (app=vcluster) are covered by instance hours and excluded unless METER_CONTROL_PLANE=true.

5. Storage GiB-Hours

vcluster_storage_gb_hours

Shared nodes
Source
Bound PVCs synced from the cluster (provisioned capacity, else the request)
Unit
gib-hours
Quantity
GiB × seconds in the window / 3600, for a Bound PVC

A PVC bills nothing while it is Pending. It bills from the second it was bound, where vBilling's watch saw it bind; a PVC that was bound before vBilling could see it bills from its creation, in the window it first counts in, and windows that closed while it was still Pending are not billed afterwards.

A resized PVC bills each capacity for the time it had it: 1 GiB for the first 32 seconds of a window and 3 GiB for the rest is 116 GiB-seconds, not 180. A deleted PVC bills until the second it was deleted, so the window it was deleted in still has its storage event.

The cluster's own data volume is excluded unless METER_CONTROL_PLANE=true.

With storage allowances (billing.allowances) this metric is informational: it stays in the ledger, the exports and the webhook feed as the whole capacity, and billing platforms get vcluster_storage_overage_gb_hours instead. Its events then carry overage_gib_hours, and included_gib and allowance_per when an allowance applies to their storage class.

Dimensions

KeyMeaning
skuStorage class

vcluster_storage_overage_gb_hours

Shared nodes Dedicated nodes
Name
Storage GiB Hours above allowance
Source
The volumes of vcluster_storage_gb_hours, and the cluster's own nodes while they are billed whole
Unit
gib-hours
Quantity
GiB above the allowance × seconds in the window / 3600, at each instant of the window

In the catalog only when billing.allowances (ALLOWANCES_FILE) sets an allowance; storage is then billed through it, every storage class included (a class without an allowance is all overage). The allowance is included per node (each of the cluster's own nodes, from when it joins to when it leaves, also while it is down or the cluster is paused), per cluster, or per volume, and applies at every second of the window: when a volume is bound, resized or deleted, and when a node joins or leaves. A cluster without nodes of its own includes nothing per node. See Included storage.

Each event carries the identity of the storage event of the same cluster, class and window, and the allowance applied: included_gib, allowance_per, allowance_storage_classes for classes that share an allowance, and gross_gib_hours, the quantity of that storage event. A window with nothing above the allowance has no event; its storage event says overage_gib_hours: 0.

KeyMeaning

6. Tenant Cluster Hours

vcluster_instance_hours

Shared nodes Dedicated nodes
Source
Cluster control plane readiness
Unit
hours
Quantity
seconds ready in the window / 3600

No charge while a cluster is provisioning or asleep (no ready replica). vBilling watches each control plane's StatefulSet or Deployment and bills the time a replica was ready, to about a second, whoever stopped or started it: a control plane scaled to zero 10 seconds before a window closes bills 50 seconds of that window, none of the windows it was down for, and the rest of the window it became ready in. For time vBilling did not watch (before it first saw the cluster, or a change that happened while vBilling itself was down) it bills by what it reads when the window is collected. With PAUSE_KEEP_BILLING=control_plane a paused cluster's control plane also bills its paused time.

KeyMeaning
tenant_classTenant class

7. LoadBalancer Hours

vcluster_lb_hours

Shared nodes
Source
Services of type LoadBalancer with an assigned address
Unit
hours
Quantity
load balancers × seconds / 3600

A load balancer that is still pending (no IP) is not billed. It bills from the second it got its address, where vBilling's watch saw that; one that had its address before vBilling could see it bills from the Service's creation, in the window it first counts in. A deleted load balancer bills until the second it was deleted.

8. Network Egress GiB

vcluster_network_egress_gb

Prometheus
Source
Prometheus counter container_network_transmit_bytes_total{{selector}}: vBilling reads its raw samples and bills the exact byte increase per window. Or your EGRESS_QUERY, an estimate.
Unit
gib
Quantity
bytes / 10243

Since v0.3 egress is a counter, exact at sample granularity, and windows Prometheus could not answer are caught up. v0.2 used increase() at the window end, an estimate. {{selector}} scopes the series to the cluster: by namespace on shared and dedicated nodes, by PROMETHEUS_SOURCE_LABEL on clusters with their own nodes (see Scope series to a cluster).

The default counts the bytes the cluster's pods transmit on their own network interfaces, to any destination, traffic to other pods included. cAdvisor also reports each node's own interfaces, once for the node and once more for every pod on the host network (kube-proxy, a CNI agent, a load balancer speaker); those series are not a pod's traffic and are left out. To bill only internet egress, point EGRESS_QUERY at flow metrics from your CNI or fabric; its events are marked as estimates. EGRESS_QUERY=none turns egress off and takes the metric out of the catalog, so no billing platform is asked to price it.

Custom metrics

Declare operator metrics as a list in metering.customMetrics. The chart passes it as CUSTOM_METRICS_FILE:

metering: customMetrics: - code: slurm_gpu_hours name: Slurm GPU hours unit: gpu-hours groupKeys: [sku, region] - code: vllm_output_tokens unit: tokens billable: false # informational: a second source to cross-check

Each entry takes code, name, unit, description, groupKeys (the dimensions billing platforms price on) and billable. billable defaults to true; false keeps a metric informational: it stays in the ledger, the exports and the webhook feed, and never reaches Stripe, Metronome or Lago. The v0.2 string form, CUSTOM_METRICS="code:unit[:key|key],..." (for example inference_output_tokens:tokens:model|region), still works and declares billable metrics. The billing adapters create meters and billable metrics for billable metrics at startup.

Usage for custom metrics arrives as per-request records (POST /api/v1/records), as window totals (POST /api/v1/events), or from Prometheus (prometheus.metrics, which declares its own metrics). The built-in litellm records format declares inference_input_tokens and inference_output_tokens on every install. See Usage Sources.
